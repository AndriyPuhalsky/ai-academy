# AIA — AI Академія / AI Architect

Дві безкоштовні освітні платформи українською про ШІ/Claude. Статичний сайт (без збірки) +
Supabase (auth/прогрес/сертифікати) + Telegram Edge Function (адмін-сповіщення).

## Стек і структура
- Чистий HTML + Tailwind CDN + vanilla JS. **Жодного build-кроку** — те, що лежить у
  репозиторії, і є тим, що деплоїться.
- Увесь динамічний контент (модулі, треки, донати, посилання) — у `config.json`
  (AI Академія) і `architect.config.json` (AI Architect). Правки контенту/реквізитів роби
  ТІЛЬКИ там, не в HTML.
- `js/auth.js` — Supabase auth, завжди читає кореневий `config.json` (навіть зі сторінок
  `/modules/`), щоб вхід був спільним для обох курсів.
- `js/progress.js` / `js/module.js` — прогрес і розблокування модулів; реальна перевірка
  порядку проходження — на сервері (RPC `submit_quiz`), клієнтське блокування — лише UX.
- `js/certificate.js` / `js/verify.js` — генерація PDF-сертифіката (jsPDF + html2canvas + QR)
  і публічна перевірка коду сертифіката.
- `tg/telegram_index.ts` — Supabase Edge Function: адмін-бот (`/stats`, `/export`) +
  сповіщення про нові реєстрації. Деплоїться окремо (Supabase CLI/Dashboard), не через git
  push сайту.
- `tg/CHANGELOG.md` — журнал інфра-змін (reverse-chronological): SQL-міграції Supabase,
  деплої/оновлення Edge Functions, зміни секретів/конфігурації, версії. Поповнюй його після
  кожної SQL-міграції, деплою Edge Function чи зміни секрету.
- `deploy-guide.local.html` — приватний покроковий рантайм-гайд власника (git, Cloudflare,
  домен, Supabase). У `.gitignore` — НЕ комітити, НЕ вважати джерелом правди про код, це
  людський runbook, а не документація коду.

## Деплой
- Прод: Cloudflare **Workers** (не класичний Pages) зі статичними assets через
  `wrangler.toml` (`[assets] directory = "."`). Git push у `main` → Cloudflare сам
  пересобирає й публікує за ~хвилину.
- Локально: `python -m http.server 8000` (потрібен реальний HTTP-сервер — `fetch(config.json)`
  не працює з `file://`).
- **`.assetsignore` у корені вирішує, що НЕ роздається з сайту.** Через
  `directory = "."` Cloudflare публікує весь репозиторій, тому будь-який новий приватний
  чи службовий файл у корені стане доступним по URL, поки його не додати в `.assetsignore`
  (синтаксис як у `.gitignore`). Уже виключені: `dev/`, `tg/`, `.claude/`, `.mcp.json`,
  `CLAUDE.md`, `wrangler.toml`, `deploy-guide.local.html`. Свідомо роздаються:
  `config.json` і `architect.config.json` (сайт їх fetch-ить) та `readme.md`.
  Перевірка після зміни — `curl -s -o /dev/null -w '%{http_code}' <url>` на dev-превʼю,
  до мержу в `main`.

## Важливе застереження: регістр шляхів
Розробка велась на macOS (файлова система нечутлива до регістру), деплой — на Cloudflare
(чутливий). Один раз це вже ламало прод: папка була `CSS/`, а всі HTML посилались на
`css/custom.css` — локально працювало, на проді стилі не вантажились взагалі. Тримай усі
шляхи до файлів/папок стабільно в нижньому регістрі і звіряй регістр у будь-яких нових
посиланнях перед комітом.

## Стан бекенду (звірено з живою базою 2026-08-23 через Supabase MCP; конфіг auth — 2026-08-24)
- **Вхід через Google увімкнений і робочий (2026-08-24).** Провайдер `google` у Supabase
  `Enabled`; у Google Cloud заведено окремий проєкт `ai-academia-506420` з OAuth-клієнтом
  типу Web application, єдиний Authorized redirect URI —
  `https://hpcyrnxschpxlrxudmqk.supabase.co/auth/v1/callback`, застосунок опубліковано
  (`In production`, не `Testing`). Authorized JavaScript origins **свідомо порожні** —
  flow server-side, не Google Identity Services. Перевірка без Dashboard:
  `GET /auth/v1/settings` → `"google": true`, `GET /auth/v1/authorize?provider=google`
  → `302` на `accounts.google.com` з тим самим `client_id`.
- **`Site URL` виправлено: був `http://localhost:8000`, став `https://ai-academia.com.ua`.**
  Це ламало б не лише OAuth, а й листи скидання пароля — шаблон підставляє `{{ .SiteURL }}`.
  `Redirect URLs` були порожні; додано чотири: прод-домен, обидва `workers.dev`
  (включно з dev-превʼю) і `http://localhost:8000/**`. Без dev-превʼю в цьому списку
  GoTrue мовчки відкидав би людину на прод, і це виглядало б як баг коду.
- **Ескалацію привілеїв через `profiles.role` ЗАКРИТО 2026-08-24** (міграція
  `dev/build/002-rls-role-escalation/02-backend/db/002-lock-profiles-role.sql`, застосував
  власник). Було: `anon`/`authenticated` мали `UPDATE` на всі колонки `public.profiles`,
  включно з `role`, а `profiles_update` не мала `WITH CHECK`, тож один `PATCH` робив
  будь-якого учня адміном. Стало (звірено з живою базою після застосування): у
  `column_privileges` лишився рівно `authenticated / full_name / UPDATE`, `INSERT`
  забраний, `with_check = (id = auth.uid())` тепер явний. `full_name` лишений свідомо —
  це право фічі «зміни своє імʼя» із задачі 001. Розбір — `.../02-backend/findings.md`.
- Політики RLS справді мають вигляд `using ((id = auth.uid()) OR is_admin())`, і роль
  "public" у Dashboard справді означає лише "застосовується до всіх ролей" — запис від
  2026-08-18 у цьому був правильний. Хибним був висновок «безпечно»: дірка не в політиці,
  а в **грантах на колонки**, яких RLS не бачить взагалі (RLS не вміє обмежувати колонки —
  це робота `GRANT`), і яких той екран Dashboard не показує.
- **Не чіпати `is_admin()`.** Вона викликається всередині RLS-політик, а ті виконуються від
  імені того, хто робить запит — забрати в неї EXECUTE означає покласти читання всіх
  таблиць. Те, що advisor світить її як "anon can execute", — не дефект.
- Записів через клієнт немає взагалі: на `progress`, `quiz_attempts`, `certificates`,
  `enrollments`, `payments`, `contact_messages` політик на INSERT/UPDATE/DELETE не існує,
  тож RLS ці команди забороняє. Усе пишеться через `SECURITY DEFINER` RPC
  (`submit_quiz`, `uncomplete_module`) і через Edge Function із service-role ключем.
- `courses`/`modules` публічно читабельні (SELECT) — каталог, так і треба. Правильних
  відповідей на тести в `modules` немає (колонки: `id, course_id, code, number, slug,
  title, passing_score, sort_order`), тож публічне читання нічого не зливає.
- **Загадку `payments` закрито:** це заготовка під платні курси —
  `user_id, course_id, amount_uah, invoice_id, status (enum payment_status), created_at,
  paid_at`. **0 рядків, ніколи не використовувалась.** Не видаляти без рішення власника.
- Живі обсяги (точний `count(*)`, а не оцінки `pg_class` — вони брешуть у рази):
  `courses` 2 · `modules` 34 · `profiles` 3 · `enrollments` 6 · `progress` 35 ·
  `quiz_attempts` 47 · `certificates` 0 · `payments` 0 · `contact_messages` 0.
- Дрібніше, не терміново: `maybe_issue_certificate(p_user, ...)` і `module_unlocked(p_user, ...)`
  приймають user параметром і не звіряють його з `auth.uid()`, а EXECUTE відкритий — підробити
  сертифікат не дає, але шаблон поганий · секрет вебхука зашитий літералом у тілі
  `notify_new_profile()` (**у репозиторій не потрапив** — перевірено всю історію git) ·
  leaked password protection вимкнено (Dashboard → Authentication → Passwords).
- `TELEGRAM_SECRET_TOKEN` задеплоєно й активовано: `setWebhook` викликано з `secret_token`,
  `getWebhookInfo` підтвердив коректний URL без помилок (2026-08-18).
- `DEPLOY_CHECKLIST.md`, згаданий у `tg/GOING_LIVE.md`, і досі відсутній у репозиторії.

## Робочий процес: dev-гілка + приватна папка планування
- `dev/` — приватна локальна папка (у `.gitignore`, ніколи не потрапляє в репозиторій).
  Тут живуть стратегічні/аналітичні документи власника (напр. `strategy-analysis.local.md`,
  `ideas.local.md`) і майстерня дизайну `dev/design/` (див. окремий розділ нижче) —
  так само, як `deploy-guide.local.html` у корені. Це НЕ місце для коду сайту — самі файли
  сайту (`js/`, `modules/`, `config.json` тощо) на дев-гілці лишаються на своїх звичних
  місцях у корені репозиторію, просто на іншій гілці git.
- Реальні зміни коду роблять на git-гілці `dev` (не на `main` напряму). Push у `dev` →
  Cloudflare Workers сам піднімає окремий Preview-деплой (URL з префіксом гілки), ізольований
  від продакшн-домену. Готове й перевірене — мерджиться `dev` → `main` → автодеплой у прод.

### ПРАВИЛО: перед початком роботи — завжди перевіряти `git status`
- **Першою дією в сесії** (до будь-яких правок) — `git status` і `git rev-parse
  --abbrev-ref HEAD`. Треба знати дві речі: на якій гілці ми стоїмо і чи чисте робоче дерево.
- Якщо гілка — `main`, спершу перемкнутись на `dev` (див. правило нижче), а не правити на місці.
- Якщо в дереві є незакомічені зміни з попередньої сесії — **не змішувати їх зі своїми
  й не комітити «до купи»**. Спершу показати власнику, що там лежить, і спитати:
  закомітити окремо, лишити як є, чи відкинути.
- Це не формальність: репозиторій = те, що деплоїться, тому випадковий коміт чужої
  недоробленої зміни їде в Preview (а з `main` — у прод) разом з нашою.

### ПРАВИЛО (тверде, без винятків): main = прод, питати перед КОЖНИМ туди push/merge
- Усі зміни — код, конфіги, контент, і ця документація теж — спершу йдуть на `dev`.
  Push/коміти в `dev` не потребують окремого дозволу щоразу.
- **Перед будь-яким push або merge у `main`** — ОБОВ'ЯЗКОВО запитати власника і дочекатись
  явного "так", навіть якщо ввімкнено autonomous/auto-режим. Це правило НЕ скасовується
  жодним налаштуванням автономності — власник прямо це підкреслив.
- Винятків за розміром зміни немає: навіть одне слово в конфізі спершу йде через `dev`.

## Дизайн: папка `dev/design/`
`dev/design/` — приватна (у `.gitignore`) майстерня дизайну: бриф, конвеєр із чотирьох
агентів, готові варіанти. У репозиторій і на прод не потрапляє.

**Джерело правди про дизайн — не цей файл, а два файли в самій майстерні:**
`dev/design/README.md` (індекс задач + повний шаблон `task.md`) і `dev/design/CLAUDE.md`
(правило пісочниці, погоджений напрям, рішення по стеку). Читати їх на початку будь-якої
дизайн-дотичної роботи; якщо вони розходяться з цим розділом — вірити їм, а не йому.

### Володіння файлами: майстерню веде окрема сесія
- `dev/design/README.md`, `dev/design/CLAUDE.md`, `dev/design/.claude/` (агенти + скіли) —
  веде сесія дизайну (`design_1`). **Не редагувати їх звідси.** Потрібна зміна — написати
  тій сесії, а не правити самому.
- Єдине, що звідси дописується в README, — рядок у таблиці «Індекс задач».
- Дизайн-сесія має жорстке правило пісочниці: пише лише в `dev/design/`, усе вище тільки
  читає, git-команд не виконує. Тому перенесення макета в код сайту — завжди наша робота,
  не її. Готові до перенесення шматки вона складає в `dev/design/handoff/`.

### ПРАВИЛО: перед кожною новою задачею — перевірити, чи потрібен дизайн
- Беручи в роботу будь-яку нову задачу чи ідею, **до написання коду** відповісти на
  питання: чи змінює вона те, що бачить користувач? Якщо так — спершу бриф на дизайн,
  і тільки після обраного варіанта — верстка.
- **Потрібен дизайн:** нова сторінка/лендінг/секція; новий UI-компонент, аналога якому в
  проєкті немає; зміна візуальної мови (кольори, типографіка, спейсинг, іконки); суттєва
  перебудова layout'у; нові анімації/інтеракції; ілюстрації та графіка.
- **Не потрібен:** багфікс без зміни вигляду; текст/контент у `config.json` чи
  `architect.config.json`; бекенд (Supabase, RPC, Edge Function); рефакторинг без
  візуальних наслідків; складання екрана з уже наявних компонентів і класів
  `css/custom.css` за наявною дизайн-системою; дрібні правки доступності.
- **Сумнівний випадок — спитати власника**, а не вирішувати мовчки за нього.

### Два потоки
- **Потік А (за замовчуванням):** заповнений `task.md` → конвеєр `aia-brief-analyst` →
  `aia-reference-hunter` → `aia-design-builder` → `aia-design-validator` працює в
  дизайн-сесії → власник обирає з 2–3 варіантів.
- **Потік Б:** власник дає готовий макет (Figma / скріншот / PNG) — агенти не вигадують
  візуал, а точно відтворюють його. Вмикається полем «Готовий макет» у брифі.

### Наша роль у потоці А
1. **Завести задачу і максимально детально заповнити бриф** разом із власником — це
   головна робота цієї сесії на вході. Папка `dev/design/NNN-slug/` (номер наскрізний,
   slug латиницею в нижньому регістрі), файл `task.md` строго за шаблоном з
   `dev/design/README.md` — шаблон читати щоразу, не відтворювати з пам'яті.
2. Дописати рядок в «Індекс задач» і тримати статус синхронним із шапкою `task.md`:
   `чекає на дизайн` → `дизайн готовий` → `у коді` → `зроблено` (є ще `на паузі`,
   `відхилено`).
3. Далі задача йде в окрему дизайн-сесію — конвеєр там, ми в нього не ліземо.
4. Коли власник обрав варіант: читати `04-variants/verdict.md` (розділ «Коротко для
   власника»), заповнити поле 12 брифа («Що піде в код») і робити верстку.

Що від дизайну не залежить (бекенд, дані, контент) — робити паралельно, макет не чекати.

### Заповнюючи бриф, пам'ятати
- **Поле «Режим» — найважливіше в технічній частині.** Воно вирішує, наскільки вільно
  агенти поводяться з поточним виглядом: `у межах системи` (палітра
  `clay`/`ivory`/`sand`/`ink`, Literata + IBM Plex, наявні компоненти `css/custom.css`) ·
  `розширення системи` (нові токени, сумісні з наявними) · `нова мова` (новий візуальний
  шар, сумісність не обмежує). Стара палітра — дефолт **лише** для `у межах системи`,
  а не універсальний закон: погоджений напрям власника — «революція», де анімація є
  основою концепції, а не декором.
- **«Що має відчути користувач» — головне поле всього брифа.** Не «має бути красиво», а
  що саме людина відчуває за перші 5 секунд і чому лишається.
- **Антиреференси сильніші за референси** — «не подобається і чим саме» не пропускати.
- Незаповнене поле не страшне: агент №1 винесе його у відкрите питання й підставить
  дефолт. Страшне — вигадати за власника й записати як факт.

### Технічні рамки макета (коротко; повний список — поле 11 шаблону)
- Жодного build-кроку: чистий HTML + Tailwind CDN + vanilla JS, GSAP для руху.
- Дизайн-система пишеться стек-агностично (CSS custom properties), щоб рішення про
  фреймворк можна було відкласти. Якщо колись знадобиться компонентний движок — кандидат
  **Astro, не React** (статика, нуль JS за замовчуванням, той самий деплой у Cloudflare).
- **Макети — HTML у `dev/design/`, не Figma:** Figma не показує scroll-driven анімацію
  чесно, тому рішення по статичному кадру буде хибним. Figma лишається як вхід (потік Б)
  і як можливий експорт зрілої дизайн-системи.
- Пріоритет пристрою: повний вау на десктопі, свідомо звужена підмножина ефектів на

## Реалізація: папка `dev/build/`

`dev/build/` — інженерна майстерня: конвеєр із чотирьох агентів, який перетворює задачу на
робочий код. Різниця з дизайном в одному рядку: **`dev/design/` малює й нічого не чіпає,
`dev/build/` чіпає реальний код і нічого не малює.**

**Джерело правди — не цей розділ, а `dev/build/CLAUDE.md`** (правила, межі зон, конвеєр)
і `dev/build/README.md` (індекс задач, шаблон `task.md`, опис ролей). Читати їх на початку
будь-якої задачі реалізації; якщо вони розходяться з цим розділом — вірити їм.
`dev/build/JOURNAL.md` — на чому все спинилось і чого чекаємо.

Створено 2026-08-23. Веде **коренева сесія** (ця), не окрема — бо саме тут git-права.

### Конвеєр
| # | Агент | Роль |
| - | ----- | ---- |
| 1 | `aia-build-pm` | Коротке ТЗ → план + **контракт даних** (він дає працювати паралельно) |
| 2 | `aia-build-backend` | Дані, RLS, RPC, Edge Function, клієнтський шар до Supabase |
| 3 | `aia-build-frontend` | Точно втілює затверджений макет. **Столяр, не дизайнер** |
| 4 | `aia-build-qa` | Ламає на dev-превʼю. **Не лагодить** — описує з доказами |

Агенти 2 і 3 — **паралельно** (їх тримає контракт даних). Агент 4 — брама з циклом фіксів,
максимум 3 кола, далі до власника. Усі Opus 5 / effort `high`.

**Вхід задачі:** коротке ТЗ власника (2–5 рядків) + `dev/design/NNN-slug/SUMMARY.md`, якщо
задача змінює вигляд. Немає макета, а вигляд змінюється → стоп, спершу бриф у дизайн.
**Нумерація спільна з дизайном:** одна фіча = один номер.
