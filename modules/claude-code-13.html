Фаза 3 · Налаштування під себе

Уся .claude/ і settings.json

Середній · 8 блоків · ≈ 45 хв читання

Досі ти приймав рішення щоразу заново: яку модель узяти, що дозволити, куди пустити Claude Code. Налаштування — це спосіб записати рішення один раз, щоб воно діяло саме. Але записане не завжди діє, і в цьому вся складність теми: файлів налаштувань не один, а чотири, вони перекривають один одного за суворим порядком, а коли твоє значення програло — ніхто про це не повідомляє. Цей модуль вчить не переліку ключів, а вмінню відповісти на питання «чому воно не діє і чий конфіг переміг».

Одразу головне: команди claude config більше не існує

Якщо ти читав будь-який туторіал із рядком claude config set -g theme dark — він мертвий. Такої підкоманди в Claude Code немає. Найгірше в цьому те, що claude config --help не падає з помилкою: він друкує звичайну довідку, ніби все гаразд. Дослівний вивід — у блоці 2, з поясненням, чому так.

Налаштування змінюють двома способами: командою /config усередині сесії або редагуванням файла settings.json руками. Цей урок — про другий спосіб, бо він охоплює все, а меню /config — лише кілька особистих опцій.

Що в цьому модулі є, а чого немає

Є: що таке папка .claude/ і що в ній лежить · чотири файли налаштувань і на кого кожен впливає · порядок перекриття й чому списки поводяться інакше за решту ключів · сімнадцять ключів, які справді потрібні · /config і --settings · як своєю командою побачити, що завантажилось · що робить Claude Code зі зламаним файлом · ключі каналу оновлень.

Немає: CLAUDE.md і пам'яті — це модуль 12; синтаксису правил дозволів (Bash(npm run *) тощо) — це модуль 7; перехоплювачів подій (hooks) — модуль 16; навичок і плагінів — модуль 14; MCP — модуль 18; глибокої діагностики — модуль 17. І немає вичерпної таблиці ключів: їх понад дві сотні, вони живуть у довіднику «Ключі settings.json».

1Навіщо це

Почнемо з факту, який дивує майже всіх: установка Claude Code не створює жодного файла налаштувань. Це дослівна позиція документації. Тобто перший запуск працює на вбудованих значеннях, і поки тебе все влаштовує, налаштувань у тебе немає взагалі — і це нормальний стан, а не недоробка.

Файли з'являються тоді, коли з'являється потреба. Три типові потреби:

  • «Перестань питати про одне й те саме». Ти дозволяєш Claude Code запускати твої тести без запиту — і це рішення треба десь зберегти.
  • «У цьому проєкті працюємо так». Команда домовилась про однакові дозволи й однакову модель — і домовленість треба покласти в репозиторій, а не переказувати кожному новачкові.
  • «Мені особисто зручніше інакше». Своя тема оформлення, свій рядок стану, своя модель — але не для всієї команди, а тільки для себе.

Три потреби — три різні адресати: ти на цій машині, проєкт для всіх, ти в цьому проєкті. Саме тому файлів налаштувань кілька, а не один. І саме тому виникає питання, з якого цей модуль почався: коли те саме написано у двох файлах, чиє значення переможе?

Що таке файл налаштувань фізично

Це звичайний текстовий файл у форматі JSON (вимовляється «джейсон»). JSON — це спосіб записати налаштування так, щоб їх читала програма. Виглядає він так: 

{
  "theme": "dark",
  "cleanupPeriodDays": 30
}

Усе, що треба про нього знати новачкові:

  • увесь вміст обгорнутий у фігурні дужки { };
  • усередині — пари "ключ": значення, розділені комами;
  • назва ключа завжди в подвійних лапках; текстове значення — теж, а число й true/false — без лапок;
  • значенням може бути не тільки число чи текст, а й вкладений блок у своїх фігурних дужках або список у квадратних [ ].
Два правила, на яких ламаються всі

Claude Code читає строгий JSON. У ньому немає коментарів (рядок, що починається з //, — це помилка) і не можна лишати кому після останнього елемента. Обидві звички приходять із мов програмування, де так робити можна; тут вони перетворюють файл на нечитабельний.

Наслідок сильніший, ніж здається: зламаний файл не діє цілком — не «частина налаштувань не спрацювала», а весь файл пропущений. У блоці 2 показано, як це виглядає на екрані.

Три слова, які знадобляться далі

Ці три поняття будуть у кожному наступному блоці, тому вводимо їх зараз.

  • Область дії (scope) — на кого поширюється те, що ти записав: на тебе на всій машині, на всіх у цьому проєкті, на тебе в цьому проєкті або на всю організацію.
  • Перекриття (precedence) — правило, за яким обирається одне значення, коли той самий ключ заданий у кількох місцях. Це не «останній виграє» і не «найновіший виграє», а фіксований порядок рівнів.
  • Керовані налаштування (managed settings) — файл, який на твою машину кладе роботодавець або організація. Ти його не створюєш і не редагуєш, а він перекриває все, що написав ти. Якщо Claude Code у тебе особистий, керованих налаштувань у тебе немає — але знати про них варто, бо саме вони пояснюють ситуацію «на роботі поводиться інакше, ніж удома».

Далі — те, як це виглядає в терміналі.

2Як це виглядає на екрані

Почнемо з екрана, який коштує дорожче за всі інші в цьому модулі, — з того, як виглядає застаріла інструкція, що вдає робочу.

Підкоманди config немає, але помилки теж немає

Придивись до третього рядка знизу: Arguments: prompt — Your prompt. Це і є пояснення. Claude Code розбирає слово config не як назву підкоманди (бо такої підкоманди немає), а як перше слово твого завдання — тобто як текст, який ти хочеш надіслати моделі. А --help перехоплює запуск раніше й друкує довідку. Виходить видимість успіху: команда «спрацювала», екран заповнився корисним текстом, і людина йде далі впевненою, що claude config існує.

Живий перелік підкоманд на версії 2.1.236 — тринадцять штук: agents, auth, auto-mode, doctor, gateway, import, install, mcp, plugin, project, setup-token, ultrareview, update. Слова config серед них немає.

Не перевіряй це набором claude config set … без --help

Без --help той самий рядок перетвориться на завдання для агента: Claude Code візьме «config set theme dark» за твій запит і піде його виконувати — витрачаючи ліміт і, можливо, правлячи щось у папці. Перевіряй наявність підкоманди переліком Commands: у виводі claude --help, а не спробою її запустити.

Як виглядає зламаний файл налаштувань

Другий екран знято в тимчасовій папці, у яку навмисно покладено файл .claude/settings.json із зайвою комою після останнього рядка. Команда claude doctor перевіряє стан установки й читає файли налаштувань поточної папки — у власній довідці Claude Code це сказано дослівно: «Reads settings files in the current directory without a trust prompt».

Вивід скорочено в позначених … місцях, а довгий шлях до тимчасової папки замінено на короткий /Users/anna/claude-lab. Решта рядків — дослівні.

Зверни увагу на останній рядок: «No installation issues found» стоїть поруч зі знайденою помилкою. Суперечності тут немає — claude doctor розділяє «проблеми встановлення» і «проблеми налаштувань» у два різні розділи. Якщо читати лише останній рядок, можна вирішити, що все гаразд.

Три екрани, яких у цьому уроці немає, і чому

Три найважливіші екрани теми — інтерактивні: вони малюються всередині сесії й не існують як текст, який можна зняти командою. Домальовувати їх у курсі про свіжість фактів було б дивно, тому описуємо словами, а дослівні рядки даємо в <code>.

  • Вікно Settings Error. Якщо на старті інтерактивної сесії Claude Code знаходить зламаний файл користувача, проєкту або локальний, він показує діалог із трьома виходами: полагодити файл з допомогою Claude, вийти або працювати далі без зламаних налаштувань. У запуску з -p (без інтерфейсу) діалогу немає взагалі: програма мовчки пропускає зламане й працює далі. Саме тому документація радить після такого запуску виконати claude doctor — інакше про пропущене не дізнаєшся ніяк.
  • Вкладка Status у /status. Там є рядок Setting sources, який перелічує кожен файл налаштувань, завантажений у цю сесію: User settings, Project local settings і так далі. Коли діють керовані налаштування, у дужках показано, яким шляхом вони приїхали.
  • Вкладка Config у /config. Це короткий список особистих опцій — тема, режим редактора, докладність виводу, — а не перегляд вмісту твого settings.json. Обидві вкладки відкриває той самий діалог: /status і /config — це одне вікно, різні вкладки.

3Як це працює

Тепер по порядку: які файли існують, де вони лежать і хто кого перекриває.

Чотири файли й п'ятий, керований

Два слова з таблиці нижче варто пояснити наперед. Репозиторій — це папка проєкту під наглядом системи контролю версій git: вона зберігає історію змін і дозволяє кільком людям працювати над одним кодом. Закомітити файл — записати його в цю історію, тобто зробити спільним для всіх, хто скопіює проєкт собі. Якщо ти git не використовуєш, ці рядки тебе не стосуються: файли з таблиці однаково працюють і в звичайній папці.

.claude/settings.json
спільний проєктний		 на всіх, хто працює в цій папці; у git-репозиторії — на всіх, хто його клонував, якщо файл закомічений командні дозволи, перехоплювачі подій, плагіни, змінні середовища проєкту

Знак ~ означає домашню папку користувача. На Windows ~/.claude — це %USERPROFILE%\.claude. Якщо треба перенести всю конфігурацію в інше місце (наприклад, тримати робочий і особистий акаунти окремо), для цього є змінна середовища CLAUDE_CONFIG_DIR: вона переносить і налаштування, і історію сесій, і плагіни.

Ці файли не з'являться самі, доки ти чогось не зробиш

~/.claude/settings.json Claude Code створює сам, коли ти вперше змінюєш у меню /config опцію, що зберігається в користувацькому файлі, — наприклад тему. А .claude/settings.local.json з'являється тоді, коли ти вперше відповідаєш на запит дозволу «так, і більше не питай»: саме туди Claude Code записує це рішення як правило allow.

Що ще лежить у папці .claude/

settings.json — не єдиний її мешканець. Папка .claude/ існує у двох примірниках одночасно: глобальна в домашній папці (~/.claude/) і проєктна в папці проєкту. Ось що в них буває — з позначкою, чи має воно їхати в репозиторій разом із кодом.

Файл або папка Де буває Комітити Що робить
CLAUDE.md проєкт і глобально так інструкції, що вантажаться щосесії (модуль 12)
rules/*.md проєкт і глобально так тематичні інструкції, за бажанням прив'язані до шляхів (модуль 12)
settings.json проєкт і глобально так дозволи, перехоплювачі подій, змінні середовища, модель за замовчуванням
settings.local.json тільки проєкт ні твої особисті перекриття в цьому проєкті
.mcp.json тільки проєкт, у корені репозиторію так зовнішні інструменти MCP для команди (модуль 18)
skills/<назва>/SKILL.md проєкт і глобально так навички, що викликаються як /назва (модуль 14)

agents/*.md проєкт і глобально так субагенти зі своїм промптом та інструментами (модуль 15)
output-styles/*.md проєкт і глобально так свої секції системного промпту — тон і формат відповідей

keybindings.json, themes/*.json тільки глобально ні свої гарячі клавіші й свої теми оформлення

Два файли навмисно живуть поза папкою: .mcp.json і CLAUDE.local.md лежать у корені проєкту, а не всередині .claude/. Це не дрібниця — покладений «логічно», всередину папки, .mcp.json не завантажиться взагалі.

Порядок перекриття: хто кого перебиває

Коли той самий ключ заданий у кількох місцях, Claude Code бере значення з найвищого рівня, який його задає. Порядок фіксований — від найсильнішого до найслабшого.

  C --> D["4. .claude/settings.json — спільний файл проєкту"]
  D --> E["5. ~/.claude/settings.json — твій файл на всю машину"]

Ключ, заданий вище, перекриває той самий ключ нижче. Стрілка тут означає «сильніший за», а не послідовність кроків.

Логіка в цьому порядку є, і вона допомагає його запам'ятати: чим вужче коло людей, яких стосується файл, тим він сильніший — крім найвищого рівня, де організація перебиває всіх свідомо. Твій особистий файл у проєкті сильніший за спільний файл команди, спільний файл команди — сильніший за твої загальні вподобання.

Списки — виняток: вони зливаються, а не перекриваються

Якщо ключ містить список — наприклад permissions.allow, — Claude Code не обирає один із файлів, а об'єднує списки з усіх. Тобто твої дозволи додаються до командних, а не замінюють їх. Це часте джерело подиву: людина прибирає правило зі свого файла й дивується, що воно й далі діє — бо воно приїхало з проєктного.

У кількох ключів, що містять моделі (fallbackModel, modelPicker, availableModels, modelSettings), власні правила: там позиція в списку має значення, тому береться значення цілком з одного файла.

Змінні середовища — не рівень у цьому стосі

Змінна середовища (environment variable) — це значення, яке ти задаєш у терміналі перед запуском програми; у модулі 1 ти вже бачив одну таку — PATH. Частина налаштувань Claude Code має і ключ у файлі, і парну змінну.

Спокуса вважати, що змінні стоять десь у стосі вище або нижче за файли. Документація каже прямо: вони не є рівнем. Хто виграє, вирішується для кожної пари окремо. Приклад із доксів: ANTHROPIC_MODEL, експортована в твоїй оболонці, перебиває ключ model з будь-якого файла, а ANTHROPIC_DEFAULT_MODEL діє тільки тоді, коли жоден файл model не задає. Дві схожі змінні — дві різні поведінки.

Окремий випадок — блок env усередині файла налаштувань. Він поводиться як звичайний ключ і підкоряється порядку перекриття, а значення з нього перезаписує те, що ти експортував в оболонці.

  S --> M["Системна папка ОС: managed-settings.json"]
  H --> X["Один набір значень на цю сесію"]
  W --> X
  R --> X
  M --> X
  style X fill:#2A211C,stroke:#D97757,color:#F0EEE6

Спільний проєктний файл читається з робочої папки сесії, а локальний — з кореня git-репозиторію. Це різні місця, і саме тут людина найчастіше шукає файл не там.

Розберемо праву гілку окремо, бо вона неочевидна. Якщо ти запустив Claude Code у підпапці git-репозиторію, локальний файл він читає й пише в корені репозиторію, а видане тобою «більше не питай» діє на весь репозиторій. Так поводяться версії починаючи з 2.1.211; раніше файл лежав у тій папці, звідки стартувала сесія, і старий файл далі читається — але при збігу ключів виграє той, що в корені.

Є винятки, коли локальний файл лишається поруч зі спільним: поза git-репозиторієм, коли коренем репозиторію є твоя домашня папка, на Windows, а також коли корінь репозиторію (або його .git чи .claude) належить іншому користувачу системи.

Сімнадцять ключів, які справді потрібні

Повний перелік налаштувань на 2026-09-04 містить 223 ключі — це прямий підрахунок рядків таблиці «All settings» офіційного довідника. Знімок тієї самої сторінки, зроблений днем раніше, містив 222: за добу додався рівно один ключ, permissions.blockReadsOutsideWorkingDirectories. Це найкраща ілюстрація того, чому цей курс просить звірятись із джерелом, а не з пам'яттю.

Учити всі 223 не треба й не варто. Робочий набір, якого вистачає на перший рік:

Колонка «де можна задавати» — не прикраса. У довіднику вона називається Scope і має п'ять можливих значень: Any file (усі чотири файли), User, local, or managed, User or managed, Managed (лише організація) і Global config (лише ~/.claude.json). Ключ, у якого стоїть щось інше, ніж Any file, не спрацює зі спільного файла проєкту — і мовчки, без попередження. Це головна причина ситуації «закомітив налаштування, а в колег воно не діє».

Ключі, що керують оновленнями

У модулі 3 ти вже бачив, що канал latest і канал stable розходяться на десяток версій. Цими налаштуваннями керують так:

  • autoUpdatesChannel — "latest" (за замовчуванням) або "stable": версія приблизно тижневої давнини, з якої відкинуті релізи з великими регресіями;
  • minimumVersion — не давати автооновленню поставити щось нижче за вказану версію;
  • requiredMinimumVersion і requiredMaximumVersion — відмовлятись стартувати на надто старій або надто новій версії. Обидва — лише керовані: у своєму файлі їх писати марно;
  • змінна DISABLE_AUTOUPDATER=1 вимикає фонові автооновлення, але claude update руками далі працює; DISABLE_UPDATES=1 суворіша — вона блокує й ручне оновлення, і claude install;
  • CLAUDE_CODE_PACKAGE_MANAGER_AUTO_UPDATE=1 дозволяє Claude Code самому запускати оновлення твого пакетного менеджера у фоні — це стосується Homebrew і WinGet.

Поруч живуть ще дві змінні, які часто шукають саме тут: USE_BUILTIN_RIPGREP=0 перемикає пошук по файлах на системний rg замість вбудованого, а CLAUDE_CODE_GIT_BASH_PATH — тільки для Windows: шлях до bash.exe з Git Bash, коли той установлений, але не в PATH.

Сім ключів, де суворіше значення перемагає організацію

Правило «керовані налаштування перебивають усе» має точний перелік винятків. Для семи ключів, пов'язаних із безпекою, Claude Code бере суворіше значення навіть із нижчого рівня: disableClaudeAiConnectors, enableArtifact, isolatePeerMachines, remoteControlAtStartup, crossSessionInbound, useAutoModeDuringPlan, syncClaudeAiSkills. Тобто заборонити собі щось ти можеш завжди, а дозволити собі те, що заборонила організація, — ні. Логіка одна: послаблення вгору не піднімається, посилення — піднімається.

4Зроби сам

Зробимо тренувальну папку, покладемо в неї налаштування, зламаємо їх навмисно й полагодимо. Нічого з твоїх робочих проєктів це не зачепить.

Крок 1. Тренувальна папка

Відкрий термінал і виконай два рядки нижче. Перший створює папку claude-lab у твоїй домашній папці разом із вкладеною .claude, другий переводить тебе всередину.

Крапка на початку імені .claude робить папку прихованою: у Finder і в звичайному ls її не видно. Щоб побачити — набери ls -a і натисни Enter.

Крок 2. Перший файл налаштувань

Створи файл ~/claude-lab/.claude/settings.json у будь-якому текстовому редакторі й поклади в нього такий вміст: 

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  },
  "cleanupPeriodDays": 7
}

Що тут написано. Правило deny забороняє читати файли .env — у них зазвичай лежать паролі й ключі доступу, і найдешевший спосіб не злити їх у транскрипт сесії — не давати їх читати взагалі (синтаксис таких правил — модуль 7). Ключ cleanupPeriodDays: 7 каже зберігати транскрипти тиждень замість стандартних тридцяти днів.

Рядок $schema — необов'язковий, але корисний: він указує редакторові на опубліковану схему налаштувань, і редактор починає підказувати назви ключів і підкреслювати помилки. Про його межу — у блоці 6.

Крок 3. Перевір, що файл читається

Не запускаючи сесію, у тій самій папці набери claude doctor і натисни Enter. Якщо у виводі немає розділу Invalid settings — файл коректний. Мовчання тут означає «все гаразд»; це та сама логіка мовчання, що й у звичайних команд термінала з модуля 1.

Крок 4. Зламай навмисно

Тепер додай кому після останнього ключа — так, щоб було "cleanupPeriodDays": 7, — збережи файл і виконай claude doctor ще раз. Ти маєш побачити рядок Invalid or malformed JSON з повним шляхом до свого файла, як на екрані в блоці 2.

Це вправа не заради вправи. Ти щойно побачив своїми очима головну властивість теми: помилка в одному символі вимикає весь файл, і без окремої перевірки про це не дізнаєшся.

Крок 5. Признач значення, яке видно

Прибери зайву кому й додай до файла ще один ключ — "spinnerTipsEnabled": false. Він вимикає короткі підказки, які Claude Code показує під індикатором роботи. Запусти claude у цій папці й подивись: підказки під спінером зникли.

Тепер створи поруч файл .claude/settings.local.json із вмістом { "spinnerTipsEnabled": true } і перезапусти сесію. Підказки повернулись — бо локальний файл стоїть у стосі вище за спільний проєктний. Це і є перекриття, побачене на власні очі.

Крок 6. Прибери за собою

Тренувальна папка більше не потрібна: видали ~/claude-lab цілком. Якщо ти встиг запустити в ній сесію, у твоїй домашній папці лишиться ще й транскрипт — прибрати його штатно можна командою claude project purge ~/claude-lab (вона друкує повний план видалення й питає підтвердження, а з ключем --dry-run показує план і нічого не чіпає).

5Як перевірити, що вийшло

Тема налаштувань небезпечна саме тим, що помилка мовчазна. Тому перевірка тут не «на всякий випадок», а частина роботи. Чотири інструменти, від найдешевшого.

claude doctor — не заходячи в сесію

Ця команда читає файли налаштувань поточної папки й друкує діагностику. Вона знаходить не тільки зламаний JSON, а й окремі значення, які не проходять перевірку. Екран нижче знятий у папці, де в коректному з погляду синтаксису файлі стояло "cleanupPeriodDays": 0:

Довгі рядки перенесені, кінець підказки скорочено, шлях до тимчасової папки замінено на /Users/anna/claude-lab. У тому ж файлі була ще одна помилка — невідома назва події для перехоплювача, — і claude doctor надрукував про неї окремий рядок вище; тут його пропущено, бо він про тему модуля 16. Решта — дослівно.

Тут видно три корисні речі одразу: який файл, який саме ключ (після знака ›) і що з ним не так, разом із запропонованим виправленням. Для решти файла це не фатально: коли ламається окреме значення, а не весь JSON, Claude Code пропускає це значення й лишає файл чинним — у документації такий випадок називається Settings Warning, на відміну від Settings Error.

/status — які файли взагалі завантажились

Усередині сесії набери /status. На вкладці Status є рядок Setting sources — перелік завантажених файлів. Він відповідає на питання «чи мій файл прочитано взагалі».

Чого він не показує — який саме файл дав який ключ. Тобто «мій файл прочитано» і «моє значення перемогло» — два різні факти, і /status підтверджує лише перший. Для другого доводиться йти від зворотного: подивитись у стос перекриття й перевірити файли вище свого.

Ще чотири команди, кожна про своє

  • /permissions — підсумкові правила дозволів, що діють зараз (після злиття всіх файлів);
  • /hooks — які перехоплювачі подій зареєстровані й з якого файла приїхали;
  • /mcp — які сервери MCP підключені й у якому вони стані;
  • /context — що реально потрапило в контекст: інструкції, навички, файли пам'яті.

Повний розбір діагностики — модуль 17. Тут важливе одне: для кожної частини конфігурації є своя команда, яка показує підсумок, а не твій намір.

Перевірка, чи локальний файл справді поза git

Коли Claude Code сам створює .claude/settings.local.json у git-репозиторії, він одноразово додає рядок **/.claude/settings.local.json до твоїх глобальних git-виключень — файла ~/.config/git/ignore (або того, на який указує налаштування core.excludesFile). Перевірити, що це справді сталось, можна однією командою в папці репозиторію: git check-ignore -v .claude/settings.local.json. Якщо правило діє, вона надрукує рядок виду /Users/anna/.config/git/ignore:1:**/.claude/settings.local.json — тобто назве файл із правилом, номер рядка й саме правило. Якщо вона не друкує нічого, файл не виключений, і найближчий коміт забере твої особисті налаштування в репозиторій.

Чи знає твоя збірка про цей ключ

Окрема ситуація: у документації ключ описаний, а в тебе не діє. Причина часто не в помилці, а в різниці версій — документація описує найновіший випуск, а в тебе стоїть старіший. Прапорець можна перевірити запуском, а ключ налаштувань запустити не можна. Обхід — пошук назви всередині самого файла програми:

Читається це так. strings дістає з двійкового файла всі текстові шматки, grep -c рахує, у скількох рядках трапилась назва. Ключ statusLine знайдений 33 рази — збірка про нього знає. blockReadsOutsideWorkingDirectories — нуль: саме той ключ, що з'явився в довіднику 2026-09-04 і потребує версії 2.1.257, а тут стоїть 2.1.236. Третій рядок — контрольний: вигадана назва теж дає нуль, і це доводить, що метод відрізняє наявне від вигаданого, а не друкує нулі завжди.

Чесна межа цього прийому

Число більше за нуль доводить, що назва є всередині збірки. Воно не доводить, що можливість доступна саме твоєму акаунту чи твоєму плану. І нуль не завжди означає «немає»: назва може складатись у програмі з частин. Тому це не заміна документації, а швидка відповідь на питання «моя версія взагалі чула це слово».

6Типові граблі

Усі сім пунктів нижче об'єднує одна риса: жоден із них не дає помилки. Налаштування виглядає записаним і не діє.

1. "auto" і "bypassPermissions" із проєктного файла не діють

Найгостріша пастка теми. Значення auto і bypassPermissions ключа permissions.defaultMode не спрацьовують зі спільного проєктного або локального файла. Сесія тихо стартує в звичайному ручному режимі, а людина впевнена, що налаштувала автоматичний.

Правильне місце для них — твій користувацький файл ~/.claude/settings.json або керовані налаштування; на одну сесію те саме дає прапорець --permission-mode. Причина обмеження зрозуміла, якщо подумати про безпеку: інакше будь-який склонований із мережі репозиторій міг би сам собі видати повну свободу дій одним закоміченим файлом.

Тонкість, яку варто знати: для bypassPermissions це обмеження з'явилось у версії 2.1.257. До неї значення діяло з будь-якого файла. Тобто на старішій збірці ти побачиш стару поведінку — і це не привід шукати помилку в себе.

2. ~/.claude.json — це не файл налаштувань

Два файли з дуже схожими іменами роблять різні речі: ~/.claude/settings.json — твої налаштування, а ~/.claude.json (окремий файл поруч із папкою) — внутрішній стан програми: вхід, персональні сервери MCP, перемикачі інтерфейсу. Ключі permissions, hooks і env, покладені в ~/.claude.json, ігноруються повністю. Документація виносить цей випадок в окремий рядок таблиці типових причин — тобто спотикаються на ньому регулярно.

3. Закомітив ключ — а в команди не діє

Дві різні причини, і лікуються вони по-різному.

  • Ключ не можна задавати зі спільного файла. Це видно в колонці Scope довідника: усе, крім Any file, зі спільного проєктного файла не працює. Лікування — перенести ключ у користувацький файл кожного або в керовані налаштування.
  • Ключ чекає на довіру до папки. Правила permissions.allow, permissions.additionalDirectories, extraKnownMarketplaces і більшість значень env діють лише після того, як людина підтвердила довіру до цієї робочої папки. До того моменту вона й далі бачить запити дозволу. Правила deny і ask, навпаки, діють одразу — заборона не чекає ні на що.

4. Проєктний файл не може задати частину змінних середовища

Та сама логіка, що й у пункті 1, але про блок env. Проєктний і локальний файли не можуть задавати змінні, якими репозиторій не має права керувати: ті, що вирішують, куди Claude Code пише свої файли (CLAUDE_CONFIG_DIR, HOME, TMPDIR, сімейство XDG_*), ті, що вивантажують вміст сесії назовні, і ті, що змінюють спосіб запуску. Claude Code відкидає такий рядок і пише попередження, яке видно лише з claude --debug. Задавати їх треба в оболонці, у користувацькому файлі або в керованих налаштуваннях.

5. Шукаєш локальний файл не в тій папці

Ти запустив Claude Code у підпапці репозиторію, відповів «більше не питай» — і йдеш шукати .claude/settings.local.json поруч. А він у корені репозиторію (версії від 2.1.211). Ще один бік тієї самої монети: якщо ти створив цей файл руками, а Claude Code у нього ще жодного разу не писав, то й у git-виключення він його не додавав. Такий файл треба ігнорувати самому, інакше твої особисті дозволи поїдуть у репозиторій із першим же комітом.

6. Редактор підкреслює ключ червоним, а ключ робочий

Рядок $schema дає редакторові підказки — і разом із ними джерело хибної тривоги. Опублікована схема налаштувань відстає від релізів, тому попередження на щойно задокументований ключ не означає, що конфігурація зламана. Це прямо сказано в документації. Перевіряти треба не кольором підкреслення, а командою claude doctor.

7. Правка не діє, бо ключ читається лише на старті

За замовчуванням Claude Code стежить за файлами налаштувань і підхоплює більшість змін без перезапуску — включно з permissions і hooks. Але кілька ключів читаються один раз, на старті сесії, і правка посеред роботи їх не зачепить:

  • model — щоб змінити модель усередині сесії, є команда /model;
  • effortLevel і modelSettings — для них є /effort;
  • outputStyle — він частина системного промпту, тому нова величина застосується після /clear або перезапуску.

7Часті питання

У мене немає жодного файла налаштувань. Це нормально?

Так. Установка не створює жодного з них, і Claude Code повністю працездатний на вбудованих значеннях. Файл з'являється тоді, коли ти вперше змінюєш опцію в /config або вперше кажеш «більше не питай» на запиті дозволу.

Чи треба класти .claude/settings.json у репозиторій?

Якщо ви працюєте командою — так, у цьому й сенс цього файла: усі, хто склонував репозиторій, отримують однакові дозволи, перехоплювачі подій, змінні середовища й плагіни. Особисті винятки кожен тримає у своєму .claude/settings.local.json, і комітити їх не треба.

Як спробувати налаштування, нічого не зберігаючи?

Прапорцем --settings при запуску: він приймає або шлях до файла, або JSON прямо в рядку. Значення діє одну сесію й не пишеться в жоден файл. У стосі перекриття він стоїть вище за всі твої файли й нижче за керовані налаштування. Приклад із документації: claude --settings '{"model": "claude-opus-4-8"}'.

Частина ключів має ще й власний прапорець (--model для model, --effort для effortLevel) або парну змінну середовища (ANTHROPIC_MODEL). Задавати Managed- і Global config-ключі через --settings не можна.

Як подивитись, чи винен у дивній поведінці мій конфіг?

Запусти claude --safe-mode — сесія стартує з вимкненими усіма кастомізаціями: CLAUDE.md, навичками, плагінами, перехоплювачами подій, серверами MCP, своїми командами й агентами. Якщо проблема зникла — причина в одному з вимкнених шарів. Вхід, вибір моделі, вбудовані інструменти й дозволи в цьому режимі працюють як звичайно, а керована політика організації лишається чинною.

Точніший інструмент — --setting-sources: він приймає перелік із user, project, local і завантажує тільки названі рівні. Так можна вимкнути рівно один шар і подивитись, що зміниться. А зовсім чисту перевірку дає запуск із порожньою конфігураційною папкою: cd /tmp && CLAUDE_CONFIG_DIR=/tmp/claude-clean claude — ця сесія не бачить нічого з твоєї ~/.claude (першого разу вона попросить вибрати тему й увійти — це ознака, що чиста папка справді діє).

Мене цікавить ключ, якого немає в переліку з блоку 3. Де його шукати?

У довіднику «Ключі settings.json» — там повний перелік із коротким описом кожного й колонкою області дії. Довідник не проходять і не здають: до нього повертаються. У самій документації те саме живе на сторінці settings-reference, і саме її варто відкривати, коли треба дослівне формулювання й позначка «потрібна версія не нижче за».

Чому в мене на роботі Claude Code поводиться інакше, ніж удома?

Найімовірніше, на робочій машині розгорнуті керовані налаштування. Перевірка — рядок Setting sources у /status: він назве кероване джерело, якщо воно діє. Змінити його зі свого боку не вийде за конструкцією — крім семи «суворіших» ключів із кінця блоку 3. Це не поломка, це політика організації.

Скільки взагалі є ключів і чи треба їх знати?

На 2026-09-04 їх 223, і кількість змінюється: за добу до того їх було 222. Знати їх напам'ять не треба нікому — це довідкова інформація за визначенням. Знати треба інше: як улаштований порядок перекриття, як подивитись область дії ключа й якою командою перевірити, що твій файл прочитано.

8Підсумок і наступний крок

Що варто винести з модуля
  • Підкоманди claude config не існує, а claude config --help друкує звичайну довідку, бо слово config розбирається як текст твого завдання. Будь-яка інструкція з claude config set застаріла.
  • Файлів налаштувань чотири: користувацький, спільний проєктний, локальний і керований. Чим вужче коло людей, тим сильніший файл, а керований перебиває всіх.
  • Списки зливаються, а не перекриваються. Твій permissions.allow додається до командного, а не замінює його.
  • Змінні середовища — не рівень у стосі. Хто виграє, вирішується для кожної пари «змінна — ключ» окремо.
  • Колонка Scope вирішує долю закоміченого ключа. Усе, крім Any file, зі спільного проєктного файла мовчки не діє — як auto й bypassPermissions.
  • Перевірка — окрема дія. claude doctor — до сесії, /status — які файли завантажені, /permissions, /hooks, /mcp, /context — по своїй частині.
  • Ключів 223, і їх кількість змінюється щодня. Вичерпний перелік — у довіднику, а не в пам'яті.

Наступний крок

Далі — модуль 14 «Навички, команди, плагіни»: як покласти в .claude/skills/ власну навичку, викликати її як /назва і поділитись нею з командою. Папку, у якій це все живе, ти щойно розібрав, тому там лишиться сам вміст.

А корисна звичка з цього модуля одна й дешева: після кожної правки файла налаштувань виконуй claude doctor у тій самій папці. Це п'ять секунд, і саме вони відрізняють «я налаштував» від «я думаю, що налаштував».

Квіз: перевір себе

Шість питань без оцінок і дедлайнів. Вони перевіряють розуміння, а не пам'ять на назви ключів: до кожної відповіді одразу з'являється пояснення, чому решта варіантів хибні.
