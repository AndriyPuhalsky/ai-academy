Трек IV · Агенти та продакшн

Агенти й агентні системи

Просунутий · 5 уроків · ≈ 75 хв читання

Усі цеглинки зібрано: промпти з Треку II, API, інструменти, пам'ять і стандартний роз'єм із Треку III. Час скласти з них системи, які працюють самі. Цей модуль розставить терміни — workflow проти агента, — дасть п'ять робочих патернів оркестрації і нарешті виростить «ембріон агента» з Модуля 6 у повноцінний цикл.

9.1Workflow чи агент: важлива різниця

Слово «агент» сьогодні клеять на все підряд, тож розставимо терміни. Різниця не академічна, а суто практична — і вона в одному питанні: хто визначає маршрут?

  • Workflow — кроки з викликами моделі з'єднані заздалегідь написаним кодом. Маршрут відомий до старту: спершу класифікація, потім екстракція, потім звіт. Ти — диригент, модель — оркестранти.
  • Агент — модель сама вирішує, які кроки і в якому порядку робити: викликає інструменти в циклі, дивиться на результати й коригує план, поки не досягне мети. Маршрут народжується в процесі.

    direction LR
    A["Крок A"] --> B["Крок B"]

  subgraph AG["Агент: маршрут обирає модель"]

Workflow — передбачуваний і дешевий; агент — гнучкий, але дорожчий і менш керований

Звідси робоче правило, яке тримає весь модуль: шукай найпростіше рішення, що працює. Дуже часто це один добре написаний промпт із Модулів 3–4. Не вистачило — ланцюжок промптів. Далі — workflow із розгалуженнями. І лише коли маршрут принципово неможливо прописати наперед — агент. Кожна сходинка вгору додає гнучкості, але забирає передбачуваність, швидкість і гроші.

9.2Базові патерни: chaining, routing, паралелізація

1 · Prompt chaining — ланцюжок. Вихід одного кроку стає входом наступного. Тижневі відгуки клієнтів: перший промпт витягає проблеми, другий групує їх за темами, третій пише звіт для власниці. Кожен крок простий і налагоджується окремо, а між кроками код може ставити «шлюзи» — перевірки, що результат придатний для наступного етапу. Пам'ятаєш антипатерн «промпт-вінегрет» із Модуля 4? Ланцюжок — його ліки.

2 · Routing — маршрутизація. Перший виклик — легкий класифікатор, який спрямовує запит у спеціалізовану гілку зі своїм промптом. Наш класифікатор звернень із Модуля 4 нарешті отримує продовження: 

flowchart LR
  IN["Звернення клієнта"] --> R["Класифікатор"]
  R -->|"нове замовлення"| A["Промпт: оформлення заявки"]
  R -->|"зміна замовлення"| B["Промпт: коригування"]
  R -->|"скарга"| C["Промпт: відповідь + ескалація людині"]
  class R hl

Кожна гілка має власний вузький промпт замість одного «промпта на всі випадки»

Класифікатор тут найкраще робити дешевою моделлю з few-shot прикладами (Модуль 4) і структурованим виводом через форсований інструмент (Модуль 6) — тоді гілка обирається надійно, а коштує копійки.

3 · Паралелізація. Незалежні підзадачі — одночасно. Два смаки: секціонування — різні аспекти паралельно (один виклик перевіряє факти листа, другий тон, третій структуру — потім результати зливаються); і голосування — та сама задача кілька разів, а код бере консенсус: корисно там, де потрібна надійність одного критичного рішення.

9.3Складніші патерни: оркестратор і оцінювач

4 · Orchestrator–workers. Зовні схоже на паралелізацію, але з принциповою різницею: підзадачі визначає не код, а модель-оркестратор. Запит «підготуй комерційну пропозицію для весілля на 80 гостей» оркестратор сам розбиває: воркеру-кухарю — меню, воркеру-логісту — доставка й персонал, воркеру-фінансисту — кошторис; потім синтезує результати в один документ. Бери цей патерн, коли структура розбиття залежить від конкретного запиту.

5 · Evaluator–optimizer. Двійка «генератор + оцінювач» у циклі: генератор створює чернетку, оцінювач перевіряє її за явними критеріями (тон, факти, обсяг) і повертає зауваження, генератор виправляє — і так до «прийнято» або ліміту ітерацій. Упізнаєш? Це автоматизоване розпізнавання з Модуля 2: цикл «оцінка → конкретний фідбек → ітерація», тільки тепер обидві ролі грає модель.

Патерн Коли брати
Prompt chaining Задача природно ділиться на відомі послідовні кроки
Routing Різні типи запитів потребують різної обробки
Паралелізація Підзадачі незалежні, або потрібен консенсус для надійності
Orchestrator–workers Розбиття на підзадачі залежить від самого запиту
Evaluator–optimizer Є чіткі критерії якості й цінність ітеративного покращення
Цінник складності

Кожен патерн — це додаткові виклики моделі: час, гроші, точки відмови. Патерни можна комбінувати (routing, а в гілках — ланцюжки), але правило з Модуля 7 повертається: складність має окупатися. Якщо один промпт дає 95% якості — він і є правильною архітектурою.

9.4Агентний цикл: думка → дія → спостереження

А тепер задачі, де маршрут наперед невідомий: налагодити код, дослідити питання, зібрати дані з кількох систем із несподіванками дорогою. Тут працює агентний цикл: модель міркує (покрокове мислення з Модуля 4), діє (викликає інструмент із Модуля 6), спостерігає результат — і повторює, поки мету не досягнуто. 

flowchart TD
  T["Задача"] --> TH["Думка: що робити далі?"]
  TH --> D{"Потрібен інструмент?"}
  D -->|"так"| ACT["Дія: tool_use"]
  ACT --> OBS["Спостереження: tool_result"]
  OBS --> TH
  D -->|"ні"| FIN["Фінальна відповідь"]
  class D hl
  class TH hl

Той самий while-цикл із Модуля 6 — тепер із метою, стоп-умовою і страховкою

«Ембріон агента» з Модуля 6 виростає трьома доповненнями: системний промпт із роллю і правилом завершення, ліміт кроків і чесна обробка помилок.

Python · універсальний агентний цикл
import json
from anthropic import Anthropic

client = Anthropic()
MODEL = "claude-sonnet-5"

SYSTEM = (
    "Ти — операційний агент кейтерингової компанії. "
    "Розв'язуй задачу крок за кроком: міркуй, викликай потрібні "
    "інструменти, аналізуй результати. Коли даних достатньо — "
    "дай фінальну відповідь без виклику інструментів."
)

def run_agent(task, tools, tool_impls, max_steps=8):
    messages = [{"role": "user", "content": task}]

    for step in range(max_steps):
        response = client.messages.create(
            model=MODEL, max_tokens=1024,
            system=SYSTEM, tools=tools, messages=messages,
        )

        # немає запитів на інструменти — агент вважає мету досягнутою
        if response.stop_reason != "tool_use":
            return response.content[0].text

        messages.append({"role": "assistant", "content": response.content})

        results = []
        for block in response.content:
            if block.type == "tool_use":
                fn = tool_impls[block.name]
                try:
                    output = json.dumps(fn(**block.input), ensure_ascii=False)
                    results.append({"type": "tool_result",
                                    "tool_use_id": block.id,
                                    "content": output})
                except Exception as err:
                    # чесна помилка — агент адаптується (Модуль 6)
                    results.append({"type": "tool_result",
                                    "tool_use_id": block.id,
                                    "content": str(err),
                                    "is_error": True})

        messages.append({"role": "user", "content": results})

    return "Досягнуто ліміт кроків — задача потребує людини."

Чотири рішення, які роблять цикл придатним до життя:

  • Стоп-умова: відповідь без tool_use — сигнал, що агент завершив; правило прописане прямо в системному промпті;
  • max_steps: страховка від нескінченного циклу і неконтрольованого рахунку — з чесним фолбеком на людину;
  • помилки без прикрас: is_error з Модуля 6 дає агенту шанс змінити план замість тихого провалу;
  • контекст росте з кожним кроком — економіка з Модуля 5: тримай результати інструментів компактними, а довгі — підсумовуй.

І принцип, що важливіший за код: прозорість. Логуй думки і кроки агента — без цього налагодження перетворюється на ворожіння, а довіра користувача — на лотерею.

9.5Claude Code зсередини — і коли агент не потрібен

Найкращий спосіб відчути агентний цикл — подивитися на живий приклад. Claude Code — агент для роботи з кодом у терміналі. Його інструменти: читання й редагування файлів, пошук по репозиторію, запуск команд і тестів. Сесія «полагодь червоний тест» виглядає як підручниковий цикл: прочитати тест (дія) → побачити помилку (спостереження) → прочитати код → внести правку → запустити тести → знову червоні? ще ітерація → зелені — мету досягнуто.

Секрет збіжності

Кодинг — ідеальне середовище для агентів, бо воно саме каже, чи вийшло: тести, компілятор, лінтер дають перевірюваний зворотний звязок. Звідси урок для твоїх агентів: дай їм спосіб перевіряти себе — валідатор, тест, контрольний запит. Цикл із перевіркою сходиться; цикл «на відчуттях» блукає.

І чесний чекліст наостанок — коли агента будувати не варто:

  • маршрут відомий заздалегідь → workflow дешевший і стабільніший;
  • досить однієї відповіді → один добрий промпт, і крапка;
  • ціна помилки висока, а перевірити автоматично нічим → людина веде, модель асистує (матриця з Модуля 2);
  • бюджет викликів критичний → вартість агента непередбачувана за визначенням.

Драбина рішень модуля: промпт → ланцюжок → workflow з маршрутизацією → агент. Підіймайся лише тоді, коли нижня сходинка чесно не тягне. А як зрозуміти, що «тягне» чи «не тягне», не на око? Саме про це наступний модуль — evals: вимірювання якості ШІ-систем.

Підсумок модуля
  • Workflow — маршрут у коді; агент — маршрут обирає модель у циклі. Починай із простішого.
  • П'ять патернів: chaining, routing, паралелізація, orchestrator–workers, evaluator–optimizer.
  • Агентний цикл = думка → дія → спостереження; обов'язкові стоп-умова і ліміт кроків.
  • Помилки інструментів повертай чесно через is_error — агент адаптується.
  • Давай агенту перевірку себе: тести й валідатори роблять цикл збіжним — секрет Claude Code.
  • Драбина: промпт → ланцюжок → workflow → агент; кожна сходинка має окупатися.
