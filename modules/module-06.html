Трек III · Розробка з Claude

Tool Use: інструменти для Claude

Середній · 5 уроків · ≈ 60 хв читання

У Модулі 1 ми чесно визнали: модель уміє одне — генерувати текст. Вона не подивиться погоду, не зазирне у твою базу замовлень і не надішле лист. Tool Use — протокол, що закриває цю прірву: модель формулює структуровані запити, а виконує їх твій код. Наприкінці модуля ти знатимеш і головний трюк продакшн-систем — гарантований структурований вивід через форсований інструмент.

6.1Модель просить — код виконує

Працює це так. Ти описуєш моделі набір інструментів — по суті, функцій твого коду. Коли модель вирішує, що для відповіді потрібен інструмент, вона його не виконує (їй просто нічим!), а повертає структурований запит: «виклич get_orders_for_date з date=2026-06-20». Твій код виконує функцію, повертає результат у розмову — і модель продовжує відповідь уже з реальними даними.

Мантра модуля

Модель — мозок, твій код — руки. Жоден інструмент не виконується без твоєї участі: ти валідуєш аргументи, обмежуєш права, логуєш кожен виклик. Це не обмеження, а перевага — повний контроль на твоєму боці.

Аналогія з Модуля 2 отримує продовження. Талановитий новий колега не має доступів до систем — і не лізе в них сам. Він пише тобі: «перевір, будь ласка, замовлення на двадцяте». Ти перевіряєш і відповідаєш. Колега формулює запити — виконуєш ти. 

flowchart TD
  U["Запит користувача + опис інструментів"] --> M["Модель"]
  M --> T["stop_reason: tool_use — запит на виклик з аргументами"]
  T --> C["Твій код виконує функцію"]
  C --> R["tool_result повертається в розмову"]
  R --> M2["Модель: фінальна відповідь з реальними даними"]
  class T hl
  class C hl

Один цикл tool use; далі побачиш, що модель може просити кілька викликів поспіль

Що це відкриває:

  • свіжі дані попри межу знань із Модуля 1 — пошук, курси, погода, розклади;
  • приватні системи — твоя база, CRM, календар, склад;
  • дії у світі — створити запис, надіслати лист, поставити задачу (з твоїм підтвердженням, де доречно);
  • точні обчислення — калькулятор замість «математики токенами».

6.2Опис інструмента: JSON Schema

Інструмент описується трьома полями: name, description та input_schema — схемою аргументів у форматі JSON Schema.

Найнедооціненіше з них — description. Це теж промпт, лише адресований рішенню «коли і як викликати». Усе з Модуля 3 застосовне: чітко, прямо, з крайніми випадками. Добрий опис каже, що робить інструмент, що повертає і коли його використовувати — а коли ні.

JSON · опис інструмента
{
  "name": "get_orders_for_date",
  "description": "Повертає список замовлень кейтерингу на вказану дату: тип події, кількість гостей, статус. Використовуй, коли користувач питає про завантаженість дня або конкретні замовлення. Не використовуй для дат у минулому місяці — їх немає в активній базі.",
  "input_schema": {
    "type": "object",
    "properties": {
      "date": {
        "type": "string",
        "description": "Дата у форматі YYYY-MM-DD, наприклад 2026-06-20"
      },
      "status": {
        "type": "string",
        "enum": ["confirmed", "pending", "all"],
        "description": "Фільтр за статусом; якщо користувач не уточнив — all"
      }
    },
    "required": ["date"]
  }
}

Практичні правила схем:

  • enum для закритих переліків — модель не вигадає п'ятий статус, якого немає у твоїй базі;
  • формати — у description поля: дати, телефони, ідентифікатори; приклад значення працює найкраще;
  • одна функція — одна відповідальність: три маленькі інструменти кращі за один «комбайн» із сімома режимами;
  • назви дієслівні й конкретні: get_orders_for_date, а не data_helper.

6.3Повний цикл: tool_use → tool_result

Зберемо все в робочий код. Сценарій: асистент кейтерингу, який уміє діставати замовлення з «бази» (для прикладу — мок-функція).

Python · повний цикл tool use
import json
from anthropic import Anthropic

client = Anthropic()
MODEL = "claude-sonnet-5"

def get_orders_for_date(date, status="all"):
    # тут був би запит до твоєї бази; для прикладу — мок
    orders = [
        {"event": "фуршет", "guests": 30, "status": "confirmed"},
        {"event": "банкет", "guests": 45, "status": "pending"},
    ]
    if status != "all":
        orders = [o for o in orders if o["status"] == status]
    return orders

tools = [{
    "name": "get_orders_for_date",
    "description": "Повертає замовлення кейтерингу на дату: тип події, "
                   "кількість гостей, статус. Використовуй для питань про "
                   "завантаженість дня чи конкретні замовлення.",
    "input_schema": {
        "type": "object",
        "properties": {
            "date": {"type": "string",
                     "description": "Дата у форматі YYYY-MM-DD"},
            "status": {"type": "string",
                       "enum": ["confirmed", "pending", "all"],
                       "description": "Фільтр; за замовчуванням all"},
        },
        "required": ["date"],
    },
}]

messages = [{"role": "user",
             "content": "Що в нас підтверджено на 2026-06-20?"}]

response = client.messages.create(
    model=MODEL, max_tokens=1024, tools=tools, messages=messages,
)

while response.stop_reason == "tool_use":
    # 1) відповідь моделі (з блоками tool_use) — в історію
    messages.append({"role": "assistant", "content": response.content})

    # 2) виконуємо КОЖЕН запитаний інструмент
    results = []
    for block in response.content:
        if block.type == "tool_use":
            if block.name == "get_orders_for_date":
                output = get_orders_for_date(**block.input)
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": json.dumps(output, ensure_ascii=False),
            })

    # 3) усі результати — одним повідомленням користувача
    messages.append({"role": "user", "content": results})

    # 4) даємо моделі продовжити з реальними даними
    response = client.messages.create(
        model=MODEL, max_tokens=1024, tools=tools, messages=messages,
    )

print(response.content[0].text)

Розбір ключових моментів:

  • stop_reason == "tool_use" — модель зупинилась і чекає результатів, фінальної відповіді ще немає;
  • content — масив блоків: ось чому в Модулі 5 текст лежав у content[0].text — поруч із текстом тепер можуть жити блоки tool_use;
  • tool_result їде в ролі user — і обов'язково з tool_use_id того запиту, на який відповідає;
  • цикл while не випадковий: отримавши результат, модель може попросити ще один виклик — і ще. Це вже ембріон агента, до якого ми дійдемо в Модулі 9.
Помилки інструментів

Якщо функція впала — не ховай це. Поверни tool_result із полем "is_error": true і людським описом проблеми: модель побачить помилку і адаптується — перепитає параметри, спробує інакше або чесно скаже користувачу, що дані недоступні.

6.4Кілька інструментів і паралельні виклики

Справжня сила з'являється з меню: дай моделі кілька інструментів — і вона сама обере потрібний для кожного кроку. Обирає вона за описами, тож якість description із уроку 6.2 вирішує все: розпливчасті описи — хаотичні виклики.

Паралельні виклики. На запит «скільки гостей сумарно на п'ятницю і суботу?» модель може повернути два блоки tool_use в одній відповіді. Правило просте: виконай усі й поверни всі tool_result одним повідомленням користувача. Наш цикл з уроку 6.3 це вже вміє — саме тому там for по блоках, а не обробка одного.

tool_choice — ручка свободи вибору:

  • {"type": "auto"} — за замовчуванням: модель сама вирішує, чи потрібен інструмент;
  • {"type": "any"} — мусить викликати якийсь із наданих інструментів;
  • {"type": "tool", "name": "..."} — мусить викликати саме цей. Запам'ятай цей варіант — він головний герой наступного уроку.

І зворотний бік: не давай інструменти «про всяк випадок». Якщо відповідь і так у знаннях моделі, зайвий виклик — це час, гроші й точка відмови. Опис може прямо казати: «використовуй лише якщо користувач питає про конкретні замовлення з бази».

6.5Структурований вивід через інструменти

У Модулях 3 і 5 ми вибивали чистий JSON інструкціями та префілом. Працює, але без гарантій структури: модель може перейменувати ключ або забути поле. Ось трюк продакшн-рівня: опиши інструмент, чия input_schema — це і є твоя бажана структура виводу, і форсуй його через tool_choice. Модель «викличе» інструмент — а block.input виявиться готовим об'єктом за схемою. Виконувати нічого не треба: сама «функція» — фікція.

Python · структурований вивід
extract_tool = {
    "name": "save_order_request",
    "description": "Зберігає структуровану заявку на кейтеринг, "
                   "витягнуту з листа клієнта.",
    "input_schema": {
        "type": "object",
        "properties": {
            "event_type": {"type": "string",
                           "enum": ["фуршет", "банкет", "кава-брейк", "інше"]},
            "guests": {"type": "integer",
                       "description": "Кількість гостей"},
            "date": {"type": "string",
                     "description": "YYYY-MM-DD або порожній рядок, якщо не вказано"},
            "contact_phone": {"type": "string"},
        },
        "required": ["event_type", "guests"],
    },
}

response = client.messages.create(
    model=MODEL,
    max_tokens=500,
    tools=[extract_tool],
    tool_choice={"type": "tool", "name": "save_order_request"},
    messages=[{"role": "user",
               "content": "Витягни заявку з листа:\n\n" + email_text}],
)

order = response.content[0].input   # готовий dict за схемою
print(order["event_type"], order["guests"])

  M --> I["block.input — об'єкт строго за схемою"]
  I --> DB["Твоя база чи CRM"]

«Виклик» нікуди не йде — нам потрібні лише його аргументи

Чому це краще за «попроси JSON»: схема з типами та enum тримає формат, преамбула неможлива в принципі, а парсити текст не треба взагалі. Чесне застереження: структура гарантується значно краще, ніж зміст — значення полів усе одно валідуй (модель може помилитися в даті чи числі; розпізнавання з Модуля 2 безсмертне).

Інструменти — це руки моделі. У Модулі 7 розберемося з пам'яттю — RAG і робота зі знаннями, що не влазять у контекст. А в Модулі 8 побачиш MCP — відкритий стандарт, який робить інструменти переносними між застосунками.

Підсумок модуля
  • Модель нічого не виконує: tool use — це структуровані запити, а руки — твій код.
  • Інструмент = name + description + JSON Schema; description — це промпт, і він вирішує.
  • Цикл: tool_use → виконання → tool_result з tool_use_id → відповідь; помилки повертай з is_error.
  • Кілька tool_use в одній відповіді — норма: виконай усі, поверни одним повідомленням.
  • tool_choice керує свободою: auto, any або конкретний інструмент.
  • Форсований інструмент = гарантована структура виводу: block.input і є твій об'єкт.
