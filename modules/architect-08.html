Claude API у коді

Практика · 6 уроків · ≈ 75 хв

Фундамент позаду — час на головне. Зараз твоя власна програма вперше по-справжньому заговорить із Claude. Ми, як завжди, керуватимемо Claude Code (він напише файли), але тепер ти вже вмієш читати код, тож розумітимеш кожен рядок. Підемо повільно, з аналогіями й розбором. Наприкінці в тебе буде робочий скрипт, що спілкується з моделлю.

Спираємось на попереднє. Ключ ми вже отримали й поклали в .env (Модуль 7), а код читати навчилися (Модуль 6). Тут усе складеться разом. Бібліотеки, які знадобляться: anthropic (офіційний SDK) і python-dotenv. Можеш поставити їх сам або попросити Claude Code: pip install anthropic python-dotenv (на macOS/Linux інколи pip3).

8.1Перший дзвінок до моделі

Нагадування для тих, хто з нуля: модель не шукає готових відповідей — вона передбачає текст маленькими шматочками-токенами (приблизно частина слова). Це важливо, бо саме в токенах рахується і довжина відповіді, і гроші. Тепер — до справи.

Аналогія. Виклик API — як заповнити бланк замовлення й віддати у віконце: ти вказуєш, яку модель береш, що питаєш і які умови, а назад отримуєш результат. Попроси Claude Code: «створи файл chat.py, що читає мій ключ із .env, надсилає Claude одне повідомлення й друкує відповідь». Він створить приблизно таке: 

import os
from anthropic import Anthropic
from dotenv import load_dotenv

load_dotenv()                                  # читаємо .env з ключем (Модуль 7)
client = Anthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))

response = client.messages.create(
    model="claude-sonnet-5",                 # приклад; актуальні моделі — у docs.claude.com
    max_tokens=300,                            # стеля довжини відповіді (у токенах)
    messages=[
        {"role": "user", "content": "Поясни простими словами, що таке API."}
    ],
)

print(response.content[0].text)                # сам текст відповіді
print(response.usage.input_tokens)             # скільки токенів пішло на запит
print(response.usage.output_tokens)            # скільки на відповідь
print(response.stop_reason)                    # чому генерація завершилась

Запусти його в терміналі:

python chat.py        # або python3 chat.py на macOS/Linux

Що ти маєш побачити. Відповідь моделі текстом, а під нею — кілька чисел (токени) і причину завершення (наприклад, end_turn). Якщо так — вітаю, твоя програма щойно поговорила з Claude!

Розбір рядок за рядком. load_dotenv() + os.getenv(...) дістають ключ із .env (Модуль 7). client = Anthropic(...) — це наш «телефон» до API. client.messages.create(...) — сам дзвінок: у дужках поля «бланку». messages=[{...}] — список (Модуль 6) з одного словника: role (хто говорить) і content (текст). А response — це не рядок, а об'єкт із кількома «відділеннями»: текст у content[0].text, лічильник токенів у usage, причина завершення в stop_reason.

Запам'ятай «анатомію» будь-якого виклику — далі вона лише обростатиме деталями:

flowchart LR
  subgraph REQ["Запит (бланк)"]
    M["model — яка модель"]
    S["system — роль і правила"]
    MSG["messages — історія діалогу"]
    P["параметри — max_tokens, temperature"]
  end
  REQ --> API["Claude API"]
  API --> R["Відповідь:
content (текст) + usage (токени)"]
  style API fill:#2A211C,stroke:#D97757,color:#F0EEE6

На вході — складові «бланку», на виході — структурована відповідь

8.2Ролі та пам'ять: як вести діалог

Поле messages — список реплік, у кожної є роль: user (людина) або assistant (модель). А тепер найнесподіваніше для новачків правило: модель не має пам'яті між викликами.

Аналогія. Уяви клерка з повною амнезією: щоразу, коли підходиш, він тебе не пам'ятає. Щоб він зрозумів контекст, ти даєш йому прочитати всю стенограму попередньої розмови. Модель — такий клерк. «Пам'ять» діалогу існує лише тому, що ти щоразу надсилаєш усю історію наново. 

sequenceDiagram
  participant T as Твій код
  participant M as Модель
  T->>M: messages = [хід 1]
  M-->>T: відповідь 1
  Note over T: додаєш відповідь 1 в історію
  T->>M: messages = [хід 1, відповідь 1, хід 2]
  M-->>T: відповідь 2
  Note over T,M: модель отримує всю історію щоразу

«Пам'ять» — це історія, яку додаєш ти; сама модель нічого не зберігає

messages = [
    {"role": "user", "content": "Запам'ятай число 7."}
]
r1 = client.messages.create(model=MODEL, max_tokens=200, messages=messages)

# Додаємо відповідь моделі в історію — інакше наступний хід її «не побачить»
messages.append({"role": "assistant", "content": r1.content[0].text})
messages.append({"role": "user", "content": "Яке число я просив запам'ятати?"})

r2 = client.messages.create(model=MODEL, max_tokens=200, messages=messages)
print(r2.content[0].text)   # "7" — бо ми передали всю історію

Наслідок для гаманця. Що довша розмова, то довшу історію ти щоразу надсилаєш — і за всі ці токени платиш знову. Тому в реальних застосунках довгі діалоги підрізають або стискають у короткий підсумок. Це не дрібниця — повернемось до вартості в уроці 8.6.

8.3Системний промпт: задаємо роль і правила

Окреме поле system — інструкція «хто ти і як поводься», що діє на весь діалог.

Аналогія. Якщо повідомлення user — це конкретні завдання, то системний промпт — посадова інструкція працівника: роль, тон, формат, межі. Пишеться раз і діє на всі наступні запити. 

response = client.messages.create(
    model=MODEL,
    max_tokens=400,
    system=(
        "Ти — лаконічний асистент із фінансів для початківців. "
        "Пояснюй простою мовою, без жаргону. Якщо питання стосується "
        "інвестицій — додавай, що це не індивідуальна порада."
    ),
    messages=[{"role": "user", "content": "Що таке депозит?"}],
)

Стоп, що це за лапки на кожному рядку? Текст розбито на три рядки, кожен у своїх лапках, без жодних плюсів. Це особливість Python: сусідні рядкові літерали автоматично склеюються в один. Тобто "abc" "def" для Python — це "abcdef". Дужки навколо (system=( ... )) дозволяють розкласти текст на кілька рядків для читабельності. Зверни увагу на пробіл у кінці кожного рядка — без нього слова злиплися б. Це ідіоматичний спосіб писати довгий текст.

Сила в тому, що той самий user-запит дасть різні відповіді залежно від інструкції: 

system="Пояснюй як дитині 10 років, одним абзацом."   # проста відповідь
system="Ти фінансовий аналітик. Відповідай точно, з нюансами."  # фахова відповідь

Це твій головний важіль керування продуктом: тут живе «характер» асистента.

8.4Параметри: керуємо відповіддю

Аналогія. Уяви на «бланку» кілька регуляторів-ручок. Покрутиш — зміниться характер відповіді:

  • max_tokens — стеля довжини відповіді (у токенах). Як ліміт на поїздку: довша відповідь = більше токенів = дорожче. Обірвалась на півслові — підніми.
  • temperature — «творчість» від 0 до 1. Нижче — точніше й передбачуваніше; вище — різноманітніше й креативніше.
  • stop_sequences — «стоп-слова»: щойно модель їх згенерує, генерація обірветься.
response = client.messages.create(
    model=MODEL,
    max_tokens=500,
    temperature=0.2,                 # факти, код, видобування — низька «творчість»
    messages=[{"role": "user", "content": "Випиши 3 ключові тези тексту..."}],
)

Інтуїція для temperature — обирай під тип задачі:

0.0 ──────── 0.3 ──────── 0.7 ──────── 1.0
точність    аналіз      письмо      брейнсторм
(код,       (витяг      (тексти,    (ідеї,
факти)      даних)      пояснення)  варіанти)

Правило великого пальця. Є «правильна» відповідь (код, видобування) → низька temperature (0–0.3). Потрібне розмаїття (ідеї, креатив) → вища. Почни з 0.2–0.3 і підкручуй за результатом.

8.5Стрімінг: відповідь, що з'являється на очах

Аналогія. Без стрімінгу — це офіціант, що чекає, поки приготуються всі страви, і виносить разом: ти сидиш перед порожнім столом. Зі стрімінгом кожну страву несуть, щойно готова. Технічно: текст надходить шматочками, щойно генерується, і користувач бачить, як він «друкується». Так працюють усі чат-інтерфейси. 

sequenceDiagram
  participant U as Користувач
  participant A as Твій застосунок
  participant M as Модель
  U->>A: запит
  A->>M: messages (stream)
  M-->>A: шматок "Жив"
  M-->>A: шматок "-був "
  M-->>A: шматок "кіт..."
  A-->>U: показує текст одразу, по шматках

Стрімінг прибирає «паузу очікування» — критично для гарного UX

with client.messages.stream(
    model=MODEL,
    max_tokens=500,
    messages=[{"role": "user", "content": "Напиши коротку казку про кота."}],
) as stream:
    for text in stream.text_stream:           # перебираємо шматочки по черзі
        print(text, end="", flush=True)        # друкуємо одразу, без переносу рядка

Розбір незнайомого. with ... as stream: — «менеджер контексту»: він сам коректно відкриє й закриє потік (не лишиться «висіти»). for text in stream.text_stream: — звичайний цикл (Модуль 6) по шматочках, що надходять. end="" прибирає автоматичний перенос рядка після кожного print (щоб шматки склеювались), а flush=True показує їх негайно.

8.6Токени, вартість і трохи про надійність

Те, що відрізняє інженера від «погрався з API»: контроль вартості. Грубе правило: ≈ 1 токен — це ~4 символи (українською зазвичай більше токенів, ніж англійською). Скільки витрачено — у відповіді, у usage (бачили в уроці 8.1): 

print(response.usage.input_tokens)    # вхід (твій запит)
print(response.usage.output_tokens)   # вихід (відповідь)

Вартість. Аналогія — таксі-лічильник: платиш за «пробіг» у токенах. Вхід і вихід тарифікуються окремо, і вихід зазвичай дорожчий. Ціни вказують «за мільйон токенів»: 

вартість = (вхідні_токени  / 1_000_000) * ціна_входу
         + (вихідні_токени / 1_000_000) * ціна_виходу

# Приклад (ЦІНИ УМОВНІ — звіряй актуальні на docs.claude.com):
# вхід 1000 ток. * $3/млн  = $0.003
# вихід 500 ток. * $15/млн = $0.0075
# разом ≈ $0.0105 за один запит

Інженерні висновки. Дешевші/швидші моделі — для простих задач, дорожчі — лише там, де треба «розум». Довгу історію підрізай (урок 8.2). max_tokens тримай розумним. Пам'ятаєш ліміт витрат у консолі (Модуль 2)? Він страхує, поки вчишся.

Коротко про збої. Інколи API відповідає помилкою: 429 («забагато запитів») чи 5xx (тимчасовий збій). Надійний код не падає, а чекає й повторює спробу з паузою, що зростає (так званий backoff). Хороша новина: офіційний SDK уже робить це автоматично — тобі лише корисно знати, що так буває.

Підсумок модуля. Твоя програма вміє звертатися до моделі, вести діалог із історією, задавати роль через system, керувати відповіддю параметрами, стрімити текст і рахувати токени з вартістю. Наступний модуль підніме якість самих запитів: як отримувати від моделі надійний, машиночитаний результат (structured outputs) — і збудуємо реальний видобувач даних.
