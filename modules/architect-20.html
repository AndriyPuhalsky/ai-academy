Екосистема моделей

Підсумок · 6 уроків · ≈ 65 хв

Весь курс ми будували з Claude — і це чудовий вибір. Але існує цілий світ інших моделей, і інженеру варто розуміти карту: коли брати топову закриту модель, коли — відкриту, а коли — локальну. Цей модуль дає орієнтацію в екосистемі й, головне, рамку вибору моделі під задачу й бюджет.

Про актуальність. Конкретні назви моделей, їхні версії, ціни й рейтинги змінюються дуже швидко. Тому тут — стабільні принципи й категорії, а свіжі порівняння завжди звіряй у документації провайдерів і на актуальних бенчмарках. Принципи вибору живуть довго; конкретні цифри — ні.

20.1Карта екосистеми моделей

Усе різноманіття моделей зручно поділити за двома осями. Перша — хто володіє моделлю:

  • Закриті (пропрієтарні). Доступ лише через API провайдера; «вагів» моделі ти не маєш. Приклади родин: Claude (Anthropic), GPT (OpenAI), Gemini (Google).
  • Відкриті (open-weight). Ваги моделі опубліковані — її можна завантажити й запускати самому. Приклади: Llama (Meta), Mistral, Qwen та інші.

Друга вісь — де модель працює: у хмарі провайдера (через API) чи на твоєму залізі (локально/самостійний хостинг).

Що тобі вже знайомо. Увесь курс ти користувався закритою моделлю через API (Claude) — найпростіший і найшвидший шлях до якісного результату. Тепер додамо до картини відкриті й локальні варіанти, щоб ти міг свідомо обирати під ситуацію.

20.2Закриті моделі (через API)

Це шлях, яким ми йшли: реєструєшся в провайдера, береш ключ, звертаєшся через API. Сюди належать найсильніші на сьогодні моделі.

Переваги:

  • зазвичай найвища якість і найкраще «міркування»;
  • максимально просто почати — лише API-виклик, жодного заліза й налаштувань;
  • провайдер сам дбає про масштабування, оновлення й надійність.

Компроміси:

  • платиш за кожен токен (Модуль 8) — на великих обсягах це відчутно;
  • залежність від провайдера (його ціни, ліміти, доступність);
  • дані йдуть на сервер провайдера (важливо для чутливих сценаріїв — Модуль 19).

Добра новина для інженера. API більшості провайдерів схожі за ідеєю: повідомлення з ролями, системний промпт, токени (усе, що ти вже знаєш із Модуля 8). Тому перейти з одного провайдера на іншого — не переписати все з нуля, а адаптувати виклики. Деталі відрізняються, але концепції ті самі.

20.3Відкриті моделі (open-weight)

У відкритих моделей (Llama, Mistral, Qwen тощо) ваги опубліковані — тобто ти можеш завантажити саму модель і запускати її де завгодно: на власному сервері з GPU, у хмарі або навіть (менші версії) на потужному ноутбуку.

Переваги:

  • Контроль і приватність: дані не йдуть до зовнішнього провайдера — модель працює на твоїй інфраструктурі;
  • Вартість на масштабі: немає оплати «за токен» провайдеру; платиш лише за своє залізо/хостинг (на великих обсягах може бути дешевше);
  • Гнучкість: можна донавчати модель під свою вузьку задачу (fine-tuning).

Компроміси:

  • ти сам відповідаєш за інфраструктуру (запуск, масштабування, оновлення) — це робота;
  • зазвичай потрібні потужні відеокарти (GPU), особливо для більших моделей;
  • якість топових відкритих моделей часто трохи нижча за найкращі закриті (хоч розрив швидко скорочується).

Коли це доречно. Відкриті моделі сяють, коли критична приватність даних, коли обсяги величезні (і оплата за токен стає завеликою), або коли потрібне глибоке налаштування під специфічну задачу. Для швидкого старту й найвищої якості «з коробки» закрита модель через API зазвичай простіша.

20.4Локальні моделі

Окремо варто згадати запуск моделі локально — прямо на твоєму комп'ютері, без інтернету й без жодного зовнішнього сервісу. Є зручні інструменти, що дозволяють завантажити відкриту модель і спілкуватися з нею локально (наприклад, Ollama — один із популярних).

Коли локальна модель корисна:

  • Максимальна приватність: дані взагалі не залишають твою машину;
  • Офлайн: працює без інтернету;
  • Експерименти й навчання: можна вільно пробувати без оплати за токени;
  • Прототипи: швидко перевірити ідею локально.

Обмеження:

  • залежить від твого заліза — великі моделі потребують потужного комп'ютера (особливо GPU);
  • якість менших локальних моделей зазвичай нижча за хмарні топові;
  • для серйозного навантаження на багатьох користувачів локальний запуск на одній машині не годиться.

Практичний орієнтир. Локальні моделі — чудові для приватних, офлайн чи навчальних сценаріїв і прототипів. Для публічного продукту з багатьма користувачами й високою якістю частіше беруть API закритої моделі або хостинг відкритої в хмарі на GPU. Точні вимоги до заліза та інструменти швидко змінюються — дивись актуальні гайди.

20.5Як обрати модель під задачу

Немає «найкращої моделі» взагалі — є найкраща під конкретну задачу й обмеження. Оцінюй за кількома осями:

  • Якість/складність задачі: просте (класифікація, короткі відповіді) чи складне (глибоке міркування, довгий код)?
  • Вартість: який бюджет і який обсяг запитів?
  • Швидкість: потрібна миттєва відповідь чи можна зачекати?
  • Приватність: чи можна надсилати дані зовнішньому провайдеру?
  • Контроль: чи потрібне донавчання під свою специфіку?
Грубий орієнтир (не догма):

  Проста масова задача (класифікація, теги)
     -> дешевша/швидша модель (закрита або невелика відкрита)

  Складне міркування, якісний текст/код
     -> топова закрита модель через API

  Чутливі дані / сувора приватність
     -> відкрита або локальна модель на своїй інфраструктурі

  Величезні обсяги, де оплата за токен задорога
     -> відкрита модель, яку хостиш сам

  Прототип / навчання / офлайн
     -> локальна модель

Практична порада. Часто розумно комбінувати: дешева модель для простих кроків, дорога — лише там, де треба «розум» (пам'ятаєш оптимізацію вартості, Модуль 18?). І завжди перевіряй вибір евалами (Модуль 19): прожени свій тест-набір на кандидатах і порівняй якість і вартість на своїй задачі, а не лише за чужими рейтингами.

20.6Гнучкість: не прив'язуйся до однієї моделі

Екосистема змінюється щомісяця: виходять нові моделі, дешевшають ціни, зсуваються лідери. Тому мудро будувати код так, щоб модель можна було замінити без переписування всього продукту. Пам'ятаєш принцип із Модуля 15 — відокремлювати логіку від деталей? Застосуй його й тут: 

# Увесь продукт кличе ОДНУ функцію — а яка модель/провайдер усередині, сховано тут:
def ask_model(prompt):
    resp = client.messages.create(
        model=MODEL, max_tokens=500,
        messages=[{"role": "user", "content": prompt}],
    )
    return resp.content[0].text

# Захотів змінити модель чи навіть провайдера?
# Міняєш лише цю функцію — решта коду (агенти, бекенд, тріаж) не чіпається.

Чому це важливо. Якщо виклики моделі розкидані по всьому коду, зміна провайдера — це біль. Якщо вони сховані за однією функцією-«перемикачем» — це кілька рядків. Така маленька дисципліна економить дні роботи в майбутньому й дає свободу обирати найкраще під момент.

Підсумок модуля. Ти бачиш карту екосистеми: закриті моделі через API (просто й якісно), відкриті open-weight (контроль, приватність, вартість на масштабі), локальні (приватність, офлайн, навчання). Ти вмієш обирати під задачу за осями якість/вартість/швидкість/ приватність/контроль і будувати код гнучко, щоб не прив'язуватись до однієї моделі. Попереду кульмінація курсу — Модуль 21: капстоун, де ти збудуєш і розгорнеш реальну AI-систему від початку до кінця.
