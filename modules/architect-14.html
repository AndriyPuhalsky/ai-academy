Фаза C · Агенти й команди агентів

Команда агентів (оркестрація)

Агенти · 7 уроків · ≈ 95 хв

Один агент чудово справляється з однією задачею. Але великі, різнопланові завдання краще розкласти між кількома спеціалізованими агентами, що працюють разом, — як у справжній команді. У цьому модулі ми не лише розберемо патерни оркестрації, а й зберемо два повні робочі приклади: команду-конвеєр і оркестратор-планувальник.

14.1Навіщо кілька агентів

Коли задача велика й різнопланова, один агент із купою інструментів починає «плутатися»: забагато можливостей, забагато рішень одразу, легше збитися. Рішення те саме, що й у людей — розподіл ролей.

Аналогія. Одна людина може зробити статтю сама, але повільно й посередньо. Команда з ролями — дослідник, копірайтер, редактор — зробить швидше і якісніше, бо кожен фокусується на своєму. Кілька агентів — це така команда: кожен має вузьку роль, чіткий системний промпт і лише потрібні інструменти.

Чому спеціалізація допомагає. Вузький системний промпт («ти лише складаєш тези») дає чіткішу, якіснішу відповідь, ніж один великий промпт «зроби все одразу». Менше задач на одну модель — менше плутанини й помилок. Це той самий принцип фокусу, що працює і для людей.

Коли це доречно. Мультиагентність варта складнощів, коли задача природно ділиться на ролі (зібрати → опрацювати → перевірити) або коли кроки можна робити паралельно. Для простих лінійних задач одного агента (Модуль 13) зазвичай достатньо — не ускладнюй передчасно.

14.2Три патерни оркестрації

Є три базові способи організувати команду агентів. Знати всі три — щоб обрати під задачу.

  • Конвеєр (послідовний). Агенти йдуть ланцюжком: вихід одного — вхід наступного (дослідник → автор → редактор). Просто й передбачувано.
  • Оркестратор + виконавці. Координатор (планувальник) розбиває мету на підзадачі, роздає виконавцям і збирає результати. Гнучко, коли план невідомий наперед.
  • Паралельний. Кілька агентів працюють одночасно над незалежними частинами, потім результати об'єднують. Швидше, коли частини не залежать одна від одної.

Як обрати. Кроки залежать один від одного → конвеєр. Незалежні → паралельно. Потрібне «розумне» динамічне розбиття на ходу → оркестратор-планувальник. Почни з найпростішого (конвеєр) і ускладнюй лише за потреби. Далі зберемо в коді конвеєр (урок 14.3) і оркестратор (урок 14.5).

14.3Будуємо команду-конвеєр (повний код)

Зберемо найзрозумілішу структуру — конвеєр із трьох спеціалістів: дослідник складає тези, автор пише за ними текст, редактор шліфує. Кожен «агент» — це виклик моделі зі своєю роллю. Ось весь файл team.py (копіюй і запускай): 

import os
from anthropic import Anthropic
from dotenv import load_dotenv

load_dotenv()
client = Anthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))
MODEL = "claude-sonnet-5"   # приклад; актуальні моделі — docs.claude.com

def call(system, user, max_tokens=700):
    """Допоміжна функція: один виклик моделі із заданою роллю."""
    resp = client.messages.create(
        model=MODEL, max_tokens=max_tokens,
        system=system, messages=[{"role": "user", "content": user}],
    )
    return resp.content[0].text

# --- Три спеціалісти, кожен зі своєю роллю ---
def researcher(topic):
    return call("Ти дослідник. Склади 3–5 ключових тез на тему. Лише список тез.",
                topic, max_tokens=400)

def writer(topic, points):
    return call("Ти копірайтер. Напиши короткий зрозумілий текст на основі тез.",
                f"Тема: {topic}\nТези:\n{points}")

def editor(draft):
    return call("Ти редактор. Виправ помилки й зроби текст чіткішим. "
                "Поверни лише готовий текст.", draft)

# --- Оркестратор-конвеєр: з'єднує спеціалістів по черзі ---
def content_team(topic):
    print("[1/3] дослідник збирає тези...")
    points = researcher(topic)
    print("[2/3] автор пише чернетку...")
    draft = writer(topic, points)
    print("[3/3] редактор шліфує текст...")
    final = editor(draft)
    return final

print(content_team("Користь ранкових прогулянок"))

Розбір. Допоміжна функція call() прибирає повтори: кожен спеціаліст — це просто виклик call() зі своїм системним промптом-роллю (Модуль 8). content_team() — оркестратор-конвеєр: він передає вихід researcher на вхід writer, а потім writer — у editor (через f"...", Модуль 6). Кожна модель робить одну річ — звідси якість.

14.4Як тече стан між агентами

«Стан» у конвеєрі — це просто дані, що передаються від одного агента до наступного. Запусти python team.py і простеж рух: 

topic ──> [дослідник] ──> points ──> [автор] ──> draft ──> [редактор] ──> final

Що ти маєш побачити у терміналі:

[1/3] дослідник збирає тези...
[2/3] автор пише чернетку...
[3/3] редактор шліфує текст...
(готовий відредагований текст про ранкові прогулянки)

Кожен рядок — це передача «естафети» наступному спеціалісту. Результат кращий, ніж від одного виклику «напиши статтю», бо текст пройшов три фокусовані етапи.

Важлива пересторога: поширення помилок. Якщо дослідник дасть слабкі тези, автор писатиме за слабкими тезами — помилка «котиться» далі ланцюгом. Тому в серйозних системах проміжні результати варто перевіряти (наприклад, додати крок-валідатор) перед передачею далі. Не передавай наступному агенту те, у чому не впевнений.

Зверни увагу: тут кожен виконавець — простий виклик. Але будь-який із них міг би бути повноцінним агентом із циклом та інструментами (Модуль 13) — принцип той самий, лише «розумніші» виконавці.

14.5Оркестратор-планувальник у коді

Конвеєр має фіксований порядок. А якщо ми не знаємо наперед, на скільки частин ділити задачу? Тоді нехай модель сама складе план, а виконавці зроблять кожну частину. Це патерн «оркестратор-планувальник». Додамо його у той самий файл (використовує call() згори): 

import json

def planner(goal):
    system = ("Ти планувальник. Розбий мету на 2–4 незалежні підзадачі. "
              "Поверни ЛИШЕ JSON-список рядків, "
              "напр. [\"підзадача 1\", \"підзадача 2\"].")
    raw = call(system, goal, max_tokens=400)
    return json.loads(raw)             # рядок JSON -> список Python

def worker(subtask):
    return call("Ти виконавець. Виконай підзадачу коротко і по суті.",
                subtask, max_tokens=500)

def orchestrate(goal):
    subtasks = planner(goal)                       # 1) планувальник ділить мету
    print("План:", subtasks)
    results = []
    for i, st in enumerate(subtasks, start=1):     # 2) виконавці роблять кожну частину
        print(f"[{i}/{len(subtasks)}] виконую: {st}")
        results.append(worker(st))
    combined = "\n\n".join(results)                 # 3) збираємо частини
    return call("Ти редактор. Об'єднай частини в один зв'язний текст.",
                combined, max_tokens=900)

print(orchestrate("Підготуй короткий гід для новачка про здоровий сон"))

Розбір. planner просить модель розбити мету й повернути JSON-список (Модуль 9), json.loads перетворює його на список Python. enumerate(subtasks, start=1) дає пари «номер, підзадача» (зручно для друку прогресу). Цикл for віддає кожну підзадачу worker, результати склеюються ("\n\n".join, Модуль 11), а фінальний виклик об'єднує їх у зв'язний текст. На відміну від конвеєра, тут кількість і зміст кроків визначає сама модель.

Надійність. planner повертає JSON — а отже, як у Модулі 9, варто обгорнути json.loads у try/except (і, за потреби, додати префіл [), щоб крива відповідь не зламала весь процес. Для навчання лишаємо просто, але в проді це обов'язково.

14.6Фреймворки для агентів

Ми писали цикл і команду «руками» — і це найкращий спосіб зрозуміти, як усе працює. Але коли систем стає багато й вони складнішають, на допомогу приходять фреймворки: готові бібліотеки, що беруть на себе рутину — керування станом, цикли, пам'ять, координацію кількох агентів, повтори при збоях.

Кілька популярних (назви корисно знати, деталі — у їхній документації):

  • LangGraph — побудова агентних робочих процесів як графів кроків.
  • LlamaIndex — сильний у роботі з даними й RAG, має й агентні можливості.
  • CrewAI — орієнтований саме на «команди» агентів із ролями.

Коли брати фреймворк. Не поспішай. Для перших проєктів власний простий код (як наш) зрозуміліший і його легше налагоджувати. Фреймворк виправданий, коли потрібні складна координація, надійне керування станом чи готові інтеграції — і коли ти вже розумієш, що відбувається «під капотом». Інакше фреймворк лише сховає механіку, яку важливо розуміти. Тепер, коли ти зібрав конвеєр і оркестратор руками, будь-який фреймворк буде тобі зрозумілим.

14.7Складнощі та як обрати структуру

Команда агентів потужна, але платиш за це. Що важливо тримати в голові:

  • Вартість і швидкість. Кілька агентів = більше викликів моделі = дорожче й повільніше (кожен — це токени, Модуль 8).
  • Поширення помилок. Помилка одного агента псує вхід наступних. Перевіряй проміжні результати.
  • Складність координації. Більше рухомих частин — більше місць для збоїв. Налагоджувати команду важче, ніж одного агента.
  • Спостережуваність. Логуй роботу кожного агента (наші print), щоб бачити, хто що зробив і де збій.
Як обрати структуру під задачу:
  Одна проста задача              -> один виклик або один агент (Модуль 12–13)
  Відомі залежні кроки            -> конвеєр (урок 14.3)
  План невідомий наперед          -> оркестратор-планувальник (урок 14.5)
  Незалежні частини, треба швидко -> паралельний

Головна порада. Тримай систему максимально простою, що вирішує задачу. Додавай агента лише тоді, коли він приносить чітку користь. «Більше агентів» ≠ «краще» — часто один добре налаштований агент перемагає заплутану команду.

Підсумок модуля. Ти знаєш три патерни оркестрації, зібрав у коді повний конвеєр і повний оркестратор-планувальник, розумієш, як тече стан і як обрати структуру, орієнтуєшся у фреймворках і свідомий складнощів.
