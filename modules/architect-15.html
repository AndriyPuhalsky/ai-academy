Агенти у бізнес-процесах

Агенти · 8 уроків · ≈ 95 хв

Ось де навички перетворюються на реальну цінність. Агент стає корисним бізнесу, коли під'єднаний до справжніх інструментів і даних — пошти, таблиць, CRM. У цьому модулі ми навчимося це робити, зберемо повну робочу автоматизацію — тріаж звернень клієнтів, — зробимо її надійною й розберемо, де обов'язково лишати людину в контурі.

15.1Від демо до реального бізнесу

Наш агент із Модуля 13 працював із вигаданими даними. У бізнесі цінність з'являється, коли агент торкається реальних процесів: читає справжні листи, пише в справжню таблицю, оновлює картку клієнта. Технічно це просто — інструмент-функція, яка замість «прикладу» звертається до реального сервісу.

Типові бізнес-автоматизації, які реально замовляють і впроваджують:

  • Тріаж звернень: сортувати вхідні листи за темою й терміновістю, готувати чернетки відповідей.
  • Обробка лідів: з форм і листів витягати дані, заносити в CRM, оцінювати пріоритет.
  • Звіти: регулярно збирати дані й складати зведення (як наш агент-аналітик).
  • Введення даних: переносити інформацію з документів у таблиці без ручної рутини.

Головна думка фази. Бізнес платить не за «розумного бота», а за зекономлений час і менше рутини. Твоя цінність як інженера — побачити нудний повторюваний процес і доручити його агенту, під'єднавши до інструментів, якими бізнес уже користується.

15.2Як агент під'єднується до реальних інструментів

Ти вже вмієш головне — tool use (Модуль 10). Інструмент бізнес-агента влаштований так само, лише всередині функції замість прикладу стоїть реальний виклик: до API пошти, таблиць, CRM чи бази даних. 

# Було (демо):
def get_new_messages():
    return ["приклад звернення 1", "приклад звернення 2"]

# Стане (реальність) — усередині звернення до справжнього сервісу:
def get_new_messages():
    # запит до API поштової скриньки / CRM і повернення нових повідомлень
    ...

Тобто архітектура агента не змінюється — змінюється лише «начинка» інструментів. Сьогодні майже кожен популярний сервіс (пошта, таблиці, месенджери, CRM) має API, до якого можна під'єднатися.

Корисно знати: MCP. Model Context Protocol (MCP) — відкритий стандарт, що дозволяє під'єднувати AI до зовнішніх інструментів і даних через готові «конектори», не пишучи кожну інтеграцію з нуля. Замість того щоб самому кодити доступ до кожного сервісу, ти береш готовий MCP-конектор. Це швидко стає індустріальним способом давати агентам «руки» до реальних систем — варто знати цей термін і дивитись, чи є готовий конектор під твою задачу.

Безпека насамперед. Реальні інструменти діють у реальному світі: надсилають листи, змінюють дані, витрачають гроші. Давай агенту лише потрібні права (Модуль 12), зберігай ключі в .env (Модуль 7) і особливо обережно стався до дій, які щось змінюють чи надсилають — про це в уроці 15.7.

15.3Проєктуємо автоматизацію тріажу

Спроєктуємо реальну задачу: автоматичний тріаж звернень клієнтів. Уяви бізнес, куди щодня падають десятки повідомлень. Наш процес: взяти нові звернення → для кожного визначити тему й скласти чернетку відповіді → записати в журнал → передати людині на перевірку перед відправкою.

тема + чернетка"]
  AG --> LOG["Запис у журнал"]
  LOG --> REV["Перевірка людиною"]
  REV --> OUT["Відповідь надіслано"]

Тріаж: агент готує, людина схвалює, відповідь іде клієнту

Які інструменти потрібні (думаємо інструментами, як у Модулі 13):

  • get_new_messages — отримати нові звернення (реально — з пошти/CRM).
  • класифікація + чернетка — це робить сама модель (Модуль 9), окремий інструмент не потрібен.
  • log_result — записати тему й чернетку в журнал для перевірки людиною.

Свідоме рішення. Помітив, що тут не потрібен повноцінний агентний цикл? Задача лінійна: для кожного звернення — ті самі кроки. Це проста й надійна автоматизація (Модуль 12: «не ускладнюй»). Агентний цикл додавай лише там, де кроки наперед невідомі.

15.4Будуємо тріаж: повний код

Ось увесь файл triage.py — копіюй і запускай. Він поєднує інструменти (з прикладними даними — реальні API підставиш потім), класифікацію з чернеткою (підхід Модуля 9) і головний процес: 

import os, json
from anthropic import Anthropic
from dotenv import load_dotenv

load_dotenv()
client = Anthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))
MODEL = "claude-sonnet-5"   # приклад; актуальні моделі — docs.claude.com

# === ІНСТРУМЕНТИ (зараз приклад; реальні API підставиш пізніше) ===
def get_new_messages():
    return [
        "Не можу оплатити, картка не проходить — допоможіть!",
        "Дякую, кур'єр приїхав вчасно, все чудово",
        "Де моя посилка? Замовлення №123 зробив тиждень тому",
    ]

def log_result(message, category, draft):
    with open("triage_log.txt", "a", encoding="utf-8") as f:
        f.write(f"[{category}]\n  клієнт: {message}\n  чернетка: {draft}\n\n")
    return "записано"

# === КЛАСИФІКАЦІЯ + ЧЕРНЕТКА (підхід Модуля 9) ===
SYSTEM = (
    "Ти асистент підтримки. Поверни ЛИШЕ JSON за схемою: "
    "{\"category\": \"оплата|доставка|товар|інше\", "
    "\"draft\": \"ввічлива чернетка відповіді клієнту українською\"}."
)

def triage_one(message):
    resp = client.messages.create(
        model=MODEL, max_tokens=500, temperature=0, system=SYSTEM,
        messages=[{"role": "user", "content": message},
                  {"role": "assistant", "content": "{"}],   # префіл (Модуль 9)
    )
    return json.loads("{" + resp.content[0].text)

# === ГОЛОВНИЙ ПРОЦЕС ===
def run_triage():
    messages = get_new_messages()
    for msg in messages:
        result = triage_one(msg)                       # тема + чернетка
        log_result(msg, result["category"], result["draft"])
        print(f"[{result['category']}] оброблено: {msg[:40]}...")
    print(f"Готово. Оброблено звернень: {len(messages)}. Дивись triage_log.txt")

run_triage()

Розбір. get_new_messages і log_result — інструменти (зараз прикладні). triage_one — це видобувач із Модуля 9: повертає словник {category, draft} з префілом. run_triage пробігає всі звернення циклом for (Модуль 6), обробляє кожне й пише в журнал. Зверни увагу: msg[:40] — зріз перших 40 символів (Модуль 6), щоб у консолі друк був коротким.

15.5Запускаємо й дивимось результат

Запусти у терміналі:

python triage.py        # або python3 triage.py на macOS / Linux

Що ти маєш побачити у терміналі:

[оплата] оброблено: Не можу оплатити, картка не проходить...
[інше] оброблено: Дякую, кур'єр приїхав вчасно, все чудово...
[доставка] оброблено: Де моя посилка? Замовлення №123...
Готово. Оброблено звернень: 3. Дивись triage_log.txt

А головне — відкрий файл triage_log.txt. Там будуть готові до перевірки записи, приблизно такі:

[оплата]
  клієнт: Не можу оплатити, картка не проходить — допоможіть!
  чернетка: Доброго дня! Прикро, що виникла проблема з оплатою...

Це вже не іграшка: за секунди агент розсортував звернення й підготував чернетки, які лишилось лише переглянути людині. На сотнях звернень це економить години щодня.

Якщо помилка одразу. Найчастіше — не підвантажився ключ. Перевір .env у тій самій папці (Модуль 7) і встановлені бібліотеки (pip install anthropic python-dotenv).

15.6Робимо тріаж надійним

Наш перший варіант має слабке місце: якщо модель колись поверне криве JSON, triage_one впаде — і весь цикл зупиниться, не обробивши решту звернень. У реальній роботі це неприпустимо: одне погане звернення не повинно «класти» всю чергу. Додамо «запобіжник» (Модуль 9): 

def triage_safe(message):
    try:
        result = triage_one(message)
        if "category" not in result or "draft" not in result:
            raise ValueError("неповна відповідь")
        return result
    except Exception as e:
        # не валимо процес — позначаємо для ручної обробки
        return {"category": "потребує-уваги",
                "draft": "(автоматична обробка не вдалася, перегляньте вручну)",
                "error": str(e)}

І використовуємо його замість triage_one у головному процесі:

def run_triage():
    messages = get_new_messages()
    for msg in messages:
        result = triage_safe(msg)                      # <-- безпечний варіант
        log_result(msg, result["category"], result["draft"])
        print(f"[{result['category']}] оброблено: {msg[:40]}...")
    print(f"Готово. Оброблено звернень: {len(messages)}.")

Розбір. try/except ловить будь-яку помилку (криве JSON, відсутнє поле). Замість падіння ми повертаємо «безпечний» запис із позначкою потребує-уваги — таке звернення просто потрапить до людини. Перевірка if "category" not in result ... гарантує, що контракт виконано (Модуль 9). Тепер жодне окреме звернення не зупинить усю чергу — це і є продакшн-мислення.

15.7Людина в контурі

Помітив ключове рішення в нашому дизайні? Агент не надсилає відповіді сам — він готує чернетки, а відправляє їх людина після перевірки. Це навмисно й дуже важливо.

Людина в контурі (human-in-the-loop) — принцип, за яким важливі або незворотні дії виконуються лише після схвалення людиною. Для дій, що читають дані, автоматизація безпечна. Для дій, що змінюють чи надсилають назовні (лист клієнту, оплата, видалення), краще лишати підтвердження — особливо поки система молода й ти ще не впевнений у її якості.

  • Читання — автоматично (зібрати, класифікувати, підсумувати).
  • Зміна/надсилання — з підтвердженням (надіслати лист, оновити запис).
  • Поступове зняття контролю. Коли впевнишся в якості (через evals, Модуль 19), частину рутинних дій можна довірити агенту повністю — але свідомо, а не наосліп.

Практичний приклад межі. У нашому тріажі: класифікація й чернетка — автоматично (це лише підготовка). А ось крок «надіслати відповідь клієнту» ми навмисно не автоматизували — його робить оператор, переглянувши triage_log.txt. Це і є людина в контурі на практиці.

15.8Підключення реальних систем і масштаб

Наш тріаж готовий — лишилось «приземлити» його на справжній бізнес. Гарна новина: код майже не зміниться, бо ми правильно відокремили інструменти.

  • Реальні дані. Заміни «начинку» get_new_messages на запит до API пошти/CRM (або готовий MCP-конектор, урок 15.2). Решта коду лишається.
  • Реальний запис. Заміни log_result із файлу на запис у таблицю чи CRM через їхній API. Інтерфейс функції той самий.
  • Регулярність. Щоб тріаж працював сам — запускай його за розкладом (наприклад, щогодини). Як зробити сервіс, що працює 24/7, — наступна фаза (Модуль 17).
  • Обсяг. На великих чергах слідкуй за вартістю (Модуль 8) і лімітами API (backoff при 429). Дешевша модель для простої класифікації економить помітно.

Чому це працює так легко. Ми від початку відокремили що робити (логіка тріажу) від звідки дані (інструменти). Тому перехід від демо до бойового — це заміна двох функцій, а не переписування. Це і є хороша архітектура, якій ти вже навчився.

Підсумок модуля й Фази C. Ти вмієш під'єднувати агентів до реальних інструментів (через API чи MCP), зібрав повну надійну бізнес-автоматизацію (тріаж із обробкою помилок), розумієш людину в контурі й знаєш, як перейти від демо до бойової системи. Це і є те, заради чого ти прийшов — автоматизувати реальну роботу. Далі — Фаза D: зробимо твоє рішення «дорослим» продуктом, що працює на сервері 24/7. Починаємо з бекенду в Модулі 16.
