Трек III · Розробка з Claude

Model Context Protocol

Просунутий · 5 уроків · ≈ 70 хв читання

У Модулі 6 модель отримала руки, у сьомому — пам'ять. Але кожна інтеграція досі писалася вручну і жила лише у твоєму коді. MCP — Model Context Protocol, відкритий стандарт, представлений Anthropic наприкінці 2024 року, — робить інструменти й дані переносними: написав сервер один раз — підключив до будь-якого сумісного застосунку. Як універсальний роз'єм замість жмені перехідників.

8.1Проблема N×M інтеграцій

Порахуймо чесно. У тебе M застосунків зі штучним інтелектом: чат-асистент, помічник в IDE, внутрішній агент. І N джерел: GitHub, база замовлень, CRM, файлове сховище. До стандарту кожна пара означала окрему кастомну інтеграцію — свій код, свій формат, свої баги. Разом M×N конекторів, і кожен новий застосунок чи джерело множить роботу знову.

MCP перетворює множення на додавання. Застосунок реалізує клієнтську частину протоколу один раз — і вміє говорити з будь-яким сервером. Джерело отримує один MCP-сервер — і доступне будь-якому застосунку. M + N компонентів замість M × N.

Чотири кастомні інтеграції перетворюються на чотири стандартні компоненти — і далі різниця лише зростає

Важливі дві речі. По-перше, MCP — відкритий стандарт: специфікація і SDK доступні всім, і його підтримка давно вийшла за межі продуктів Anthropic — це фактично спільна мова галузі для підключення контексту. По-друге, tool use з Модуля 6 нікуди не зник: MCP стандартизує, як інструменти описуються, знаходяться і викликаються між застосунками, — сама механіка виклику тобі вже знайома.

8.2Архітектура: host → client → server

У протоколі три ролі.

  • Host — застосунок, у якому живе модель: Claude Desktop, Claude Code, твій власний агент. Він вирішує, які сервери підключати і що показувати моделі.
  • Client — конектор усередині хоста. Один клієнт тримає з'єднання рівно з одним сервером: зв'язок 1:1.
  • Server — легка програма перед конкретним джерелом: оголошує свої можливості та виконує запити. База замовлень, файли, месенджер — кожному своє.

Спілкуються вони повідомленнями JSON-RPC 2.0. Транспорт — на вибір: stdio для локальних серверів (хост запускає сервер як підпроцес і говорить із ним через стандартні потоки) або HTTP для віддалених.

Один клієнт — один сервер; серверів у хоста може бути скільки завгодно

Життєвий цикл простий: хост підключає сервер → відбувається рукостискання й обмін можливостями («у мене три tools і два resources») → під час роботи модель і хост викликають ці можливості, а результати повертаються в контекст розмови.

Ключова думка

Сервер не знає і не мусить знати, який саме хост його викликає. Саме ця взаємна анонімність дає переносимість: сервер бази замовлень, написаний для Claude Desktop, без жодної зміни працюватиме в Claude Code чи будь-якому іншому сумісному застосунку.

8.3Три примітиви: tools, resources, prompts

Сервер може пропонувати три типи можливостей — і різниця між ними не в тому, «що це», а в тому, хто ініціює використання.

Примітив Хто ініціює Приклад
Tools Модель — сама вирішує викликати get_orders_for_date: дістати замовлення з бази
Resources Застосунок — підкладає дані в контекст menu://current: актуальне меню для читання
Prompts Користувач — явно обирає шаблон weekly_report: тижневий аналіз відгуків
  • Tools — наш Модуль 6 у стандартизованій обгортці: функції зі схемами, які модель викликає за потреби.
  • Resources — дані для читання, адресовані URI: файл, запис бази, документ. Модель не «лазить» по них сама — хост вирішує, що і коли підкласти в контекст.
  • Prompts — готові параметризовані шаблони, які людина запускає свідомо (наприклад, слеш-командою). Пам'ятаєш шаблон тижневого звіту з Модуля 4? Ідеальний кандидат: один раз поклав на сервер — уся команда користується.

Цей поділ — не бюрократія, а рівні довіри: модель контролює лише tools, застосунок — resources, людина — prompts. Кожен примітив запускається тим, кому це належить за ризиком. Для повноти: протокол має й «зворотні» можливості клієнта — наприклад, sampling, коли сервер просить хоста згенерувати текст моделлю, — але це вже за межами нашого модуля.

8.4Перший власний MCP-сервер

Офіційний Python SDK має шар FastMCP, який робить сервер майже декларативним: декоратор перетворює функцію на tool, type hints стають JSON-схемою, а docstring — описом. Пам'ятаєш, як у Модулі 6 ми писали схеми руками? Тут вони генеруються самі — і це чесна винагорода за розуміння механіки.

Python · server.py — сервер кейтерингу
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("catering")

ORDERS = [
    {"date": "2026-06-20", "event": "фуршет", "guests": 30, "status": "confirmed"},
    {"date": "2026-06-20", "event": "банкет", "guests": 45, "status": "pending"},
]

@mcp.tool()
def get_orders_for_date(date: str, status: str = "all") -> list[dict]:
    """Повертає замовлення кейтерингу на дату у форматі YYYY-MM-DD.
    status: confirmed | pending | all (за замовчуванням all)."""
    result = [o for o in ORDERS if o["date"] == date]
    if status != "all":
        result = [o for o in result if o["status"] == status]
    return result

@mcp.resource("menu://current")
def current_menu() -> str:
    """Актуальне меню для подій."""
    return "Фуршет: канапе, тарти, лимонади. Банкет: три подачі, десертний стіл."

@mcp.prompt()
def weekly_report(reviews: str) -> str:
    """Шаблон тижневого аналізу відгуків — той самий, з Модуля 4."""
    return (
        "Ти — аналітик якості сервісу кейтерингу. Проаналізуй відгуки, "
        "згрупуй проблеми за темами і дай три пріоритетні дії.\n\n"
        "<reviews>\n" + reviews + "\n</reviews>"
    )

if __name__ == "__main__":
    mcp.run()   # транспорт за замовчуванням — stdio

Тридцять рядків — і в тебе сервер з усіма трьома примітивами. Лишилося сказати хосту, де його знайти. Для Claude Desktop це запис у конфігурації:

JSON · фрагмент конфігурації хоста
{
  "mcpServers": {
    "catering": {
      "command": "python",
      "args": ["/повний/шлях/до/server.py"]

У Claude Code сервер додається командою claude mcp add; точні шляхи конфігів і нюанси конкретних клієнтів — у документації MCP та самого застосунку. Після перезапуску хост побачить можливості сервера: спитаєш у чаті «що в нас підтверджено на двадцяте?» — і модель викличе твій get_orders_for_date через стандартний протокол. Той самий цикл tool use з Модуля 6, лише тепер між процесами і без жодного рядка інтеграційного коду на боці застосунку.

8.5Екосистема готових серверів і безпека

Перед тим як писати свій сервер — перевір каталоги готових: файлова система, Git і GitHub, бази даних, пошук, месенджери, таск-трекери — екосистема налічує сотні серверів від спільноти й вендорів. А твій RAG-ретривер із Модуля 7 — природний кандидат стати сервером search_knowledge_base: один раз загорнув — і база знань доступна з будь-якого MCP-сумісного застосунку.

Тепер серйозна частина. MCP-сервер — це код, який працює з твоїми правами і чий вивід читає твоя модель. Звідси чотири правила:

  • Встановлюй лише довірене. Сервер із випадкового репозиторію — як випадковий виконуваний файл; маленькі сервери нескладно переглянути очима перед запуском.
  • Prompt injection повертається. Описи інструментів і їхні результати — теж вхід для моделі: зловмисний сервер може «отруїти» контекст інструкціями (tool poisoning). Розділення даних та інструкцій з Модуля 3 і пильність з Модуля 11 — обов'язкові.
  • Мінімальні права. Read-only доступ, де можливо; окремі токени з вузькими дозволами замість «майстер-ключа».
  • Людина підтверджує небезпечне. Видалення, надсилання, платежі — лише з явним підтвердженням користувача, а не «тихо» з волі моделі.

На цьому Трек III завершено повністю: модель отримала руки (Модуль 6), пам'ять (Модуль 7) і стандартний роз'єм до світу (Модуль 8). Попереду фінальний трек: у Модулі 9 усе це запрацює в циклі — агенти й агентні системи; Модуль 10 навчить вимірювати якість, а Модуль 11 поглибить сьогоднішні безпекові застереження.

Підсумок модуля
  • MCP перетворює M×N інтеграцій на M+N: одна спільна мова для застосунків і джерел.
  • Архітектура: host (застосунок) → client (конектор 1:1) → server (перед джерелом); JSON-RPC поверх stdio або HTTP.
  • Три примітиви за рівнем контролю: tools викликає модель, resources підкладає застосунок, prompts запускає користувач.
  • FastMCP: type hints стають схемою, docstring — описом; робочий сервер — це ~30 рядків.
  • Сервер не знає хоста — тому написане один раз працює всюди.
  • Безпека: сервери працюють із твоїми правами — довіряй, обмежуй, підтверджуй небезпечне.
