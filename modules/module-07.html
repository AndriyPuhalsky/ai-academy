Трек III · Розробка з Claude

RAG і робота зі знаннями

Середній · 5 уроків · ≈ 60 хв читання

Контекстне вікно велике, але скінченне — і за кожен вхідний токен ти платиш. Що робити, коли знань — база FAQ, сотні договорів, ціла внутрішня вікі — більше, ніж розумно класти у промпт? Відповідь індустрії — RAG, retrieval-augmented generation: «генерація, підсилена пошуком». Ідея проста: не тягни всю бібліотеку — знайди потрібні сторінки.

7.1Навіщо RAG: межі «вкласти все у промпт»

Здавалося б, рішення очевидне: контекст великий — клади всі документи в кожен запит. На практиці це ламається з трьох причин.

  • Фізична межа. Вікно сягає сотень тисяч токенів, але корпоративна база знань легко більша — а українська, нагадаємо з Модуля 1, ще й «дорожча» в токенах.
  • Гроші та швидкість. Платити за двісті сторінок вхідних токенів на кожен запит заради одного потрібного абзацу — марнотратство; та й обробка великого контексту повільніша.
  • Якість. Ефект «голки в сіні»: серед тонн нерелевантного тексту моделі легше загубити потрібне — і впевненіше згалюцинувати.

Аналогія, яка тримає весь модуль: досвідчений бібліотекар. На питання читача він не перечитує бібліотеку — за каталогом знаходить три потрібні книжки і кладе на стіл. RAG — це автоматичний бібліотекар для нашого «робочого столу» з Модуля 1: Retrieval (знайти релевантні фрагменти) → Augmentation (підкласти їх у промпт) → Generation (відповісти, спираючись на них). 

flowchart LR
  Q["Питання"] --> R["Пошук: знайти релевантні фрагменти в базі знань"]
  R --> C["У промпт кладемо лише знайдене"]
  C --> M["Модель відповідає, спираючись на фрагменти"]

RAG — системна версія «заземлення» з Модуля 4: документи тепер добираються автоматично

7.2Embeddings: зміст як координати

Перше питання RAG: як шукати? Пошук за ключовими словами ламається на синонімах: для нього «банкет» і «святкова вечеря на 40 осіб» — різні рядки, хоча зміст один. Потрібен пошук за сенсом.

Тут з'являється embedding — числове представлення тексту: вектор із сотень чи тисяч чисел. Спеціальна модель-ембедер навчена так, щоб тексти про одне й те саме опинялися поруч у цьому багатовимірному просторі. Уяви карту смислів: «фуршет» і «банкет» — сусідні квартали, «рахунок за оренду залу» — зовсім інший район міста.

Близькість векторів міряють косинусною подібністю: 1 — однаковий напрямок (той самий зміст), близько 0 — нічого спільного. Ось уся математика на іграшкових векторах:

Python · косинусна подібність
def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = sum(x * x for x in a) ** 0.5
    norm_b = sum(x * x for x in b) ** 0.5
    return dot / (norm_a * norm_b)

# іграшкові вектори на 4 виміри — справжні мають сотні й тисячі
v_banquet = [0.9, 0.1, 0.7, 0.0]   # «банкет на 45 гостей»
v_buffet  = [0.8, 0.2, 0.6, 0.1]   # «фуршет для компанії»
v_invoice = [0.1, 0.9, 0.0, 0.8]   # «рахунок за оренду залу»

print(cosine(v_banquet, v_buffet))    # ≈ 0.99 — теми близькі
print(cosine(v_banquet, v_invoice))   # ≈ 0.13 — теми різні
Важлива деталь

Ембедер — окрема спеціалізована модель, не Claude. Для продакшну беруть готові рішення — наприклад, Voyage AI (його рекомендує документація Anthropic) або open-source моделі. Головне правило: питання і документи мають проходити через одну й ту саму embedding-модель, інакше «карти смислів» не зійдуться.

7.3Chunking: різати з розумом

Документи в базу знань потрапляють не цілком, а чанками — фрагментами. Навіщо різати: пошук влучає в конкретний абзац, а не у двохсотсторінковий PDF; у контекст їде лише потрібне; і короткий зв'язний шматок embedding «тримає» значно краще за простирадло.

Розмір — компроміс. Завеликі чанки тягнуть у вікно зайве і розмивають пошук; замалі — втрачають зміст: фрагмент «він має бути сплачений протягом п'яти днів» без сусідніх речень не скаже, хто такий «він».

Стратегія Суть Коли брати
Фіксований розмір + перекриття Рівні шматки, сусідні перекриваються на 10–20% Швидкий старт, однорідні тексти
За структурою документа Заголовки, абзаци, пункти договору Найкращий дефолт для більшості баз
Семантичний chunking Межі — там, де змінюється тема Складні кейси, коли структури немає

Золоте правило: чанк має бути зрозумілим сам по собі. Найдешевший спосіб цього досягти — контекстний заголовок: допиши на початок кожного чанка рядок на кшталт «Документ: Договір оренди №7 · Розділ: Оплата». Один рядок помітно покращує і пошук, і точність відповідей — особливо коли в базі багато схожих документів.

7.4Повний цикл RAG у коді

RAG живе у два етапи. Індексація — заздалегідь і нечасто: порізати документи, порахувати embeddings, скласти у сховище. Запит — щоразу: ембеднути питання, знайти найближчі чанки, зібрати промпт, отримати відповідь.

client = Anthropic()
MODEL = "claude-sonnet-5"

    # (Voyage AI, sentence-transformers тощо); тут — заглушка
    ...

# ---------- Етап 1 · Індексація (виконується заздалегідь) ----------
chunks = [
    {"id": "faq-01", "text": "FAQ · Замовлення: мінімальний фуршет — 15 гостей."},
    {"id": "faq-02", "text": "FAQ · Доставка: по Чернівцях безкоштовно від 5000 грн."},
    {"id": "faq-03", "text": "FAQ · Зміни: приймаємо до 48 годин до події."},
]
index = [
    {"id": c["id"], "vector": embed(c["text"]), "text": c["text"]}
    for c in chunks
]

# ---------- Етап 2 · Запит (виконується щоразу) ----------
def retrieve(query, k=3):
    q = embed(query)
    scored = sorted(index, key=lambda c: cosine(q, c["vector"]), reverse=True)
    return scored[:k]

def answer(question):
    found = retrieve(question)
    context = "\n\n".join(
        "<chunk id=\"" + c["id"] + "\">\n" + c["text"] + "\n</chunk>"
        for c in found
    )
    response = client.messages.create(
        model=MODEL,
        max_tokens=600,
        temperature=0,
        system="Відповідай ЛИШЕ на основі фрагментів у <knowledge>. "
               "Після кожного твердження вкажи id джерела у квадратних "
               "дужках, наприклад [faq-02]. Якщо відповіді у фрагментах "
               "немає — чесно скажи це.",
        messages=[{"role": "user",
                   "content": "<knowledge>\n" + context + "\n</knowledge>\n\n"
                              "Питання: " + question}],
    )
    return response.content[0].text

print(answer("Скільки коштує доставка фуршету по місту?"))

Розбір ключових рішень:

  • top-k = 3–5 — типовий старт: досить для відповіді, не засмічує контекст;
  • temperature 0 — фактична задача, мінімум випадковості (Модуль 5);
  • теги і вимога посилань — усе ремесло Модулів 3–4 працює тут: <knowledge> відокремлює дані, id чанків роблять відповідь перевірюваною;
  • чесний fallback — «у фрагментах немає» замість вигадки: системний промпт вимагає це прямо.

У продакшні замість списку в пам'яті — векторні сховища: FAISS, Chroma, Qdrant, pgvector. Принцип той самий, масштаб і швидкість інші. А коли базовий RAG запрацює, є рівень два: гібридний пошук (вектори плюс ключові слова), reranking знайдених чанків окремою моделлю і фільтри за метаданими — датою, типом документа, клієнтом.

7.5Цитування джерел і чесний вибір підходу

Чому цитування — не прикраса, а вимога: посилання на джерело робить відповідь перевірюваною, а галюцинацію — видимою. Користувач клікає на [faq-02] і бачить, що там написано насправді. Три робочі рівні:

  • id чанків у промпті + вимога посилань — як у коді вище: найпростіше і вже працює;
  • «цитати перед висновком» з Модуля 4 поверх знайдених чанків — для відповідей із високою ціною помилки;
  • вбудовані citations в API — для документних блоків Claude вміє повертати точні прив'язки до фрагментів джерела; деталі та актуальний синтаксис — у docs.claude.com.

І чесна розмова наостанок: RAG потрібен не завжди. Це ще одна система — індекс, синхронізація, моніторинг, — і вона має окупатися.

Ситуація Розумний вибір
Один документ чи мала база, оновлюється рідко Просто поклади в контекст цілком; кешування промпта здешевить повтори
Велика або жива база: сотні документів, щоденні зміни RAG: переіндексував змінений чанк — і система актуальна
Потрібні точкові посилання на джерела RAG природніший: чанки вже мають id
Прототип на сьогодні ввечері Почни з контексту; RAG доростеш, коли впрешся в межі

Правило треку: починай із найпростішого, що працює. RAG дав моделі пам'ять, tool use з Модуля 6 — руки. У Модулі 8 побачимо MCP — відкритий стандарт, що з'єднує і пам'ять, і руки з будь-яким застосунком: твій RAG-ретривер, до речі, часто і стає одним із MCP-інструментів.

Підсумок модуля
  • RAG = знайти → підкласти → відповісти: не тягни бібліотеку, принеси сторінки.
  • Embedding — координати змісту: близькі за сенсом тексти мають близькі вектори; міряємо косинусом.
  • Ембедер — окрема модель; питання й документи ембедь однією і тією самою.
  • Чанк має жити сам по собі: ріж за структурою, додавай контекстний заголовок, давай перекриття.
  • У промпт — top-k чанків з id; вимагай посилань і чесного «у базі немає».
  • RAG — не завжди: малу статичну базу дешевше покласти в контекст цілком.
