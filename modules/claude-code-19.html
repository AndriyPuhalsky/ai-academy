Фаза 4 · Інструменти й автоматизація

Запуск без діалогу: Claude як утиліта

Середній · 8 блоків · ≈ 50 хв читання

Усі попередні модулі описували розмову: ти пишеш, Claude Code відповідає, показує кроки, питає дозволу, ти тиснеш «так». Розмову не можна вставити у файл зі скриптом і не можна доручити серверу, який запускає перевірки після кожної твоєї зміни в коді. Цей модуль про те, як та сама програма перетворюється на звичайну команду: приймає завдання рядком, друкує відповідь текстом і завершується числом, за яким скрипт розуміє «вийшло» чи «ні».

Це один із двох модулів про автоматизацію, і вони поділені за дуже простою межею: тут запуск робиш ти — руками, скриптом або подією в репозиторії. Про те, як Claude Code працює, коли тебе взагалі немає за комп'ютером (розписання, канали в месенджерах, віддалені сесії), — наступний, двадцятий модуль.

Що в цьому модулі є, а чого немає

Є: прапорець -p (він же --print) · стандартний ввід, стандартний вивід і конвеєр (pipe) · три формати відповіді (text, json, stream-json) · коди виходу, включно з рідкісним 143 · структурована відповідь за схемою (--json-schema) · режим --bare і чому в скрипті він майже завжди правильний · безпека чужого репозиторію · GitHub Actions і GitLab CI · автоматична рецензія пул-реквеста · Agent SDK оглядово.

Немає: завдань за розписанням, /loop, хмарних Routines, каналів (Telegram, Discord), Remote Control і віддалених поверхонь — це модуль 20. Режими дозволів розібрані в модулях 7 і 8, зовнішні інструменти MCP — у 18, перехоплювачі подій (hooks) — у 16; тут вони з'являються лише там, де від них залежить безпека неінтерактивного запуску.

Про екрани в цьому уроці

Усі п'ять блоків термінала — живі запуски 2026-09-04 на Claude Code 2.1.236, macOS 26.5.2, у порожній тестовій теці /private/tmp/c19-demo. Два перші — це один справжній оплачений запуск: команда й відповідь на неї, а ціна видна прямо у виводі. Решта три не роблять жодного запиту до моделі й тому нічого не коштують: Claude Code відкидає такі команди ще на розборі аргументів.

Приклади, які взяті з документації й не запускались на цій машині (конвеєр з файлом, YAML для GitHub і GitLab), стоять звичайним блоком коду, а не блоком «термінал». Так видно різницю між «я це бачив» і «так написано в доксах».

1Навіщо це

Уяви три задачі, які трапляються щотижня в будь-якому проєкті:

  • перед відправкою змін перевірити їх на друкарські помилки — не очима, а автоматично;
  • отримати збірку, яка впала з двома екранами незрозумілого тексту, і швидко зрозуміти, у чому корінь;
  • щоб кожну пропозицію змін у спільному проєкті хтось прочитав першим — навіть коли всі зайняті.

Кожну з них Claude Code вміє. Але в тому вигляді, у якому ти працював із ним досі, кожна вимагає, щоб жива людина сиділа перед вікном: відкрила сесію, вставила текст, прочитала відповідь, натиснула «дозволити». Автоматизувати діалог неможливо — його можна лише повторювати руками.

Прапорець -p прибирає діалог. Claude Code отримує завдання одним рядком, виконує його й завершується. Ніякого екрана, ніяких кроків, ніякого «продовжити?». На виході — текст, який можна зберегти у файл, передати іншій програмі або показати в журналі сервера.

Три слова, без яких далі буде незрозуміло

Це поняття не про Claude Code — вони старші за нього років на п'ятдесят і стосуються будь-якої програми в терміналі. Якщо ти їх уже знаєш, наступні три абзаци можна прогорнути.

  • Стандартний вивід (stdout) — це те, що програма друкує в термінал. Той самий текст можна не показувати на екрані, а покласти у файл: знак > після команди означає «замість екрана — у цей файл». Наприклад, ls > список.txt не покаже нічого, але створить файл зі списком.
  • Стандартний ввід (stdin) — це те, що програма отримує «на вхід», не з клавіатури, а від іншої програми або з файла.
  • Конвеєр, або pipe — вертикальна риска | між двома командами. Вона з'єднує вивід лівої зі вводом правої: «візьми те, що надрукувала перша команда, і віддай другій». На клавіатурі цей знак зазвичай там само, де зворотний слеш.

І четверте, найважливіше для цього модуля:

  • Код виходу (exit code) — число, яке команда лишає після себе. Нуль означає «все гаразд», будь-яке інше число — «щось пішло не так». Число не друкується на екрані; його дивляться окремою командою echo $? одразу після виконаної. Саме на цьому числі тримається вся автоматизація: скрипт не вміє читати текст, зате вміє порівняти число з нулем.

Документація Claude Code формулює це в одне речення: програма завершується кодом 0 при успіху й ненульовим при збої, «тож ваші скрипти можуть розгалужуватись за статусом виходу».

Що таке CI і до чого тут він

CI (continuous integration, «безперервна інтеграція») — це сервіс, який після кожної твоєї зміни в коді сам запускає перевірки: збирає проєкт, ганяє тести, перевіряє стиль. Ти нічого не натискаєш — сервіс помічає зміну й запускає перелік команд, описаний у файлі всередині твого ж репозиторію. У GitHub це називається GitHub Actions, у GitLab — GitLab CI/CD.

Ще два слова з того самого світу, бо далі вони трапляться десятки разів. Репозиторій — тека проєкту під наглядом git, системи контролю версій: вона пам'ятає кожну зміну й того, хто її вніс. Пул-реквест (pull request; у GitLab його називають merge request) — заявка «я зробив зміни в окремій гілці, прошу влити їх в основну». Саме на сторінці такої заявки колеги дивляться різницю в коді й лишають зауваження — і саме туди вміє писати Claude Code. Докладно про роботу з git — модуль 21.

Для CI будь-який інструмент — це команда, яка щось робить і повертає код виходу. Тому claude -p вставляється туди рівно так само, як npm test або ls. Уся друга половина цього модуля — про наслідки цього факту: і про те, що він дає, і про те, чим він небезпечний.

Одна фраза, яку варто запам'ятати

-p не робить Claude Code «слабшим» чи «іншим». Це той самий агент із тими самими інструментами й тими самими правами. Зникає лише той, хто дивиться на екран і каже «ні». Усе, що в діалозі вирішувала людина, у цьому режимі вирішують налаштування — або не вирішує ніхто.

2Як це виглядає на екрані

Найкоротший неінтерактивний запуск виглядає так. Тека порожня, у ній немає ні .claude, ні CLAUDE.md, ні .mcp.json — це навмисно, щоб на вивід не впливало нічого зайвого.

Три частини цього рядка: -p вимикає діалог і вмикає друк відповіді, --output-format json просить не голий текст, а структуру з метаданими, --model haiku садить запуск на легшу модель, щоб він коштував менше — про вибір моделі був модуль 10. Відповідь приходить одним довгим рядком; нижче — той самий вивід, пропущений через python3 -m json.tool, щоб він розклався по рядках, і скорочений: із нього прибрано поля з таймінгами, повторний розріз iterations і технічні ідентифікатори. Нічого не додано.

Читається це так:

Поле Що воно означає
result сама відповідь. Те, що в режимі text було б єдиним, що ти побачив
is_error false — робота завершилась нормально
num_turns скільки ходів знадобилось. Одне питання без інструментів — один хід
session_id ідентифікатор розмови. Саме за ним її можна продовжити наступною командою
total_cost_usd вартість цього запуску в доларах. Документація попереджає: це оцінка з боку клієнта, вона може розійтися з реальним рахунком
permission_denials перелік дій, у яких було відмовлено. Порожній — нічого не блокувалось

І тут — перший неприємний сюрприз, який видно тільки на справжніх числах. Відповідь складалась із двох літер, а коштувала близько двох центів. Причина в рядку cache_creation_input_tokens: 8018: у контекст поїхав увесь стартовий вантаж сесії — системна частина, файли пам'яті, описи інструментів. Відповідь коротка, підготовка до неї — ні. Про те, чим це лікується, — далі, коли зайде мова про --bare.

Три екрани помилок, які нічого не коштують

Наступні три блоки зняті так само наживо, але жоден із них не звертається до моделі: Claude Code відкидає команду ще на розборі аргументів. Це важлива властивість — на таких запусках можна безпечно перевіряти свої припущення.

Перший — найчастіша причина, чому приклад із документації не працює в новачка. Прапорець --bare (про нього блок 3) навмисно не читає ні збережений вхід, ні системне сховище паролів:

Машина, на якій це знято, увійшла за підпискою й в інтерактивному режимі працює бездоганно. Але --bare «збереженого входу» не бачить: він приймає лише ключ API у змінній середовища. Порада «спробуй перезайти» тут не допомагає — потрібен інший спосіб автентифікації.

Другий екран — про структурований вивід. Прапорець --json-schema просить відповідь заданої форми, і Claude Code перевіряє саму схему до запуску. Дві помилки, які легко сплутати, дають два різні повідомлення:

Обидва запуски завершились кодом 1. Перший каже «це взагалі не JSON», другий — «JSON правильний, але як опис форми він недійсний». Друге повідомлення дослівно збігається з тим, що обіцяє документація, плюс діагностика від перевірки схеми. Останній рядок довелось перенести на два — у терміналі він один.

Третій екран — той, заради якого цей курс узагалі існує. У документації на 2026-09-04 описаний прапорець --permission-prompts із приміткою «потребує Claude Code v2.1.259 або новішої». Ось що він робить у встановленій 2.1.236:

Останні дві команди — це перевірка, яка стане в пригоді ще багато разів. strings дістає з програми всі текстові рядки, grep -c рахує збіги, а $(which claude) підставляє шлях до тієї копії claude, яка справді запускається. Нуль означає «цієї назви в моїй збірці немає». Останній рядок — контрольний: вигадана назва теж дає нуль, отже перевірка працює, а не завжди друкує нуль.

Висновок, який варто винести за межі цього прапорця: документація описує найсвіжішу версію, а в тебе встановлена та, що встановлена. Розрив у пару десятків версій — норма, а не аварія. Тому в скрипті, який має працювати на чужих машинах, кожен нечастий прапорець варто перевірити такою парою команд.

3Як це працює

Усередині claude -p — той самий агентний цикл, що й у сесії: модель читає завдання, викликає інструменти, дивиться на результат, повторює. Відрізняються «краї»: звідки береться завдання й куди дівається відповідь.

Шлях одного неінтерактивного запуску. Розвилка на початку — найважливіше рішення всього модуля.

Що вантажиться, якщо не сказати інакше

Без --bare неінтерактивний запуск підбирає рівно той самий контекст, що й інтерактивна сесія: перехоплювачі подій з .claude/settings.json проєкту, зовнішні сервери з .mcp.json, файл пам'яті CLAUDE.md, навички, власні команди, субагентів, плагіни.

Для роботи у власному проєкті це зручно. Для чужого репозиторію це головна небезпека всього модуля, і документація каже про неї прямо: без --bare сесія -p виконує хуки з налаштувань проєкту й підключає сервери з його .mcp.json навіть у теці, якій ти ніколи не давав довіри. Ні діалогу довіри до робочої теки, ні окремого схвалення кожного сервера в цьому режимі немає — показати їх нікому.

Те саме написано в довідці самої програми. Ось дослівний фрагмент опису -p зі знімка claude --help, знятого 2026-09-03 на версії 2.1.236:

З довідки claude --help, 2.1.236

«Note: The workspace trust dialog is skipped when Claude is run in non-interactive mode (via -p, or when stdout is not a TTY, e.g. piped or redirected output). Only use this in directories you trust. Settings files that fail validation are silently ignored in this mode (no error dialog is shown).»

«Діалог довіри до робочої теки пропускається в неінтерактивному режимі — через -p або коли вивід не є терміналом, тобто перенаправлений чи переданий далі конвеєром. Використовуйте це лише в теках, яким довіряєте. Файли налаштувань, які не пройшли перевірку, у цьому режимі мовчки ігноруються, без вікна помилки.»

Зверни увагу на другу половину: діалог довіри пропускається не лише через -p, а й тоді, коли вивід перенаправлений. Тобто claude > звіт.txt у чужому репозиторії теж стартує без питання про довіру — сесія лишається інтерактивною, але цього запобіжника в ній уже немає.

Чотири способи запустити чужий репозиторій і не постраждати

Документація дозволів перелічує їх поіменно. Вони не взаємозамінні:

Спосіб Що саме закриває
--bare найширший: із проєкту не читаються ні хуки, ні навички, ні команди, ні субагенти, ні плагіни, ні сервери .mcp.json. Але блок env і кілька помічників у налаштуваннях проєкту все одно діють
--setting-sources user Claude Code не читає ні файли налаштувань проєкту, ні його .mcp.json, лишаючи твої власні
--settings '{"disableAllHooks": true}' вимикає перехоплювачі подій саме для цього запуску. Той самий ключ у твоїх користувацьких налаштуваннях не рятує: налаштування проєкту сильніші й можуть повернути false
disabledMcpjsonServers ключ у налаштуваннях, який відхиляє конкретний сервер із .mcp.json за іменем — у сесіях будь-якого типу

Найпростіша звичка: у скрипті й у CI писати --bare, доки не з'ясувалось, що чогось бракує. Документація каже про нього дослівно: «рекомендований режим для скриптових і SDK-викликів, і в майбутньому релізі стане дефолтом для -p».

Ціна цього рішення — автентифікація. У режимі --bare Claude Code ніколи не читає ні збережений вхід за підпискою, ні системне сховище паролів. Потрібен ключ API у змінній ANTHROPIC_API_KEY. Це рівно той екран помилки, який ти бачив у блоці 2.

Три формати відповіді

Формат Що друкує Коли брати
text лише текст відповіді. Це значення за замовчуванням коли відповідь читатиме людина або вона одразу йде у файл
json один об'єкт із відповіддю, ідентифікатором сесії, вартістю й лічильниками коли відповідь читатиме програма
stream-json потік подій, по одному JSON-об'єкту на рядок, у міру роботи коли треба показувати хід роботи, доки він триває

Потоковий формат вмикається разом із двома супутніми прапорцями: --output-format stream-json --verbose --include-partial-messages. Останній рядок потоку — подія result із фінальним текстом і метаданими, тобто те саме, що дав би формат json.

Обережно з потоком у навчальних і публічних матеріалах

Перша ж подія потоку (system/init) містить перелік того, що завантажилось на цій машині: сервери MCP, плагіни, навички, субагенти, ідентифікатор сесії й локальні шляхи. Це зручно для діагностики й геть незручно для скріншота в чаті: разом із подією поїде мапа твоєї робочої машини.

Корисний побічний ефект того самого: у полі mcp_server_errors видно записи --mcp-config, які не пройшли перевірку й були пропущені. Поле з'являється лише за наявності помилок, тому перевірка в CI звучить як «масив не порожній — валимо збірку». Потребує версії 2.1.219 або новішої.

Коди виходу

  • 0 — успіх;
  • будь-яке інше число — збій. Помилка в самих аргументах друкується в потік помилок (stderr) ще до старту, а поломка вже під час роботи — наприклад, відсутня автентифікація — друкується як результат у звичайний вивід;
  • 143 — окремий випадок: процес зупинили сигналом SIGTERM. Так робить CI, коли спрацював таймаут завдання, і так робить kill. Хід, що тривав, лишається незавершеним, результат не записується. Щоб завершити хід коректно, документація радить SIGINT замість SIGTERM.

Конвеєр: подати дані на вхід

Неінтерактивний режим читає стандартний ввід, тому в Claude Code можна «влити» вміст файла або вивід іншої команди. Приклад із документації — пояснити, чому впала збірка: 

cat build-error.txt | claude -p 'concisely explain the root cause of this build error' > output.txt

Читається зліва направо: cat друкує вміст файла, конвеєр віддає його Claude Code, той пояснює причину, а знак > кладе пояснення у файл output.txt. Замість build-error.txt постав будь-який свій файл.

Обмеження, про яке краще знати заздалегідь: переданий конвеєром ввід обмежений 10 МБ. Більше — і Claude Code завершиться з виразною помилкою й ненульовим кодом. Для великих файлів документація радить не вливати їх у конвеєр, а назвати шлях у самому завданні: нехай агент прочитає файл сам.

Той самий підхід перетворює Claude Code на команду проєкту. Приклад із документації для файла package.json — «лінтер друкарських помилок», який дивиться лише на твої зміни відносно основної гілки: 

{
  "scripts": {
    "lint:claude": "git diff main | claude -p \"you are a typo linter. for each typo in this diff, report filename:line on one line and the issue on the next. return nothing else.\""
  }
}

Запускається це командою npm run lint:claude. Документація окремо пояснює два рішення в цьому рядку: різницю подають конвеєром, щоб агенту не знадобився дозвіл на запуск команд, а подвійні лапки екранують, щоб рядок працював і на Windows.

Те саме, але на чужій машині: CI

Далі — той самий claude -p, тільки запускає його не ти, а сервіс. Для GitHub є готова дія (action) anthropics/claude-code-action: ти кладеш у репозиторій невеликий файл-опис, і далі все відбувається саме. 

flowchart LR
  A["Хтось пише @claude у коментарі до задачі або PR"] --> B["GitHub бачить подію й запускає робочий процес"]
  B --> C["Перевірки: чи має автор права на запис і чи це не бот"]
  C --> D["actions/checkout: копія репозиторію на машині GitHub"]
  D --> E["anthropics/claude-code-action, всередині той самий claude -p"]
  E --> F["Відповідь коментарем у тій самій задачі або PR"]
  style E fill:#2A211C,stroke:#D97757,color:#F0EEE6

Інтерактивний режим дії GitHub: запуск від згадки @claude. Автоматичний режим влаштований так само, але замість згадки спрацьовує будь-яка подія, а завдання задане заздалегідь.

Найшвидший спосіб це підключити — команда /install-github-app, набрана прямо в сесії Claude Code: вона встановить застосунок GitHub, збереже секрет із ключем і відкриє готовий пул-реквест із файлами робочих процесів. Потрібні права адміністратора репозиторію. Ручний шлях описаний окремо: встановити застосунок, додати секрет, скопіювати файл робочого процесу самому.

Ось найкоротший робочий файл із документації. Він живе за адресою .github/workflows/claude.yml у твоєму ж репозиторії: 

name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}

Що тут не «шаблонний шум», а сенс: on перелічує події, на які реагувати; if не дає запускати машину на коментарях без згадки; permissions видає рівно ті права, які потрібні; actions/checkout кладе на машину копію репозиторію; рядок із secrets. підставляє ключ, збережений у налаштуваннях репозиторію. Ключ у сам файл не пишуть ніколи — файл лежить у репозиторії, а секрети GitHub зберігає окремо й не показує в журналах.

Два режими дії розрізняються однією ознакою — наявністю поля prompt:

  • інтерактивний (поля prompt немає): Claude чекає на згадку @claude у коментарі, у рецензії або в тексті щойно відкритої задачі, і відповідає коментарем там само;
  • автоматичний (поле prompt є): завдання задане заздалегідь, згадка не потрібна, а результат за замовчуванням лягає в журнал запуску, а не в коментар.

Перед кожним запуском дія перевіряє того, хто його спричинив: у автора має бути право запису в репозиторій, і він не має бути ботом. Друга перевірка існує рівно для того, щоб два боти не зациклились, викликаючи один одного.

Аргументи командного рядка передаються полем claude_args — тобто все, що ти вмієш робити прапорцями локально, працює й тут: 

claude_args: "--max-turns 5 --model claude-sonnet-5 --mcp-config /path/to/config.json"

GitLab CI/CD

Для GitLab готової «дії» немає — там завдання описують кроками звичайного скрипта. Інтеграція у стані бета і, за словами документації, підтримується самим GitLab, а не Anthropic. Її суть — той самий виклик, який ти вже бачив: 

script:
  - >
    claude
    -p "${AI_FLOW_INPUT:-'Review this MR and implement the requested changes'}"
    --permission-mode acceptEdits
    --allowedTools "Bash Read Edit Write mcp__gitlab"
    --debug

Перед цим кроком у файлі стоїть встановлення Claude Code офіційним інсталятором і рядок, який додає теку ~/.local/bin у PATH — саме туди інсталятор кладе програму, і в базовому образі ця тека в PATH не значиться. Ключ ANTHROPIC_API_KEY додається в налаштуваннях проєкту як замаскована змінна, щоб не потрапити в журнали.

Рецензія пул-реквеста

Це окремий продукт, який теж варто знати на ім'я, щоб не переплутати з попередніми двома. Code Review — керований сервіс: він сам аналізує пул-реквести й лишає зауваження прямо на тих рядках коду, де знайшов проблему. Свій файл робочого процесу для цього не потрібен.

Стан на 2026-09-04 за документацією: research preview, доступний на планах Team і Enterprise, недоступний організаціям із режимом нульового зберігання даних. Кожна знахідка позначається рівнем: 🔴 важлива (помилка, яку варто виправити до злиття), 🟡 дрібниця, 🟣 наявна раніше (помилка в коді, яку цей пул-реквест не приносив). Перевірка ніколи не блокує злиття — вона завершується нейтральним результатом навмисно, щоб не ламати наявні процеси команди.

Налаштовується не через CLAUDE.md, а окремим файлом REVIEW.md у корені репозиторію: у ньому пишуть, що саме команда хоче бачити позначеним і з якою суворістю. Документація зазначає, що @-імпорти в цьому файлі не розгортаються — правила треба класти в нього самого.

Якщо плану Team немає, те саме доступне локально командою /code-review прямо в сесії: вона рецензує коміти твоєї гілки й незбережені зміни, працює фоновим субагентом у власному контекстному вікні, а прапорець --fix одразу застосовує знайдене. Псевдонім — /review.

Agent SDK — коли командного рядка мало

Agent SDK — це той самий Claude Code у вигляді бібліотеки, яку ти підключаєш до власної програми: ті самі інструменти, той самий агентний цикл, те саме керування контекстом. Він існує для двох мов: claude-agent-sdk для Python і @anthropic-ai/claude-agent-sdk для TypeScript.

Вибір між ним і -p документація описує коротко: командний рядок — для інтерактивної роботи й разових задач, SDK — коли ти будуєш власний застосунок і не хочеш писати цикл викликів інструментів самостійно. І окремо: щоб керувати тим самим циклом із будь-якої іншої мови, документація радить запускати CLI підпроцесом — із -p і --output-format json. Тобто те, що ти вивчив у цьому модулі, і є універсальним інтерфейсом.

Одне обмеження, яке варто знати наперед: без окремого погодження Anthropic не дозволяє стороннім розробникам пропонувати в своїх продуктах вхід через claude.ai і ліміти підписки. Для власного застосунку на SDK передбачений ключ API.

4Зроби сам

Перед початком — про витрати

Кроки 2–6 роблять справжні запити до моделі й витрачають твій ліміт або гроші так само, як звичайна сесія. Завдання нижче навмисно крихітні. Якщо хочеш заощадити, додай до кожного --model haiku, як у блоці 2.

Крок 1. Окрема тека, щоб нічого не заважало

Створи порожню теку й зайди в неї. Дві команди, набрати одну за одною й натиснути Enter: 

mkdir -p ~/claude-headless
cd ~/claude-headless

mkdir створює теку, -p тут означає «не лаятись, якщо вона вже є» (це інший -p, не той, що в Claude Code — збіг літери), ~ — твоя домашня тека. Навіщо порожня: у ній немає ні CLAUDE.md, ні .claude/, тому на результат не впливає нічого, крім твоєї команди.

Крок 2. Найпростіший запуск

claude -p "Напиши одним реченням, що робить команда ls"

На екрані з'явиться лише текст відповіді — без рамок, без кроків, без питань. Сесія завершилась.

Крок 3. Подивитись код виходу

Одразу після попередньої команди, не запускаючи нічого іншого: 

echo $?

Має надрукуватись 0. Тепер зроби помилку навмисно й повтори перевірку: 

claude -p "x" --output-format bogus
echo $?

Тепер буде 1, а перед ним — рядок, у якому Claude Code перелічує допустимі значення. Це та сама пара, якою перевіряють будь-який прапорець: запусти з навмисно неправильним значенням і подивись, чи взагалі програма про нього знає.

Крок 4. Відповідь у JSON і як дістати з неї потрібне

claude -p "Скажи слово ГОТОВО і нічого більше" --output-format json

На екрані — довгий рядок JSON. Щоб дістати з нього лише відповідь, його треба передати конвеєром програмі, яка вміє читати JSON. Класичний вибір — jq, але вона за замовчуванням не встановлена. Тому спершу спробуй її: 

claude -p "Скажи слово ГОТОВО і нічого більше" --output-format json | jq -r '.result'

Якщо у відповідь прилетить command not found зі згадкою jq — це не поломка, а відсутня програма (повідомлення про пошук у PATH розбиралось у модулі 1). Її можна встановити, а можна обійтись тим, що вже є на будь-якому macOS і Linux: 

claude -p "Скажи слово ГОТОВО і нічого більше" --output-format json | python3 -c "import json,sys; print(json.load(sys.stdin)['result'])"

Обидва варіанти роблять одне: беруть з об'єкта поле result і друкують його без лапок.

Крок 5. Подати файл на вхід

Створи маленький файл із помилкою й попроси пояснити його, не називаючи шляху: 

echo "TypeError: cannot read property 'name' of undefined" > error.txt
cat error.txt | claude -p "поясни українською, що означає ця помилка і з чого почати пошук"

Claude Code отримав текст помилки стандартним вводом — жодного дозволу на читання файлів для цього не знадобилось. Це і є причина, з якої документація радить подавати різницю коду конвеєром, а не просити агента прочитати її самому.

Крок 6. Скрипт, який перевіряє код виходу

Створи файл check.sh і поклади в нього ось це. Назва латиницею й імена змінних латиницею — не примха: оболонка не приймає кириличних імен змінних і відповість command not found на першому ж рядку. 

#!/bin/bash
answer=$(claude -p "$1" --output-format json)
code=$?

if [ $code -ne 0 ]; then
  echo "Claude завершився з кодом $code" >&2
  exit $code
fi

echo "$answer" | python3 -c "import json,sys; print(json.load(sys.stdin)['result'])"

Запускається так: bash check.sh "склади список файлів у цій теці". Тут "$1" означає «перший аргумент, переданий скрипту», -ne 0 — «не дорівнює нулю», а >&2 відправляє повідомлення в потік помилок, щоб воно не змішалось із корисним виводом. Це кістяк будь-якої обгортки: спитати, перевірити число, і тільки потім користуватись відповіддю.

Крок 7 (необов'язковий). Якщо в тебе є репозиторій на GitHub

Відкрий у ньому звичайну інтерактивну сесію claude й набери /install-github-app. Знадобляться права адміністратора репозиторію й встановлений GitHub CLI (gh) з виконаним gh auth login — Claude Code перевірить його наявність і попередить, якщо не знайде. Далі — за підказками; наприкінці відкриється готовий пул-реквест із файлами робочих процесів. Поки він не злитий, нічого не змінюється.

5Як перевірити, що вийшло

У неінтерактивному режимі немає екрана, який показав би, що коїться. Тому питання «а чи спрацювало?» тут вирішується не враженням, а конкретними командами.

Чи завершилось успішно

echo $?

Нуль — так. Ненульове число — ні, і ось як його читати:

Що бачиш Що це означає
0 усе гаразд
1 і повідомлення до старту помилка в самих аргументах: невідомий прапорець, недопустиме значення, зламана схема
1 і повідомлення в звичайному виводі збій уже під час роботи. Класичний випадок — відсутня автентифікація
143 процес зупинили сигналом. У CI це майже завжди таймаут завдання

Чи не помилився агент усередині успішного запуску

Код виходу каже про запуск, а не про зміст. У форматі json є окреме поле: 

claude -p "твоє завдання" --output-format json | jq -r '.is_error'

Поруч варто дивитись на permission_denials: якщо масив не порожній, агенту щось заборонили, і зробив він менше, ніж ти просив.

Чи існує прапорець у твоїй збірці

Дві незалежні перевірки, обидві безкоштовні. Перша — запустити команду з цим прапорцем і подивитись на реакцію. Додавати до неї --help не можна: за наявності --help Claude Code глушить помилку про невідомий прапорець і друкує звичайну довідку, ніби прапорець існує. Ця пастка розібрана в модулі 17.

Друга — пошук по самій програмі, як у блоці 2: 

strings "$(which claude)" | grep -c -- "--назва-прапорця"
strings "$(which claude)" | grep -c -- "--вигадана-назва"

Перший рядок має дати число більше нуля, другий — нуль. Без другого рядка перевірка нічого не доводить: раптом вона завжди друкує нуль.

Чи не втягнув запуск чужі налаштування

Найпростіша відповідь: якщо ти написав --bare, не втягнув, бо цей режим із теки не читає нічого. Якщо не писав — подивись сам, що там лежить, перш ніж запускати: 

ls -la .claude
cat .mcp.json

Відповідь No such file or directory на обидві команди — добра новина: у репозиторії немає ні налаштувань із перехоплювачами подій, ні описів зовнішніх серверів.

Чого перевірка claude doctor тут не дасть

У модулі 17 показано, що claude doctor завершується кодом 0 навіть тоді, коли знайшов зламані налаштування. Як «ворота» в CI він непридатний: його код виходу не несе результату перевірки. Дивитись треба на текст, який він надрукував, а не на число після нього.

6Типові граблі

1. --bare плюс підписка дорівнює «не працює»

Найчастіша причина, чому приклад із документації не запускається в новачка. Bare-режим не читає ні збережений вхід за підпискою, ні системне сховище паролів — ніколи, і це не помилка, а задум. Треба або ключ API у змінній ANTHROPIC_API_KEY, або прибрати --bare.

Окремо: довгий токен, який видає команда claude setup-token (він діє рік і дозволяє автентифікацію підпискою в CI), bare-режим теж не читає — документація каже про це прямим текстом.

2. «У CI ж ізольовано» — ні

Без --bare запуск -p у склонованому репозиторії підтягне його .claude/ і його .mcp.json, не спитавши. Діалогу довіри в цьому режимі не існує. Чотири способи це закрити — у блоці 3; найкоротший з них --bare.

3. --continue як перевірка «чи є попередня розмова»

Здається логічним: запустити claude -p --continue, і якщо продовжувати нічого — отримати помилку. Насправді помилки не буде: у теці без жодної збереженої сесії запуск мовчки починає нову розмову й створює новий запис. Перевірено двічі, у двох порожніх теках, на 2.1.236.

Наслідок для скрипта: --continue не годиться як перевірка існування сесії. Якщо тобі потрібна саме конкретна розмова, збережи її ідентифікатор із поля session_id і продовжуй через --resume — тоді код виходу справді щось означатиме.

4. Фоновий сервер, запущений усередині запуску, помирає

Якщо агент під час роботи підняв щось у фоні — сервер розробки, спостерігач за файлами, — ця оболонка вбивається приблизно через п'ять секунд після того, як Claude Code віддав фінальну відповідь і ввід закрився. П'ять секунд — навмисна пауза, щоб задача, яка закінчується одразу після результату, встигла надрукувати своє.

Фонові субагенти й робочі процеси з цього правила виключені: їхній результат є частиною фінальної відповіді, тому claude -p на них чекає. Але й це очікування обмежене — за замовчуванням десять хвилин безперервного простою, щоб застряглий субагент не тримав процес вічно.

5. Обгортка, яка ковтає помилку

Класика: скрипт запускає claude -p, а далі перевіряє власне припущення — наприклад, чи з'явився файл — і сам вирішує, чим завершитись. Код виходу Claude Code при цьому не читається взагалі, і збій автентифікації виглядає так само, як успішна робота з порожнім результатом. Перевіряй число, як у кроці 6 попереднього блоку.

6. Таймаут у CI, який виглядає як загадковий збій

Завдання впало, у журналі — обрубаний вивід і код 143. Це не поломка Claude Code: 143 означає, що процес зупинили сигналом SIGTERM, а так робить саме CI, коли вичерпався ліміт часу. Лікується або збільшенням ліміту, або звуженням завдання, або прапорцем --max-turns, який обмежує кількість ходів.

Ще три, коротко

  • Прапорець --worktree в CI протікає. Неінтерактивний запуск із ним не прибирає за собою робочі копії й лишає замок git worktree lock. На сервері, який запускається сотні разів, це повільне заповнення диска. Він же пропускає перевірку довіри до теки, тоді як інтерактивний --worktree її не пропускає.
  • Сповіщення з перехоплювача подій у CI не працюють у принципі. Налаштування terminalSequence, яким хук подає сигнал термінала, у режимі -p і в Agent SDK ігнорується. Слухати нікому.
  • Хуки типу PermissionRequest у -p здебільшого не спрацьовують. Вони вимагають, щоб запуском керував Agent SDK із власним оброблювачем дозволів; у звичайному claude -p потрібен PreToolUse. А у фонових субагентів правило суворіше: якщо жоден хук не дав рішення, виклик відхиляється.

7Часті питання

Мені потрібен ключ API, щоб користуватись -p?

На своїй машині — ні. Звичайний claude -p користується тим самим входом, що й інтерактивна сесія, тобто твоєю підпискою. Ключ API стає потрібен у двох випадках: коли ти додаєш --bare, і коли запуск відбувається на чужій машині, де жодного входу немає.

Для другого випадку є проміжний варіант: команда claude setup-token видає токен на рік, який автентифікує саме твою підписку (потрібен план Pro, Max, Team або Enterprise). Токен ніде не зберігається — його друкують один раз, і його треба одразу покласти в змінну CLAUDE_CODE_OAUTH_TOKEN там, де він потрібен. Обмеження: він уміє лише робити запити до моделі, тому віддалені сесії й конектори claude.ai через нього не працюють. І, повторюючись, у --bare він не читається.

Чи можна виконати слеш-команду через -p?

Частково — і це дуже корисно знати. Навички й власні команди працюють: досить вписати /назва в текст завдання, і Claude Code розгорне її перед запуском. Кілька вбудованих команд приймають значення аргументом: /model sonnet, /effort, /fast, /color, /rename; /mcp без аргументів друкує текстовий підсумок стану серверів. Змінити налаштування можна через /config ключ=значення.

Що не працює: команди, які існують лише в терміналі, — наприклад /login. Автори сусідніх модулів цього курсу натрапили на ще дві межі на версії 2.1.236: /status і /hooks відповідають дослівним isn't available in this environment, а claude -p "/doctor" зависає — запуск довелось обірвати через дві хвилини.

Скільки коштує один такий запуск?

Стільки ж, скільки та сама робота в сесії, — плюс вартість стартового вантажу, який їде в контекст щоразу заново. У прикладі з блоку 2 на дволітерну відповідь пішло понад вісім тисяч токенів на створення кеша, і саме вони склали майже всю ціну.

Три способи це зменшити: --bare (не вантажить пам'ять, навички й плагіни), дешевша модель через --model, і менше ходів через --max-turns. Є ще прямий запобіжник — --max-budget-usd зі стелею витрат; він працює лише разом із -p, а витрати субагентів рахуються в ту саму стелю. Коли стеля вибрана, спроба породити субагента падає з повідомленням Budget limit reached. Потребує версії 2.1.217 або новішої. Докладно про гроші й ліміти — модуль 11.

Чим -p відрізняється від Agent SDK?

Формою, а не змістом. -p — це команда, яку викликає скрипт; SDK — це бібліотека, яку ти підключаєш до своєї програми на Python або TypeScript і керуєш агентом зсередини процесу. Якщо твоя мова не Python і не TypeScript, документація радить саме -p з --output-format json, запущений підпроцесом, — і це не обхідний шлях, а офіційна рекомендація.

А GitHub Actions, GitLab CI і Code Review — це три різні речі?

Так, і плутанина між ними коштує часу. GitHub Actions і GitLab CI — це твої робочі процеси на твоїй інфраструктурі: ти пишеш файл, ти обираєш події, ти платиш за хвилини роботи машин. Code Review — керований сервіс Anthropic для пул-реквестів на GitHub: свого файла робочого процесу не потрібно, але потрібен план Team або Enterprise. Локальна команда /code-review — четверта річ, вона працює в твоїй сесії й нічого нікуди не публікує, доки її не попросили.

Що станеться, якщо в чужому репозиторії лежить шкідливий хук?

У неінтерактивному запуску без захисту — він виконається, без питання й без повідомлення. Це найреальніший вектор атаки з усіх, названих у цьому курсі, і саме тому він проговорюється двічі: тут і в модулі 22, де розбирається безпека загалом. Правило одне: перш ніж запускати -p у чужому коді, подивись, що в його .claude/ — або запускай із --bare.

Чи працює це на Windows?

Так, з однією історичною поправкою, яку варто знати, якщо в тебе стара збірка: до версії 2.1.211 нечитабельний стандартний ввід на Windows валив сесію або змушував її мовчки завершитись без жодного виводу. У свіжих версіях Claude Code у такому випадку друкує попередження в потік помилок і продовжує роботу з тим завданням, яке передане в командному рядку.

8Підсумок і наступний крок

Головна зміна цього модуля — не новий прапорець, а зміна ролі. Досі Claude Code був співрозмовником, і всі рішення про безпеку ухвалювала людина, дивлячись на екран. У неінтерактивному режимі того, хто дивиться, немає. Тому все, що раніше вирішувалось натисканням «ні», тепер вирішується заздалегідь — прапорцями й налаштуваннями.

Підсумок модуля
  • claude -p "завдання" виконує роботу без діалогу, друкує відповідь у стандартний вивід і завершується кодом: 0 — успіх, ненульовий — збій, 143 — зупинено сигналом (у CI це майже завжди таймаут).
  • Три формати: text для людини, json для програми, stream-json для показу ходу роботи. У json лежать result, is_error, session_id, total_cost_usd — остання цифра є оцінкою, а не рахунком.
  • Неінтерактивний запуск читає теку, у якій стоїть: хуки, .mcp.json, CLAUDE.md — без діалогу довіри й без питань. --bare цього не робить і саме тому рекомендований для скриптів; ціна — потрібен ключ API.
  • Ввід можна подати конвеєром (обмеження 10 МБ), вивід — покласти у файл. Це і перетворює агента на звичайну команду поруч із git і npm.
  • У CI все те саме: GitHub Actions через anthropics/claude-code-action і /install-github-app, GitLab CI через звичайний крок скрипта. Ключі — тільки в секретах, ніколи у файлі робочого процесу.
  • Code Review — окремий керований сервіс для пул-реквестів (Team і Enterprise, research preview), налаштовується файлом REVIEW.md і не блокує злиття. Локальний аналог без нього — команда /code-review.
  • Agent SDK — той самий Claude Code як бібліотека для Python і TypeScript. З інших мов офіційна рекомендація — викликати -p підпроцесом.
  • Прапорець із документації може ще не існувати у твоїй збірці. Перевіряти — запуском без --help і пошуком strings із контрольною вигаданою назвою.

Наступний крок

Далі — модуль 20 «Коли Claude працює без тебе». Тут запуск завжди починався з твоєї дії: ти набрав команду, ти злив пул-реквест, ти поставив коментар. У наступному модулі зникає й це: завдання за розписанням, хмарні запуски без увімкненої машини, канали в месенджерах, які самі штовхають повідомлення в сесію, і віддалене керування. Там же — чесне порівняння трьох різних механізмів розписання, які легко сплутати між собою.

А до того варто зробити одну маленьку річ: узяти будь-яку рутинну перевірку у своєму проєкті — стиль коміт-повідомлень, друкарські помилки в документації, забуті TODO — і оформити її одним рядком у package.json або в крихітному скрипті. Автоматизація починається не з CI, а з першої команди, яку більше не треба набирати руками.

Квіз: перевір себе

Шість питань про те, що відбувається насправді, а не про назви прапорців. До кожної відповіді одразу з'являється пояснення, чому решта варіантів хибні.
