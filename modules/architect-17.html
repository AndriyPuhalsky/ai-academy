Деплой: робимо продукт живим

Продакшн · 8 уроків · ≈ 90 хв

Твій бекенд працює — але лише на твоєму комп'ютері. Якщо вимкнути термінал, усе зникає. У цьому модулі ми задеплоїмо продукт: розмістимо його в інтернеті, щоб він мав постійну адресу й працював 24/7, навіть коли твій комп'ютер вимкнено. Підемо крок за кроком, з перевірками.

Чесно про інтерфейси хостингів. Кнопки й назви на платформах деплою час від часу змінюються. Тому я даю стабільну послідовність дій і принципи, а точні кроки під конкретну платформу завжди звіряй у її офіційній документації. Це нормальна щоденна практика інженера — і Claude Code теж допоможе з налаштуванням деплою, якщо попросиш.

17.1Що таке деплой

Деплой (deployment) — це розміщення твого коду на сервері в інтернеті, щоб він працював постійно й мав публічну адресу (URL), за якою до нього може звернутися будь-хто.

Аналогія. Локальний запуск (uvicorn на твоєму комп'ютері) — це ресторан у тебе вдома: відчинений, лише поки ти там, і адреси ні в кого немає. Деплой — це відкрити ресторан у місті з вивіскою й адресою: він працює цілодобово, і гості приходять самі, навіть коли тебе немає.

Що дає жива адреса:

  • Доступ для інших: клієнт, колега чи замовник відкриває URL — і користується.
  • Робота 24/7: сервіс живе незалежно від твого комп'ютера.
  • Портфоліо: жива демка, яку можна показати роботодавцю чи клієнту, — сильніша за код у репозиторії.

17.2Що потрібно перед деплоєм

Деплой пройде гладко, якщо підготувати чотири речі (усі ти вже вмієш):

  • Код на GitHub. Платформи деплою беруть код прямо з твого репозиторію (Модуль 5). Переконайся, що main.py та index.html запушені.
  • requirements.txt — список бібліотек (Модуль 16), щоб сервер знав, що встановити. Має містити: fastapi, uvicorn, anthropic, python-dotenv.
  • Команда запуску — як сервер має стартувати твій бекенд (розберемо в 17.4).
  • План для ключа. Ключ НЕ їде в Git (Модуль 7) — на хості його задають окремо, як змінну оточення (урок 17.6).

Найважливіше нагадування. Перевір, що .env у .gitignore і його немає на GitHub (Модуль 7). Ключ ми додамо на хост окремо й безпечно. Якщо ключ колись потрапив у Git — відклич його в консолі й створи новий.

17.3Як працює хостинг (концепція)

Сучасні платформи деплою роблять усе майже автоматично. Загальна схема однакова майже всюди: 

flowchart LR
  GH[("GitHub
(твій код)")] --> P["Платформа хостингу"]
  P --> B["Будує:
ставить requirements"]
  B --> R["Запускає:
команда старту"]
  R --> URL["Жива адреса
(публічний URL)"]
  class URL hl

Платформа бере код із GitHub, ставить бібліотеки, запускає бекенд і дає URL

Тобто: ти під'єднуєш свій GitHub-репозиторій → платформа сама завантажує код, встановлює бібліотеки з requirements.txt, запускає твою команду старту — і видає публічну адресу. Після цього кожен git push зазвичай автоматично оновлює живий сервіс.

Приклади платформ. Для Python-бекенду популярні, зокрема, Render, Railway, Fly.io (є й інші). Багато з них мають безкоштовний або дешевий стартовий тариф, якого вистачить для навчання й демо. Обери одну й далі дій за нашою послідовністю + її актуальними доксами — принцип скрізь однаковий.

17.4Готуємо бекенд до деплою

На сервері запуск трохи відрізняється від локального. Команда старту для FastAPI на більшості платформ виглядає так: 

uvicorn main:app --host 0.0.0.0 --port $PORT

Розбір. --host 0.0.0.0 каже серверу «приймай запити ззовні» (на твоєму комп'ютері цього не треба, а на хості — обов'язково). $PORT — це змінна оточення: платформа сама призначає порт і передає його через неї, а ми просто підставляємо. Локально ми писали фіксований порт, тут — динамічний від хоста.

Цю команду ти або вкажеш у налаштуваннях платформи (поле «Start Command»), або покладеш у спеціальний файл (наприклад, Procfile чи конфіг платформи — залежить від неї, дивись її докси). А requirements.txt має лежати в корені репозиторію: 

# requirements.txt
fastapi
uvicorn
anthropic
python-dotenv

Підказка. Не пам'ятаєш точний вміст requirements.txt чи який конфіг-файл потрібен платформі? Попроси Claude Code: «підготуй мій FastAPI-проєкт до деплою на [назва платформи]» — він згенерує потрібні файли й команду старту й пояснить кроки.

17.5Деплоїмо крок за кроком

Послідовність на типовій платформі (точні назви кнопок звіряй у її доксах, але кроки ті самі):

  1. Зареєструйся на обраній платформі (зазвичай можна увійти через GitHub).
  2. Натисни щось на кшталт «New» → «Web Service» (новий вебсервіс).
  3. Під'єднай свій GitHub-репозиторій із проєктом.
  4. Платформа спитає налаштування. Вкажи:
    • Build Command (як ставити залежності): pip install -r requirements.txt;
    • Start Command (як запускати): uvicorn main:app --host 0.0.0.0 --port $PORT.
  5. Додай змінну оточення з ключем (наступний урок) — до першого запуску.
  6. Натисни «Deploy» (запустити деплой) і дочекайся завершення збірки.

Що ти маєш побачити. Платформа покаже журнал збірки (рядки про встановлення бібліотек), потім — повідомлення про успіх (наприклад, «Live» / «Deploy succeeded») і публічну адресу виду https://твій-сервіс.onrender.com (домен залежить від платформи). Це і є жива адреса твого бекенду.

17.6Змінні оточення на хості (ключ)

Найважливіший крок із погляду безпеки. Локально ключ лежав у .env. На сервері файлу .env немає (і не має бути!) — натомість платформа дає розділ Environment Variables (змінні оточення), куди ти безпечно вписуєш ключ.

  1. У налаштуваннях сервісу знайди розділ «Environment» / «Environment Variables».
  2. Додай змінну: ім'я ANTHROPIC_API_KEY, значення — твій справжній ключ.
  3. Збережи й перезапусти сервіс, якщо потрібно.

Чому код міняти не треба. Згадай Модуль 7: ми читаємо ключ через os.getenv("ANTHROPIC_API_KEY"). Ця команда бере значення зі змінних оточення — байдуже, чи вони з локального .env, чи задані на хості. Тому той самий код працює і локально, і в проді. Це й була причина від початку не вписувати ключ у код.

Критично. Ключ задається лише в цьому розділі платформи. Ніколи не клади його в код, не коміть у Git і не показуй у фронтенді (Модуль 16). Якщо ключ десь «засвітився» — відклич його в консолі Anthropic і створи новий.

17.7Перевіряємо живий продукт і фронтенд

Відкрий свою живу адресу з доданим /docs (наприклад, https://твій-сервіс.onrender.com/docs) і протестуй ендпоінт /ask, як робив локально (Модуль 16).

Що ти маєш побачити. Та сама сторінка документації, що й локально, але вже за публічною адресою. Виклик /ask повертає відповідь моделі. Вітаю — твій AI живе в інтернеті 24/7! Поділись адресою з другом — він зможе відкрити її зі свого пристрою.

Тепер під'єднаємо фронтенд. У файлі index.html заміни локальну адресу бекенду на живу:

// було (локально):
const res = await fetch("http://127.0.0.1:8000/ask", { ... });

// стане (жива адреса твого бекенду):
const res = await fetch("https://твій-сервіс.onrender.com/ask", { ... });

Фронтенд (статичний index.html) можна розмістити двома шляхами:

  • На статичному хостингу (наприклад, Netlify, Vercel, GitHub Pages) — просто для HTML-сторінок, часто безкоштовно.
  • Прямо з бекенду — щоб був один деплой. FastAPI вміє віддавати статичні файли:
from fastapi.staticfiles import StaticFiles
# після оголошення ендпоінтів:
app.mount("/", StaticFiles(directory="static", html=True), name="static")
# поклади index.html у папку static/ — і бекенд віддаватиме його на головній адресі

Не забудь про CORS. Якщо фронтенд на окремому домені, додай його в дозволені у CORSMiddleware замість "*" (Модуль 16) — у проді це безпечніше, ніж «дозволити всім».

17.8Вартість, «сон», домен і налагодження

  • Безкоштовні тарифи «засинають». Багато платформ на free-тарифі присипляють сервіс після простою — перший запит після паузи буде повільним (сервіс «прокидається»). Для демо це ок; для бойового продукту беруть платний тариф, що не засинає.
  • Дві статті витрат. Не плутай: окремо платиш платформі за хостинг (за тариф) і окремо Anthropic за виклики моделі (за токени, Модуль 8). Слідкуй за обома.
  • Власний домен. Замість ...onrender.com можна під'єднати свій домен (наприклад, myapp.com) у налаштуваннях платформи — для солідного вигляду.
  • Логи деплою — твій друг. Якщо сервіс не стартував, відкрий журнал (Logs) на платформі: там видно причину (немає бібліотеки, помилка в команді старту, відсутній ключ).

Типові помилки деплою. «Build failed» — частіше неповний requirements.txt (додай бракуючу бібліотеку). Сервіс стартував, але /ask повертає помилку ключа — не додав ANTHROPIC_API_KEY у змінні оточення (урок 17.6). Фронтенд не отримує відповідь — перевір, що оновив адресу у fetch і налаштував CORS. Лог платформи майже завжди підкаже, що саме не так.

Підсумок модуля. Ти задеплоїв бекенд із GitHub на хостинг, безпечно задав ключ через змінні оточення, перевірив живий ендпоінт, під'єднав фронтенд і знаєш про вартість, «сон», домен і де шукати причини збоїв. Твій AI-продукт тепер справді живий в інтернеті — це величезна віха. Наступний модуль — LLMOps: як тримати живий продукт під контролем (вартість, логи, версії промптів, надійність).
