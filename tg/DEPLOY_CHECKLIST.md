# Чеклист розгортання: Supabase, файли, smoke-тест

Доповнення до `GOING_LIVE.md` (той — про хостинг, домен і авто-деплой Cloudflare).
Цей — про **базу, Edge Functions і перевірку, що все справді працює**.

Написано 2026-09-06 (задача 006). Усі факти нижче звірені з живою базою через
Supabase MCP і з `CHANGELOG.md` того ж дня, а не відтворені з пам'яті.

> **Секретів у цьому файлі немає й не повинно бути.** Репозиторій публічний:
> тут лише **назви** змінних оточення. Значення живуть у Supabase → Edge Functions
> → Secrets і в менеджері паролів власника.

## 1. Що це і чим відрізняється від `GOING_LIVE.md`

| Питання | Де відповідь |

| Як підняти хостинг, купити домен, під'єднати авто-деплой | `GOING_LIVE.md` |

## 4. Порядок для чистої бази

> ### Чесно про діру в цьому пункті
>
> **Базової схеми в репозиторії немає жодним файлом.** Таблиці `courses`, `modules`,
> `profiles`, `progress`, `quiz_attempts`, `certificates`, `enrollments`, `payments`,
> їхні RLS-політики, гранти й функції (`submit_quiz`, `maybe_issue_certificate`,
> `verify_certificate`, `uncomplete_module`, `module_unlocked`, `is_admin`,
> `handle_new_user`, `notify_new_profile`, `admin_user_report`) створювались у
> Dashboard **поза гітом**, на самому початку проєкту. Ті `схема → rebuild →
> certificate_progress → telegram`, на які посилається `GOING_LIVE.md`, у
> репозиторії теж відсутні.
>
> **Наслідок:** підняти проєкт «з нуля» лише за файлами репозиторію **неможливо**.
> Міграції з таблиці вище — це правки поверх схеми, якої в гіті немає.
>
> **Що з цим робити (окрема задача, не робилось):** зняти дамп схеми з живої бази —
> `supabase db dump --schema public -f supabase/schemas/000-baseline.sql` (лише
> структура, **без даних учнів**) — і покласти в репозиторій як базовий файл.
> До того моменту єдина повна копія схеми існує в одному екземплярі: у проді.

Поки базового файла немає, порядок для чистої бази такий:

1. [ ] Створити схему **вручну** за станом живого проєкту (див. попередження вище).
2. [ ] `tg/contact_messages.sql` — таблиця форми звернень.
3. [ ] `002-lock-profiles-role.sql` — права на `profiles`.
4. [ ] `005-1-course-ai-terminal.sql`, далі `005-2-module-titles.sql`.
5. [ ] Наповнити `courses` і `modules` рештою курсів. **Коди модулів мають бути
       глобально унікальними**: `js/auth.js` будує `AIA_MODULE_MAP` запитом
       `select id, code` **без фільтра за курсом**, тож збіг коду в різних курсах
       мовчки затер би чужий модуль. База такий збіг дозволяє — обмеження там
       `UNIQUE(course_id, code)`, не глобальне.
6. [ ] Перевірити тригери: `auth.users → on_auth_user_created` (створює профіль) і

       доступна всім: обидва стани погані.

**Контрольний стан живої бази на 2026-09-06** (з чим звіряти результат):

## 5. Edge Functions

Дві функції, обидві деплояться **окремо** (Supabase CLI або вебредактор Dashboard),
**не** через `git push` сайту.

| Функція | Файл у репозиторії | Що робить |
| --- | --- | --- |
| `telegram` | `tg/telegram_index.ts` | Адмін-бот (`/stats`, `/export`, `/messages`, кнопки) + приймає Database Webhook на вставку в `profiles` і шле адміну сповіщення про реєстрацію. |
| `contact` | `tg/contact_index.ts` | Приймає форму «Написати нам», пише в `contact_messages`, шле адміну; опційно перевіряє Cloudflare Turnstile. |

Розкладка для CLI: `supabase/functions/telegram/index.ts` і
`supabase/functions/contact/index.ts`.

- [ ] Задеплоїти обидві функції.
- [ ] **Секрети — тільки назви, значення вписати в Dashboard:**
      `TELEGRAM_BOT_TOKEN`, `ADMIN_CHAT_ID`, `WEBHOOK_SECRET`,
      `TELEGRAM_SECRET_TOKEN`, `TURNSTILE_SECRET_KEY` (опційно).
      `SUPABASE_URL` і `SUPABASE_SERVICE_ROLE_KEY` середовище Edge Functions
      підставляє саме — вручну їх не додавати.
- [ ] Прописати вебхук бота **з секретним токеном** (без нього ендпоїнт відкритий
      будь-кому, хто знає адресу):
      `setWebhook` з параметрами `url` = адреса функції `telegram` і
      `secret_token` = значення `TELEGRAM_SECRET_TOKEN`.

- [ ] Database Webhook на `insert` у `public.profiles` → функція `telegram`,

> Функція перевіряє секретний токен на вході. Не прибирати цю перевірку й не

## 6. Smoke-сценарій

Порядок фіксований: кожен крок — один перевірюваний факт. Проходити на живій
адресі, не на localhost.

1. [ ] **Вхід.** Зареєструватись/увійти один раз — вхід спільний для всіх курсів.
2. [ ] **Прогрес видно.** `/`, `/architect`, `/claude-code` показують пілюлю
       прогресу в шапці (гостю її не видно взагалі).
3. [ ] **Квіз.** Пройти один модуль до кінця — прогрес збільшився на всіх трьох
       лендінгах, наступний модуль розблокувався. Порядок проходження перевіряє
       **сервер** (RPC `submit_quiz`); блокування на клієнті — лише UX.
4. [ ] **Сертифікат.** Після останнього модуля курсу сертифікат з'являється на
       `/certificate` сам. Завантажити PDF: два аркуші, кирилиця не «пливе»,
       QR читається, підпис видавця й медальйон називають **той курс**, який
       пройдено, а посилання «До програми курсу →» веде на його лендінг.
5. [ ] **Перевірка коду.** `/verify` за кодом із сертифіката — картка «дійсний»
       з іменем і назвою курсу. Той самий код із кириличними `а/с/е` або
       у ВЕРХНЬОМУ регістрі теж має знаходитись (нормалізація на клієнті).
6. [ ] **Бот.** `/stats` у Telegram відповідає числами; `/messages` показує
       звернення з форми.
7. [ ] **Сповіщення про реєстрацію.** Нова реєстрація → адмін отримує
       повідомлення (тобто працює зв'язка тригер → Database Webhook → функція).

> **Пастка перевірки:** адреси з `.html` віддають **307**, а не 200 — перевіряти
> `/roadmap`, а не `/roadmap.html`.
>
> **Друга пастка:** окремої dev-бази немає. Превʼю-деплой пише в **ту саму
> продову базу**, тож кроки 1, 3 і 4 створюють справжні рядки й справжній
> сертифікат із публічним кодом. Слід тестового акаунта прибирається окремо
> (зразок — `005-4-cleanup-qa-account.sql`).

## 7. Відкат

| Крок не пройшов | Що робити |
| --- | --- |
| Міграція | Виконати блок `ВІДКАТ` **із самого файла міграції** — він там обов'язковий. Якщо відкат у файлі позначений як неможливий (напр. видалення даних), не застосовувати міграцію, поки не буде резервної копії. |
| Edge Function | Передеплоїти попередню версію з git-історії того ж файла. Секрети при передеплої не змінюються. |
| Вебхук бота | Повторно викликати `setWebhook` із правильними `url` і `secret_token`; `deleteWebhook` вимикає бота повністю. |
| Сайт | Cloudflare → попередній deploy. Код відкочується `git revert`, **не** `push --force`. |
| Виданий сертифікат | Рядок у `certificates` **не видаляється клієнтом**: політики DELETE немає. Потрібна окрема міграція із запобіжником (зразок — `005-3-cleanup-qa-certificate.sql`). |

Правило, яке дорожче за зручність: **`main` = прод**. Будь-яка правка спершу йде
на `dev`, а в `main` — лише після прямого «так» власника, мержем `--no-ff`
(fast-forward дає `main` той самий SHA, і Cloudflare не збирає новий білд).
