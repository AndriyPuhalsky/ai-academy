# AIA Build — інженерна майстерня

Робоча папка для **реалізації** задач AI Академії / AI Architect: планування, бекенд,
фронтенд, тестування. Дизайн вирішується не тут, а в сусідній `dev/design/`; тут макет
перетворюється на робочий код на гілці `dev`.

Різниця між двома майстернями в одному рядку: **`design/` малює і нічого не чіпає,
`build/` чіпає реальний код і нічого не малює.**

## ПРАВИЛО №1 (тверде, без винятків): `main` — це прод із живими користувачами

- **Жоден агент цієї майстерні не має права на `git push origin main`, `git merge` у `main`,
  `git checkout main` з наміром щось там правити.** Не «краще не треба» — заборонено.
- Уся робота — на гілці `dev`. Мерджить у `main` тільки власник, після прямого «так»
  у діалозі. Це правило **не скасовується** автономним/auto-режимом: так вимагає кореневий
  `CLAUDE.md`, і власник прямо це підкреслив.
- Перед будь-якою правкою: `git rev-parse --abbrev-ref HEAD`. Якщо це не `dev` — зупинитись
  і сказати про це, а не «швиденько перемкнути».
- Причина: у Cloudflare Workers `main` = автодеплой у прод за ~хвилину. У проді живі учні,
  видані сертифікати й робочий вхід. Помилка на `dev` коштує rebuild-у превʼю; помилка
  в `main` — репутації курсу.

## ПРАВИЛО №2 (тверде): зони запису — у кожного агента своя

Ця майстерня **не пісочниця**: агенти правлять справжній код сайту. Саме тому межі мають
бути вужчі за «увесь репозиторій», інакше четверо агентів затруть роботу один одного.

| Агент | Пише | Тільки читає |
| ----- | ---- | ------------ |
| `aia-build-pm` | `dev/build/NNN-slug/01-plan.md`, `README.md` (індекс), `JOURNAL.md` | увесь код — план пишеться з коду, а не навпаки |
| `aia-build-backend` | `tg/telegram_index.ts`, `tg/CHANGELOG.md`, `js/auth.js`, `js/progress.js`, `js/module.js`, `js/certificate.js`, `js/verify.js`, `dev/build/NNN-slug/02-backend/` | HTML, `css/`, `wrangler.toml`, `.assetsignore`, `.gitignore` |
| `aia-build-frontend` | HTML у корені й `modules/`, `css/*.css` (`tokens`, `components`, `claude-code`, `roadmap`), `config.json`, `architect.config.json`, JS-код інтеракцій, `dev/build/NNN-slug/03-frontend/` | `tg/`, схема Supabase, `wrangler.toml`, `.assetsignore` |

**Поза зоною для всіх чотирьох, без винятків:**
- `wrangler.toml`, `.assetsignore`, `.gitignore` — один рядок тут вирішує, що деплоїться
  і що видно з інтернету. Зміни — через власника.
- `dev/design/` — це чужа майстерня, її веде сесія `design_1`. Читаємо звідти скільки треба,
  не пишемо нічого.
- `~/.claude/` — глобальні агенти, скіли, налаштування.
- `dev/*.local.md` — приватні документи власника.
- `deploy-guide.local.html` — людський runbook власника, не документація коду.

Якщо задача справді вимагає вийти за свою зону — агент **не робить цього сам**: описує
у своєму звіті, що і де треба змінити, і віддає далі. Сусідній агент або власник зробить.

## ПРАВИЛО №3 (тверде): репозиторій ПУБЛІЧНИЙ — усе, що тут написано, побачить світ

- `dev/build/` версіонується в гіті (кореневий `.gitignore`: `dev/*` + `!dev/design/` +
  `!dev/build/`), а `github.com/AndriyPuhalsky/ai-academy` — **публічний**.
- **Історія гіта не забуває.** Видалити файл пізніше ≠ прибрати його з репозиторію: він
  лишається в старих комітах назавжди. Тому фільтр стоїть на вході, а не на виході.
- Для цієї майстерні правило гостріше, ніж для дизайну, бо бекенд працює саме з чутливим.
  **Ніколи не класти сюди:**
  - ключі й токени: `SUPABASE_SERVICE_ROLE_KEY`, `TELEGRAM_BOT_TOKEN`,
    `TELEGRAM_SECRET_TOKEN`, будь-який JWT, connection string з паролем. `anon`-ключ теж
    не переносити «для зручності» — він і так є в `config.json`, дублювати нема потреби;
  - **реальні дані учнів**: рядки з `profiles`, `certificates`, `progress`, email, імена,
    коди сертифікатів. У прикладах SQL і в звітах QA — тільки вигадані значення;
  - вивід `SELECT *` із живих таблиць. Потрібно показати структуру — показувати схему
    (назви й типи колонок), а не рядки;
  - фінанси, платіжні реквізити, чернетки цін, невидані комерційні плани.
- **Нормально класти:** плани, SQL-міграції (DDL без даних), назви таблиць і колонок,
  політики RLS, звіти тестування, скріншоти публічних сторінок, номери задач.
- Сумнівно — **не публікувати і спитати власника**. Ціна помилки асиметрична: зайве
  питання коштує хвилину, злитий `service_role` — ротації всіх ключів і, можливо,
  скомпрометованої бази.
- Окремо від гіта: кореневий `.assetsignore` виключає `dev/` з роздавання Cloudflare
  Workers, тому ці файли не висять на домені. Перевірено на dev-превʼю (`/dev/design/CLAUDE.md`
  → 404). Файл веде коренева сесія — не чіпати.

## ПРАВИЛО №4: git — що можна і чого не можна

Дозволено (це рішення власника 2026-08-23, свідоме):
- `git add` / `git commit` — по своїй зоні, атомарними комітами;
- `git push origin dev` — щоб Cloudflare підняв Preview і тестувальник мав що перевіряти;
- `git status`, `git diff`, `git log`, `git branch` — скільки треба.

Заборонено:
- будь-що з `main` (див. правило №1);
- `git push --force`, `git reset --hard` на спільній гілці, `git rebase` вже запушеного;
- `git commit` чужих незакомічених змін «до купи». Побачив у `git status` чуже — показати
  власнику й спитати, а не вирішувати самому. Репозиторій = те, що деплоїться;
- комітити `node_modules`, дампи бази, скріншоти з персональними даними.

### ⚠ Кілька агентів в одному дереві: комітити ТІЛЬКИ через `git commit -- <шляхи>`

Заведено 2026-09-07 після задачі 010, де це коштувало зіпсованої історії.

**Заборони `git add -A` НЕДОСТАТНЬО.** Індекс git один на все робоче дерево, і `git commit`
без pathspec бере **весь індекс** — включно з тим, що туди поклав інший агент секунду тому.
У 010 троє фронтендерів працювали паралельно; коміт етапу 6 захопив **62 файли замість
трьох** — усі 57 уроків і два `js/` сусіда, який саме зробив `git add` своєї зони.

```bash
git commit -- modules/ js/module.js js/quiz.js -m "010 feat: …"   # ✅ бере рівно ці шляхи
git add modules/ js/module.js js/quiz.js && git commit -m "…"      # ❌ бере весь індекс
```

Ознака, що це сталося з тобою **з іншого боку**: твій `git add` пройшов, а `git commit`
каже **«nothing to commit, working tree clean»** — значить, сусід уже забрав твої файли
у свій коміт.

**Що робити, побачивши це:** **нічого не переписувати.** `git reset --soft` і `--amend` на
спільній гілці, поки сусіди можуть комітити в ту саму секунду, ризикують втратити чужий
коміт. Вміст дерева при цьому правильний — зіпсоване лише повідомлення. Описати у звіті
й віддати рішення кореневій сесії, у якої є повна картина. У 010 обидва агенти вчинили
саме так, і це було правильно.

**Решта дисципліни паралельної роботи** (перевірено на 010, тримається):
- спільні файли (`css/tokens.css`, `css/components.css`, `js/motion.js`, `js/tw-theme.js`)
  — **тільки читання** для всіх, хто працює паралельно. Потрібне правило → готовий CSS
  у звіт, застосовує коренева сесія. Інакше троє агентів перезаписують файл один одному
  **мовчки**;
- `git push` робить **коренева сесія після всієї хвилі**, не агенти — інакше гонка на
  віддаленій гілці;
- `index.lock` зайнятий = сусід комітить у цю секунду. Зачекати й повторити, **не видаляти
  lock руками**;
- свій порт для `http.server` кожному (8301 / 8302 / 8303), інакше сервери бʼються за один.

**Формат коміта:** `NNN feat|fix|db|qa: що зроблено` — щоб з `git log` було видно, до якої
задачі належить зміна. Приклад: `001 feat: вхід через Google у модалці авторизації`.

## ПРАВИЛО №6 (тверде): кожен агент пише звіт `.md` файлом — і ім'я файла НЕ починається з `report`

Слово власника 2026-10-02: «кожен агент має писати в кінці звіт у форматі md, і харнес не має
це блокувати». Повторював десятки разів, тому правило тверде.

**Причина блоку (знайдено в коді Claude Code 2.1.287, 2026-10-02) — одна-єдина:** інструмент
`Write` для **підагента** відхиляє файл, чиє **ім'я** (не шлях) відповідає
`^(REPORT|SUMMARY|FINDINGS|ANALYSIS).*\.md$` без урахування регістру, з текстом
«Subagents should return findings as text, not write report files». Перевірка вшита в код і
стоїть **до** дозволів, тому жодне allow-правило в `settings*.json` її не знімає — саме тому
всі попередні «виправлення дозволами» не працювали. На `Edit`, на коренову сесію й на імена
на кшталт `review-j01.md`, `cross-findings.md`, `01-plan.md` вона не діє.

**Тому імена звітів агентів — з префіксом ролі:**

| Агент | Файл звіту | Наступні кола |
| --- | --- | --- |
| `aia-build-backend` | `02-backend/backend-report.md` | `backend-report-round2.md` |
| `aia-build-frontend` | `03-frontend/frontend-report.md` | `frontend-report-round2.md` |
| `aia-build-qa` | `04-qa/qa-report.md` | `qa-report-round2.md` |
| `aia-build-pm` | `01-plan.md` (як і було) | — |
| `aia-content-reviewer` | `review-<урок>.md` (як і було) | — |

- **Заборонені перші слова імені файла `.md` для будь-якого агента:** `report`, `summary`,
  `findings`, `analysis` (у будь-якому регістрі, з будь-яким продовженням: `report-wave2.md`,
  `Summary.md`, `findings.md` — усі блокуються). `SUMMARY.md` задачі пише лише коренева сесія.
- Звіт створюється **інструментом `Write`** — не heredoc (у worktree його відхиляє сторож
  ізоляції), не python. Фінальне повідомлення агента — короткий підсумок + шлях до файла.
- У брифі агента коренева сесія **щоразу пише повний шлях файла звіту** з цим ім'ям: визначення
  агентів підхоплюються на старті сесії, тож бриф — найнадійніший вхід.
- Старі файли `report.md` у задачах до 015 не перейменовуються — на них стоять посилання в
  індексі й журналі; правило діє для всього нового.
- Якщо `Write` усе одно відмовив — агент не шукає обхідних шляхів, а дає повний текст звіту
  фінальним повідомленням і точний текст відмови; коренева сесія записує файл сама й розбирає
  причину (новий блок харнеса = нове правило тут).
- Після оновлення Claude Code перевірити, чи правило не змінилось:
  `strings -n 30 ~/.local/bin/claude | grep -c "subagent_md_report_blocked"` і сам регулярний
  вираз поруч.

## Конвеєр: PM → (бекенд ∥ фронтенд) → QA → цикл фіксів

На відміну від дизайн-конвеєра, цей **не лінійний** — бо розробка не лінійна.

```
        ┌────────────────┐
        │ aia-build-pm   │  план, контракт даних, нарізка, критерії
        └───────┬────────┘
                │
        ┌───────┴────────┐
        ▼                ▼
┌───────────────┐  ┌────────────────┐   паралельно: бекенд не чекає макет,
│ build-backend │  │ build-frontend │   фронтенд не чекає базу — обидва
└───────┬───────┘  └────────┬───────┘   тримаються контракту від PM
        └───────┬───────────┘
                ▼
        ┌────────────────┐
        │  aia-build-qa  │  перевірка на dev-превʼю
        └───────┬────────┘
                │ дефекти → назад до відповідного агента
                │ (максимум 3 кола, потім — до власника)
                ▼
            SUMMARY.md → рішення власника про merge у main
```

**Чому паралельно.** Бекенд-частина (схема, RLS, RPC, Edge Function) від вигляду не
залежить — це прямо зафіксовано в кореневому `CLAUDE.md`: «що від дизайну не залежить,
робити паралельно, макет не чекати». Тримає їх разом **контракт даних** з `01-plan.md`:
які поля, які типи, які помилки, які стани. Якщо контракту немає — PM не закінчив роботу.

**Чому цикл, а не одноразова перевірка.** Тестувальник не «підтверджує» — він ламає.
Знайдені дефекти повертаються авторові, автор лагодить, QA перевіряє ще раз. Ліміт —
**3 кола**: якщо після третього дефекти лишаються, це вже не баг, а неправильно
поставлена задача — виносити до власника, а не крутити цикл далі.

**Ліміт відповідальності QA.** Тестувальник **не правит код**. Він пише
`04-qa/report.md` із доказами (крок → очікувано → фактично → скріншот). Причина: агент,
який і тестує, і лагодить, завжди схильний визнати свій фікс успішним.

## Вхід задачі: коротке ТЗ + `SUMMARY.md` з дизайну

Власник дає **2–5 рядків** ТЗ (або каже голосом) — PM-агент сам розгортає це в план,
читаючи код. На відміну від дизайну, тут детальний бриф не потрібен: деталі виводяться
з коду, а не з голови власника.

Якщо задача змінює те, що бачить користувач, вхід **обов'язково** включає
`dev/design/NNN-slug/SUMMARY.md` і обраний варіант із `04-variants/`. Немає макета, а
вигляд змінюється → **стоп**, спершу бриф у дизайн-майстерню. Фронтендер тут — столяр,
не дизайнер (див. його визначення).

Коли дизайн не потрібен (багфікс без зміни вигляду, бекенд, контент у конфігах,
рефакторинг) — задача заводиться прямо тут, без `design/`. Повний перелік критеріїв —
у кореневому `CLAUDE.md`, розділ «перед кожною новою задачею — перевірити, чи потрібен
дизайн».

### Окремої dev-бази НЕМА — і це свідоме рішення (2026-08-23)

Питання розглядалось і закрите: **одна база на все**, вона ж прод.

- Supabase-бранчинг перевірено: доступний **лише від плану Pro ($25/міс)** плюс
  **$0.01344 за бранч на годину** (≈$9.8/міс, якщо тримати постійно) → ≈$35/міс. На
  поточному Free-плані кнопка `Create branch` є, але впирається в апгрейд.
- Безкоштовна альтернатива (другий проєкт — Free дає 2 активні на організацію) власником
  **свідомо відхилена**.
- Бранч усе одно приходить **без даних** (синхронізується лише схема), тож сідинг довелось
  би писати в обох варіантах.

**Два наслідки, які визначають роботу конвеєра. Обидва — не деталі.**

**Наслідок 1: MCP дивиться в ПРОД.** Немає «пісочниці, де можна спробувати». Кожен
читальний запит іде в живу базу; кожна помилкова зміна — незворотна. Саме тому правило
«зміни тільки файлами» тут не бюрократія, а єдиний захист.

**Наслідок 2: dev-превʼю теж працює з продовою базою.** У `config.json` один
жорстко прописаний `supabase.url` (проєкт `hpcyrnxschpxlrxudmqk`), а в `js/auth.js` немає
вибору середовища за хостом. Тобто реєстрація на
`dev-ai-academy.andriy-puhalsky.workers.dev` створює **справжній рядок у продових
`profiles`**, проходження квізу — справжній `quiz_attempts`, а видача сертифіката —
справжній публічний код верифікації. Ізоляція середовищ у цьому проєкті є на рівні
хостингу, але **не на рівні даних**.

Тому тестувальник має жорстке обмеження на тести, що пишуть у базу (див. його визначення),
а не звичайне «тестуй на превʼю і все».

### Якщо колись вирішимо зробити dev-базу

Щоб не переоткривати: найдешевший шлях — **другий безкоштовний проєкт** (не бранч), а вибір
бази — **один `config.json` із двома блоками** (`supabase.prod` / `supabase.dev`) і вибором
у `js/auth.js` за `location.hostname` (`workers.dev` або `localhost` → dev). Один файл на
обох гілках = нуль конфліктів при мержі; anon-ключі й так публічні за дизайном, захищає RLS.
Окремо доведеться налаштувати Google OAuth на другому проєкті (свій redirect URL у Google
Cloud) — це не безкоштовно за часом, тому й не робимо зараз.

### Межа доступу

- **Читати через MCP — вільно й обов'язково.** Схема, політики RLS, advisors, логи, стан
  Edge Functions, документація. Гадати про схему заборонено: якщо не подивився — не пиши.
- **Змінювати базу напряму — ні.** Будь-яка DDL, зміна RLS, нова RPC, індекс, тригер: агент
  пише SQL-файл у `NNN-slug/02-backend/db/` з іменем `NNN-<порядок>-<що-робить>.sql`, до
  нього — блок відкату, і виносить у звіт. Застосовує власник (Dashboard або CLI).
- **Ніколи не виконувати `apply_migration`, `execute_sql` з DDL, `drop`, `truncate`,
  `delete` без `where`** — навіть якщо MCP це технічно дозволяє.
- **Після кожної застосованої міграції — запис у `tg/CHANGELOG.md`.** Це вимога кореневого
  `CLAUDE.md`. Так само для деплою Edge Function і зміни секретів.
- **Ніякого `service_role`-ключа** ні в коді, ні в цій папці, ні у звітах.

### Стан MCP

Сервер прописаний у кореневому `.mcp.json`: `https://mcp.supabase.com/mcp`,
`project_ref=hpcyrnxschpxlrxudmqk`, features `docs, account, database, debugging,
development, functions, branching`.

**Працює з 2026-08-23.** У `settings.local.json` стоїть
`"enabledMcpjsonServers": ["supabase"]`, сервер піднімається на старті сесії й проходить
OAuth (власник відкриває посилання з `mcp__supabase__authenticate` у браузері). Першою ж
звіркою з живою базою знайдено відкриту дірку в правах — задача `002-rls-role-escalation`.

Конфіг живе **тільки в кореневому `.mcp.json`**. Дублікат `dev/.mcp.json` прибрано
2026-08-23: ключ проєкту в `~/.claude.json` — `/Users/ander1.sage/Downloads/AIA`, тобто
читається саме кореневий, а два однакові конфіги в двох місцях — це пастка «зміниш один,
забудеш другий».

**Вимикати/вмикати MCP може тільки власник.** Правка `settings.local.json` із сесії
блокується класифікатором дозволів, і це правильно: доступ до живої бази з даними учнів
відкриває людина. Шлях: `/mcp` → `supabase` → перезапуск сесії. Не обходити.

**Запасний шлях — браузер.** Бекендеру доданий `mcp__claude-in-chrome` (рішення власника,
2026-08-23): якщо MCP не піднявся або чогось не вміє, він може подивитись те саме в
Supabase Dashboard живим браузером. Правила ті самі, що й для MCP: **дивитись — вільно,
змінювати базу — ні**. Клікати «Run» у SQL Editor, правити політики в UI, тиснути кнопки,
що пишуть у базу, — заборонено так само категорично, як `apply_migration`. Зміни бази
йдуть **тільки** файлами міграцій на затвердження власником.

Якщо схему з живою базою звірити не вдалося жодним шляхом — бекендер **обов'язково
позначає це у звіті**. Гадати й називати це фактом — ні.

## Технічні межі (успадковані від основного проєкту)

- **Жодного build-кроку.** Чистий HTML + Tailwind CDN + vanilla JS. Те, що лежить у
  репозиторії, і є тим, що деплоїться. Ніяких npm-залежностей у корені, ніякого бандлера.
- **Увесь динамічний контент — у `config.json` / `architect.config.json`**, не в HTML.
  Правка тексту чи посилання = правка конфіга.
- **Регістр шляхів — завжди нижній.** Це вже раз ламало прод (папка `CSS/` проти посилань
  `css/`): macOS не чутлива до регістру, Cloudflare — чутливий. Звіряти регістр у кожному
  новому посиланні перед комітом.
- **Палітра БІЛЬШЕ НЕ дубльована по файлах** (з 2026-09-07, задача 010). Було: 66 копій
  `tailwind.config` у HTML, тобто новий токен = 66 однакових правок. Стало: **один
  `js/tw-theme.js`**, який читає `var(--токен)` з `css/tokens.css`. Новий токен = **одна**
  правка в `tokens.css`; `grep -c 'tailwind.config' *.html modules/*.html` має давати **0**.
  ⚠ **Альфа-модифікатори Tailwind (`bg-ink/85`) на `var()`-кольорі дають
  `rgba(0,0,0,0)` — повністю прозоре, без помилки в консолі.** Не вживати їх узагалі;
  для напівпрозорих ролей є готові токени (`--c-accent-quiet` тощо).
- `js/auth.js` завжди читає кореневий `config.json`, навіть зі сторінок `/modules/` —
  щоб вхід був спільним для всіх курсів. Не «оптимізувати» це на відносний шлях.
- Реальна перевірка порядку проходження модулів — на сервері (RPC `submit_quiz`);
  клієнтське блокування в `js/progress.js` — лише UX. Не переносити перевірку на клієнт.
- Доступність не опційна: `.skip-link`, `#ariaLive`, `aria-current`, видимий фокус,
  контраст, `prefers-reduced-motion`.
- Локальний перегляд: `python3 -m http.server 8000` з кореня (`fetch()` не працює
  з `file://`).

## Зв'язок із дизайн-майстернею

- **Нумерація спільна:** одна фіча = один номер. `design/001-oauth-google` і
  `build/001-oauth-google` — дві фази однієї задачі. Бекенд-задачі без дизайну беруть
  наступний вільний номер зі спільної послідовності (дірки в нумерації `design/` — норма).
- Вхід від дизайну: `dev/design/NNN-slug/SUMMARY.md` (точка входу),
  `04-variants/verdict.md` (деталі), `04-variants/variant-X/` (код обраного варіанта),
  `00-decisions.md` (рішення власника, вагоміші за `task.md`).
- **Ми не пишемо в `dev/design/`.** Потрібна зміна макета — сказати власнику; він передасть
  сесії `design_1`. Пряме листування між сесіями — тільки з разової згоди власника
  (це його тверде правило).
- Поле 12 брифа дизайну («Що піде в код») заповнює коренева сесія після приймання
  варіанта — не PM-агент. Статус у таблиці `design/README.md` (`у коді` → `зроблено`)
  теж рухає коренева сесія.

## Як харнес знаходить цих агентів (важливо)

Визначення агентів і скілів **фізично лежать тут**, у `dev/build/.claude/`, — щоб усе
про майстерню було в одній папці. Але Claude Code шукає агентів і скіли в
`~/.claude/` і в `.claude/` **кореня проєкту**, а не в довільних вкладених папках. Тому
з сесії, запущеної з `AIA/dev` або з кореня, агенти в `dev/build/.claude/agents/`
просто не існують — це перевірено (агентів дизайн-майстерні звідси теж не видно).

**Рішення: відносні симлінки в кореневій `AIA/.claude/`** (створено 2026-08-23):

```
AIA/.claude/agents/aia-build-pm.md   -> ../../dev/build/.claude/agents/aia-build-pm.md
AIA/.claude/skills/supabase          -> ../../dev/build/.agents/skills/supabase
...                                     (7 агентів + 19 скілів)
```

Чому саме так:
- **симлінки, не копії** — джерело правди лишається одне. Правиш
  `dev/build/.claude/agents/*.md`, і зміна діє одразу, без синхронізації;
- **відносні, не абсолютні** — виживають після `git clone` на іншому ноутбуці й після
  переміщення папки;
- **комітити їх треба.** Кореневий `.claude/` не в `.gitignore` (ігнорується лише
  `.claude/settings.local.json`, глобальним правилом `~/.config/git/ignore`), тож симлінки
  поїдуть у гіт і на другому ноутбуці конвеєр запрацює одразу після клону;
- сайту це не видно: `.claude/` є в кореневому `.assetsignore`.

**Побічний ефект, про який треба знати.** Сім скілів (`accessibility`, `performance`,
`animation-vocabulary`, `gsap-core`, `gsap-timeline`, `gsap-scrolltrigger`,
`review-animations`) тепер видні на рівні проєкту — тобто й сесії `design_1` теж, поверх
її власних локальних копій. Функціонально це нічого не змінює: копії **побайтово
ідентичні** (звірено по MD5, обидві з тих самих апстрімів). Коли в `dev/design/` є своя
локальна версія — вона й виграє, бо конкретніша.

**Якщо додаєш або перейменовуєш агента чи скіл — онови симлінк:**

```bash
cd /Users/ander1.sage/Downloads/AIA
ln -sfn ../../dev/build/.claude/agents/<новий>.md .claude/agents/<новий>.md
ln -sfn ../../dev/build/.agents/skills/<новий> .claude/skills/<новий>
```

Перевірка, що не зламано: `test -r .claude/agents/<ім'я>.md` (симлінк на неіснуючий
файл читається як помилка, а харнес просто тихо не покаже агента).

## Скіли

19 скілів, вендорені в `.agents/skills/`, симлінки в `.claude/skills/`, походження й хеші —
у `skills-lock.json`, ліцензії — в `.agents/skills/ATTRIBUTION.md`. Глобальний
`~/.claude/skills/` навмисно не зачіпаємо.

Свідомо **не** ставили `vercel-labs/agent-skills@web-design-guidelines`: у репозиторію
немає ліцензії (перевірено 2026-08-22), тобто «всі права збережено», а `dev/build/` їде
в публічний гіт. Дизайн-майстерня цей скіл використовує локально, з виключенням із гіта.

Додати скіл: `npx skills add <owner/repo@skill> -y` **з папки `dev/build/`** (без `-g`,
інакше поїде в `~/.claude/`). Після цього — дописати рядок в `ATTRIBUTION.md` і перевірити
ліцензію апстріму: `curl -s https://api.github.com/repos/<owner>/<repo> | grep spdx`.
Немає ліцензії — не комітити.
