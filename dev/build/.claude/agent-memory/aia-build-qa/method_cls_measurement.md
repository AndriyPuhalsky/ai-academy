Вікно, яким керує `mcp__claude-in-chrome`, тут майже завжди у фоні:
`document.visibilityState === "hidden"`, `document.hasFocus()` буває `true`, але це не рятує.

Наслідки, кожен уже коштував часу (коло 2 задачі 001, 2026-08-25):
- **`PerformanceObserver({type:'layout-shift', buffered:true})` віддає 0 записів**, і
  `performance.getEntriesByType('layout-shift')` теж 0. Chrome не генерує зсуви для
  прихованої сторінки. Контрольний дослід: вставити `div` висотою 120px на початок `body` —
  якщо запису немає, інструмент мертвий, а не сторінка ідеальна. **Робити цю перевірку
  ПЕРЕД тим, як написати «CLS = 0».**
- **`setInterval` душиться до 1 Гц**, `requestAnimationFrame` не викликається взагалі —
  будь-яка часова діаграма гідратації виходить брехливою.
- ⚠️ **ЗАСТАРІЛО (звірено 2026-09-05, задача 005): `resize_window` ПРАЦЮЄ.** 768 → 768,
  1024 → 1024, 1180 → 1180 — заміряно `innerWidth`. Не чинний більше запис про те, що він
  «рапортує успіх і нічого не міняє». Що лишилось чинним: Chrome не дає вікна вужчого за
  500 px, тому 390 знімається лише iframe'ом. Деталі — [[method-viewport-widths]].
- `osascript -e 'tell application "Google Chrome" to activate'` не допоміг; спроба перелічити
  вікна через AppleScript впала в таймаут AppleEvent — не витрачати на це час удруге.

**Що працює замість цього.** CLS цікавить не сам по собі, а джерелом — зміною боксу. Її
можна виміряти детерміновано: створити `position:absolute; visibility:hidden; left:-9999px`
контейнер **усередині того самого батька** (щоб діяли ті самі CSS-змінні), покласти туди
розмітку «до» і «після» і порівняти `getBoundingClientRect().width`. Дає число з точністю
0.01 px і не залежить ні від видимості, ні від таймінгу.

Пастка пробника: якщо правило в CSS написане через `#id[attr]`, клон **має зберегти `id`** —
інакше правило не спрацює і вийде хибний дефект (у мене резерв пілюлі показав 26px замість
119.6px саме через знятий `id`).

Ще одна корисна дрібниця: свіжість білда звіряється не на око, а через
`performance.getEntriesByType('resource')` → `decodedBodySize` проти `wc -c` файлу з робочого
дерева; `transferSize: 0` = віддано з кеша.

Див. [[method-guest-tests-on-localhost]].

## «CLS покращився» доводиться тільки парою «база проти дерева»

Додано 2026-09-10 (011, хвиля 2). Абсолютне число гуляє від прогону до прогону (той самий
`index.html` @768 дав 0,0204 і 0,0053 у двох сусідніх завантаженнях), тому «стало 0,0053 —
добре» нічого не доводить. Робочий рецепт:

```bash
mkdir -p /tmp/base && git archive <база> | tar -x -C /tmp/base
python3 -m http.server 8322 --bind 127.0.0.1 --directory /tmp/base &   # «до»
python3 -m http.server 8321 --bind 127.0.0.1 --directory <корінь> &    # «після»
```

Один і той самий скрипт ганяє обидва порти по 2 прогони на сценарій. Тоді видно і
покращення (гість на уроці 1280×900: **0,0824 → 0,0001**, і зник запис із джерелом
`FOOTER`), і те, що решта чисел **не зрушила** (768: 0,0033 = 0,0033), і те, що великі
числа сайту (`/architect` @768 0,0406, `/roadmap` @768 0,0477) — **однакові в базі й у
дереві**, тобто не твоя задача їх завела. Без цієї пари довелося б подавати їх дефектом.
