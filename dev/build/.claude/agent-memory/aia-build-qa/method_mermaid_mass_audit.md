# Масовий аудит діаграм Mermaid: стенд в одному документі

## Швидкий шлях (перевірено 2026-09-08, задача 010)

Не вантажити 58 сторінок по iframe (≈3 с кожна, тайм-аут CDP 45 с ⇒ 4 сторінки за виклик).
Замість цього:

1. Стати на будь-яку **сторінку модуля** превʼю — вона вже має `mermaid`, `AIA.mermaidTheme`,
   `tokens.css`, `components.css`.
2. `fetch()` усі 58 URL (тільки HTML, без сабресурсів) → `DOMParser` → зібрати `pre.mermaid`
   textContent. 58 фетчів ≈ 5 с.
3. Побудувати офскрін-стенд з ТІЄЮ Ж ієрархією, що на сторінці:
   `main > article.ds-prose > section > div.ds-diag > pre.mermaid`.
4. Ширина `main` → ширина `.ds-diag`: **768 → 766 (вʼюпорт 1440) · 704 → 702 (768) ·
   350 → 348 (390)**. Ці три значення однакові для всіх трьох курсів.
5. Рендерити **послідовно з `await`** (див. [[project_mermaid_id_collision]]) і міряти.

100 діаграм за ~2 виклики. Валідація: 20 реальних сторінок превʼю проти стенда —
ширина SVG збіглася до 1 px, кількість вузлів — точно.

## ⚠ ВИПРАВЛЕНО 2026-09-08 (коло 2): iframe ламається НЕ через ширину

Старий запис тут стверджував, що iframe убиває нативний рендер Mermaid (і Ф-Е з нього
вивів «не міряти в iframe ширшому за 1024»). **Обидва висновки хибні.** Контрольні заміри:

| Умова | Результат |
| ----- | --------- |
| iframe 320 / 390 / 768 / 1024 / 1440, «прогрітий» | **262 завантаження, 0 відмов** |
| **перша** навігація щойно створеного iframe | падає майже завжди |
| вкладка верхнього рівня, реальна навігація | **~25 завантажень, 0 відмов** |
| схована вкладка + голодний цикл опитування | «0 svg» — артефакт [[method-hidden-window-traps]] |

**Рецепт, що прибирає відмови:** перед кожною сторінкою вантажити `about:blank` у той самий
iframe і лише потім цільовий URL. Плюс сон на `MessageChannel`, не на `setTimeout`.

**І головне про сам симптом:** `data-processed="true"` **ставиться ДО рендеру** — це видно
в коді `mermaid@10.9.1` (`T.setAttribute("data-processed","true")` іде перед `await render`).
Тому «`data-processed` є, `<svg>` немає» **не доводить відмову** — це ще й вигляд середини
рендеру. Не будувати на цій ознаці вердикт без другого заміру через кілька секунд.

Коли відмова таки справжня, `<pre>` містить **самий лише CSS теми як текст** (~3 КБ,
починається з `#mermaid-<id>{font-family:"trebuchet ms"`), джерело діаграми **знищене**,
`.ds-diag__fallback` мовчить (бо `mermaid.run` не кидає), а контейнер ще й отримує
`tabindex="0"` — зупинка Tab на сміттi шириною 30 000 px.

## ⛔ Розкриття заблокованого уроку: `display: revert` ЛАМАЄ сітку

`main > [hidden]{display:revert}` повертає `<article>` до `display:block` **із origin
користувацького агента**, тобто викидає авторський `.ds-prose{display:grid}`. Наслідок:
`.ds-diag` перестає бути в колонці `wide` і розтягується на всю ширину `main`
(на 1440 — 1014 px замість 766). На ≤ 768 різниці немає (там `grid-column: 1/-1`), тому
пастка спрацьовує тихо саме на десктопі. Правильно:

```css
main > [hidden]{display:revert !important}
article.ds-prose[hidden]{display:grid !important}
```

Контроль, що обхід чесний: сторінки, де стаття НЕ схована (`module-01`, `architect-01`,
`claude-code-01`, `claude-code-ref-hooks`), мають дати ті самі `clientWidth` — 348 на 390,
702 на 768, 766 на 1440.

## Метрики, які варто знімати з кожної діаграми

- **накладання:** попарний перетин `getBoundingClientRect()` для `g.node`
  (для `sequenceDiagram` — `rect.actor`, `g.node` там немає);
- **вихід тексту за коробку:** `foreignObject.firstElementChild.scrollWidth` проти атрибута
  `width`. Шум субпікселя до ~1 px — поріг ставити 1,2;
- **масштаб:** `svg.getBoundingClientRect().width / svg.viewBox.baseVal.width`.
  Це головна метрика читабельності, див. [[project_mermaid_shrink_to_fit]];
- `aria-roledescription` → `flowchart-v2` / `sequence` / `error`.

`foreignObject` у Mermaid має `overflow: hidden`, а `.nodeLabel` — `white-space: nowrap`.
Тому переливи **обрізаються**, а не налазять на сусіда. Якщо на екрані видно накладання —
причина інша (див. [[project_mermaid_id_collision]]).
