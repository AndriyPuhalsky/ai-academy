Щоб побачити, що показує сайт при обриві звʼязку, **не треба ні вимикати Wi-Fi, ні блокувати
хост у DevTools**. Досить у консолі замінити `window.fetch` на функцію, що відхиляє
`new TypeError("Failed to fetch")`, і натиснути кнопку у формі. Жоден запит при цьому не
виходить із машини — тобто ні листа, ні рядка в продовій базі.

**Чому це діє на вже створений `window.sb`** (неочевидне й перевірене на `@supabase/auth-js`
2.117.2): `resolveFetch` повертає `(...args) => fetch(...args)`, тобто глобальний `fetch`
береться **в момент виклику**, а не в `createClient`. Якби він фіксувався при створенні
клієнта, підміна після завантаження сторінки нічого б не дала — і це перше, що треба
перевірити при оновленні бібліотеки.

**Той самий прийом у другий бік — підробити відповідь сервера:** повернути з заглушки
справжній `new Response(JSON.stringify({...}), { status: 400 })`. Так перевіряються гілки,
яких живий Supabase на вимогу не віддає (невпізнані помилки, 503, тощо).

**Що реально прилітає при обриві** (виміряно, не з памʼяті): auth-js обгортає будь-яке
відхилення `fetch` у `AuthRetryableFetchError` зі `status === 0`, а `message` бере з рідної
помилки браузера як є — Chrome «Failed to fetch», Firefox «NetworkError when attempting to
fetch resource.», Safari «Load failed». ⚠ Той самий клас приходить і на HTTP 500–504, 520–530,
але вже з НЕнульовим статусом: ознака «немає інтернету» — саме `status === 0`, а не назва класу.

**Перевірку логіки без браузера** роблю окремим файлом у scratchpad: читаю живий `js/auth.js`,
вирізаю з нього потрібні функції дужка-в-дужку й ганяю на підроблених помилках у Node. Так
тест читає **той самий текст**, що поїде в прод, і не вимагає ні сервера, ні акаунта.
