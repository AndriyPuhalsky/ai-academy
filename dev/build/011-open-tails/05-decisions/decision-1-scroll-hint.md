## Рішення

**Так — додаємо постійно видиму смугу прокрутки на ті самі шість скролерів, але НЕ так, як
пропонувалось у звіті:** правило `::-webkit-scrollbar` саме по собі на цьому сайті **не діє
взагалі** (заміряно), бо його мовчки вимикає успадкований `scrollbar-color` із §38.8; тому
спека нижче — `scrollbar-color: auto` + `::-webkit-scrollbar` **12 px з прозорим полем
4 px** (видимий повзунок 4 px, колір `--c-line-strong`) під `@supports`, плюс окрема гілка
стандартних властивостей для Firefox. Гасіння краю **лишається без змін**: смуга його не
замінює, вони закривають різні випадки.

---

## Чому

### 1. Проблему, названу у звіті, замір підтверджує — але вона менша, ніж здається

Для кожного прокручуваного блока порахували, чи є «чорнило» (текст або графіка діаграми)
у смузі згасання шириною 40 px, окремо по зрізах висоти 200 px. Вісім сторінко-ширин
(`ref-hooks` 1280/768, `claude-code-07`, `-20`, `-22`, `ref-settings` 1280, `claude-code-10`,
`architect-08`, `module-05` 390):

| Показник | Значення |
| -------- | -------- |
| прокручуваних блоків | **50** |
| зрізів по 200 px | **211** |
| зрізів, де в краю НЕМАЄ чорнила (згасання не видно) | **24 = 11,4 %** |
| блоків, де згасання не видно **ніде** | **0** |
| блоків, вищих за вʼюпорт | **16 = 32 %** |

Тобто гасіння працює у 88,6 % випадків і в жодному блоці не мовчить повністю. Найгірший
блок — та сама таблиця `min-w-[54rem]` у `ref-hooks` на 1280: **6 порожніх зрізів із 14**.

### 2. Ширшати смузі згасання немає сенсу — це перевірено, а не припущено

Найдешевший здогад «зробити `--fade-w` більшою» відкидається числами (9 сторінко-ширин,
287 зрізів):

| `--fade-w` | 16 | 24 | 32 | **40 (зараз)** | 56 | 64 | 80 | 96 |
| ---------- | -- | -- | -- | -------------- | -- | -- | -- | -- |
| зрізів без чорнила | 16,4 % | 15,0 % | 13,2 % | **12,9 %** | 12,2 % | 12,2 % | 11,1 % | 10,1 % |

Подвоєння смуги (40 → 80) купує 1,8 п.п. Поточні `var(--s-10)` стоять рівно на коліні
кривої — **не чіпати**.

### 3. У спокої на macOS зараз НЕМАЄ жодної смуги — і це не те, що видно на знімках

Заміряно на всіх шести типах скролерів: `offsetHeight − бордери − clientHeight = **0 px**`,
тобто смуги **накладні** (overlay) і місця не займають. Смуга, яку видно на
`stand/shots/t8-390-…-termtermbo-start.png`, — це накладна смуга, що спалахнула після
`scrollIntoView()` у самому скрипті заміру й гасне за 1–2 с. **Знімки стенда тут вводять
в оману**; у живому читанні під блоком немає нічого.

### 4. Пастка, через яку пропозиція зі звіту не спрацювала б мовчки

`css/components.css` §38.8 має `html { scrollbar-width: thin; scrollbar-color: var(--c-line) transparent; }`.
**`scrollbar-color` — успадкована властивість**, тож вона доходить до кожного скролера
сторінки (заміряно: computed `scrollbar-color` на скролері = `rgb(67, 60, 53) rgba(0,0,0,0)`).
А Chrome ≥ 121 **ігнорує `::-webkit-scrollbar`, якщо на елементі задані стандартні
властивості смуги**. A/B на живій сторінці:

| Що застосовано | Товщина смуги |
| -------------- | ------------- |
| база | 0 px |
| `::-webkit-scrollbar { height: 6px }` (пропозиція зі звіту, як є) | **0 px — не діє** |
| `scrollbar-color: auto` + `::-webkit-scrollbar { height: 6px }` | 6 px |
| `scrollbar-color: auto` + `::-webkit-scrollbar { height: 12px }` + поле 4 px | **12 px** |
| `scrollbar-width: thin; scrollbar-color: <токен>` на самому скролері | 0 px (лишається накладною) |

Тобто без `scrollbar-color: auto` фронтендер написав би правило, побачив «нічого не
змінилось», і пішов би шукати причину не там. Це головна причина, чому це рішення —
не «так/ні», а спека.

### 5. Смуга й гасіння закривають РІЗНІ випадки, і жодне не закриває все

- **гасіння** видно на будь-якій висоті блока, але лише там, де в краю є вміст (88,6 %);
- **смуга** видно завжди, коли блок прокручується, і вона одна показує **скільки ще
  лишилось** — але вона живе **знизу блока**, а 32 % блоків вищі за вʼюпорт, тож поки
  людина читає середину такого блока, смуги на екрані немає.

Разом вони покривають істотно більше, ніж кожне окремо. Те, що лишається непокритим
(високий блок + порожній край), — окремий рядок реєстру, див. «Що це рішення НЕ закриває».

### 6. Ціна перевірена, а не оцінена

- **Висота.** +12 px рівно на тих блоках, що **справді прокручуються**; на решті 0
  (Chrome не малює смугу там, де нема переповнення). По сторінках: `ref-hooks` 1280 —
  8 блоків × 12 = 96 px на 25 297 (0,4 %); `claude-code-10` 390 — 6 × 12 = 72 px на 41 672
  (0,2 %); `module-05` 390 — 12 × 12 = 144 px.
- **CLS — без регресії** (замір «без смуги» / «зі смугою», кеш вимкнено, Supabase
  заблокований): `claude-code.html` 390 — 0 / 0; 1280 — 0,0064 / 0,0050; `index.html` 390 —
  0 / 0; `claude-code-10` 390 — 0,0405 / 0; `module-05` 390 — 0 / 0; `ref-hooks` 1280 —
  0,071 / 0,074. Причина, чому зсуву немає: правило чисто CSS-не, тож місце під смугу
  враховане з першої розкладки, а не після роботи JS.
- **Контраст повзунка** (фактичні фони під скролерами заміряні, не вгадані):

| Фон під скролером | `--c-line` #433C35 (як у §38.8) | `--c-line-strong` #746C62 |
| ----------------- | ------------------------------- | ------------------------- |
| таблиця — `--c-bg` #161311 | 1,71 ✗ | **3,58 ✓** |
| термінал і код — `--c-sunken` #0E0C0A | 1,80 ✗ | **3,78 ✓** |
| діаграма — `--c-surface` #1E1A17 | 1,59 ✗ | **3,34 ✓** |

Тому колір повзунка — `--c-line-strong` («усе, що межею ідентифікує контрол»), а не
`--c-line` («ТІЛЬКИ декоративний хайрлайн»). Це рівно та роль, яку токени описують у
`tokens.css`, і вона ж дає ≥ 3:1 за SC 1.4.11.

### 7. Маска §41 смугу не чіпає — перевірено дослідом, а не з коментаря

Навмисно роздули смугу згасання до 300 px і зняли низ таблиці: **текст у краю гасне,
повзунок — ні**, по всій довжині однаковий. Тришарова маска (L2 `exclude`) справді лишає
жолоб смуги поза градієнтом, і для власної webkit-смуги теж. Додатково: геометрично
повзунок майже ніколи не доходить до згаслого краю — він завжди зміщений у бік,
протилежний тому, де є ще вміст.

## Наслідки

### Що зміниться для людини

- Під кожним широким блоком, який справді прокручується, зʼявиться **тонка світла риска
  4 px** з полем 4 px згори й знизу — видима завжди, а не лише під час прокрутки. Вона ж
  показує позицію: видно, що прогорнуто чверть, а що — майже все.
- Мишею її можна тягнути (площа наведення 12 px). Це не єдиний спосіб: усі **179 обгорток
  таблиць** мають `tabindex="0" role="region" aria-label`, **107 терміналів** — `tabindex`,
  діаграми дістали `tabindex/role/aria-labelledby` у 011, а Chrome ≥ 127 сам робить
  прокручувані контейнери фокусованими. Тому смуга — підказка, а не єдиний контрол
  (це і є підстава для винятку «еквівалентний контрол» у SC 2.5.8).
- На **Windows/Linux** зміна — на краще й непомітна: там смуга й зараз класична (займає
  місце), але пофарбована в `--c-line` (1,71) і завтовшки ~15–17 px; стане 12 px з
  повзунком 3,58.
- Гасіння краю не змінюється жодним пікселем.

### Що ризикує

| Ризик | Ціна | Як перевірити заздалегідь |
| ----- | ---- | ------------------------- |
| **`::-webkit-scrollbar` — вендорна річ**, Chrome її колись може прибрати на користь стандартних властивостей | деградація тиха й мʼяка: смуга знову стає накладною, тобто повертається сьогоднішній стан; нічого не ламається | правило лежить під `@supports selector(::-webkit-scrollbar)`; якщо селектор перестане підтримуватись, увімкнеться гілка Firefox зі стандартними властивостями |
| **`scrollbar-color: auto` знімає токенний колір** із шести скролерів у Chrome | у Chrome колір задає `::-webkit-scrollbar-thumb` тим самим токеном — видимої різниці нема; у Firefox колір лишається токенним через другу гілку | замір: computed `scrollbar-color` на скролері = `auto`, повзунок малюється `--c-line-strong` |
| **iOS Safari** — чи стане смуга там постійною, перевірити нікому: агенти на телефон не ходять | максимум — на iPhone лишається сьогоднішній стан (накладна смуга) | конструктивно недоступне (рядок 21 реєстру); окремо позначити для власника |
| **Firefox на macOS**: `scrollbar-width: thin` там може лишитись накладною | те саме — сьогоднішній стан | Firefox не є цільовим браузером (рішення власника про Safari за аналогією), гілка додається «щоб не гірше» |
| **Хтось потім поставить `scrollbar-width` на ці шість селекторів** | webkit-стилі мовчки вимкнуться, смуга зникне, і причину шукатимуть у кольорах | записано в «Що НЕ робити» і в коментарі §41.1 |
| Файл спільний для трьох платформ | зміна їде на AI Академію, AI Architect і AI Термінал одночасно; при релізі — патч-версії `0.5.1 / 1.4.1 / 1.2.1`, як у звіті | перевірити всі три лендінги й по одному уроку кожного курсу |

### Що це рішення НЕ закриває (і це свідомо)

**Високий блок із порожнім краєм.** 32 % прокручуваних блоків вищі за вʼюпорт; поки людина
читає їхню середину, смуга знизу на екран не потрапляє, а гасіння в таких зрізах може бути
порожнім (найгірше — 6 зрізів із 14 у першій таблиці `ref-hooks` на 1280). Ані смуга, ані
ширша маска цього не лікують (див. таблицю в §2).

**Рекомендація кореневій сесії:** завести в реєстрі рядок **1a** — «підказка для блоків,
вищих за вʼюпорт», тип **Д + В** (потрібен макет і рішення власника). Живі кандидати, щоб
не переоткривати: липка підказка знизу видимої частини скролера (потрібна обгортка +
`position: sticky` + JS — це вже новий компонент, тобто макет) · звузити `min-w-[54rem]`
у семи таблицях `ref-hooks` до фактично потрібного (тоді край перестає бути порожнім, але
це правка контенту довідника) · перевести найширші прозові таблиці в списки, як уже
зроблено з `claude-code-02#l4` 2026-09-09. Без цього рядка хвіст зникне з поля зору —
рівно те, проти чого й заведено 011.

## Специфікація для фронтендера

**Файл:** `css/components.css` — **один**. JS не змінюється взагалі: `js/ui.js`
(`initScrollFades`) і атрибути `data-scroll-fade` лишаються як є; смуга свідомо **не**
привʼязана до атрибута (див. «Що НЕ робити», пункт 2). HTML не змінюється.

**Куди:** у кінець файла, одразу після §41 (зараз файл закінчується правилом
`[data-scroll-fade="left"]`, рядок 2516). Нова підсекція — **41.1**.

**Шість скролерів** — рівно ті самі, що в `js/ui.js` (`FADE_SCROLLERS`) і в §41, у тому ж
порядку:

```
.ds-tbl__wrap
.ds-diag > pre.mermaid
.term > .term__body
.ds-code > .ds-code__pre
.ds-prose > .ds-code__pre
.ds-prose > section > .ds-code__pre
```

**Точний CSS** (перевірено на живих сторінках: смуга 12 px на всіх прокручуваних блоках,
вертикальна смуга `.ds-tbl__wrap--tall` теж 12 px, 0 помилок консолі):

```css
/* ============================================================================
   41.1 · 011 · РЯДОК 1 · ПОСТІЙНО ВИДИМА СМУГА ПРОКРУТКИ НА ТИХ САМИХ ШЕСТИ СКРОЛЕРАХ
   ----------------------------------------------------------------------------
   Гасіння краю (§41) показує «далі є ще» ТІЛЬКИ там, де в краю є вміст. Замір
   2026-09-10 (50 прокручуваних блоків, 211 зрізів по 200 px): у 11,4 % зрізів
   край порожній і гасити нічого. Ширша маска це не лікує — 40 → 80 px купує
   1,8 п.п., тому --fade-w лишається var(--s-10).
   Смуга закриває саме цей випадок і додає те, чого маска не вміє взагалі:
   СКІЛЬКИ ще лишилось.

   ⚠ ПАСТКА, ЧЕРЕЗ ЯКУ ЦЕ ПРАВИЛО МОЖЕ МОВЧКИ НЕ ПРАЦЮВАТИ.
   §38.8 ставить html { scrollbar-width: thin; scrollbar-color: var(--c-line) … }.
   `scrollbar-color` УСПАДКОВУЄТЬСЯ, а Chrome ≥ 121 ігнорує ::-webkit-scrollbar
   на елементі, у якого задані стандартні властивості смуги. Тому першим рядком
   іде scrollbar-color: auto — без нього ::-webkit-* не діють узагалі (заміряно
   A/B: 0 px проти 12 px). Рядок html у §38.8 НЕ чіпати: він фарбує смугу
   сторінки, і на Windows це видима річ.

   Товщина 12 px = площа наведення; видимий повзунок 4 px — прозоре поле 4 px
   робиться border + background-clip: padding-box. Колір --c-line-strong, бо це
   роль «межа, що ідентифікує контрол»: 3,34–3,78 до трьох фонів під скролерами
   (--c-surface / --c-bg / --c-sunken) проти 1,59–1,80 у --c-line, тобто SC 1.4.11.
   Місце під смугу враховане з першої розкладки, тому CLS не додається (заміряно
   на 6 сторінко-ширинах). Маска §41 смуги не торкається: жолоб лежить між рамкою
   і padding-box, і шар L2 (exclude) лишає його непрозорим — перевірено дослідом
   зі смугою згасання 300 px.
   ========================================================================== */
@supports selector(::-webkit-scrollbar) {
  .ds-tbl__wrap,
  .ds-diag > pre.mermaid,
  .term > .term__body,
  .ds-code > .ds-code__pre,
  .ds-prose > .ds-code__pre,
  .ds-prose > section > .ds-code__pre { scrollbar-color: auto; }

  .ds-tbl__wrap::-webkit-scrollbar,
  .ds-diag > pre.mermaid::-webkit-scrollbar,
  .term > .term__body::-webkit-scrollbar,
  .ds-code > .ds-code__pre::-webkit-scrollbar,
  .ds-prose > .ds-code__pre::-webkit-scrollbar,
  .ds-prose > section > .ds-code__pre::-webkit-scrollbar { width: var(--s-3); height: var(--s-3); }

  .ds-tbl__wrap::-webkit-scrollbar-track,
  .ds-diag > pre.mermaid::-webkit-scrollbar-track,
  .term > .term__body::-webkit-scrollbar-track,
  .ds-code > .ds-code__pre::-webkit-scrollbar-track,
  .ds-prose > .ds-code__pre::-webkit-scrollbar-track,
  .ds-prose > section > .ds-code__pre::-webkit-scrollbar-track { background: transparent; }

  .ds-tbl__wrap::-webkit-scrollbar-thumb,
  .ds-diag > pre.mermaid::-webkit-scrollbar-thumb,
  .term > .term__body::-webkit-scrollbar-thumb,
  .ds-code > .ds-code__pre::-webkit-scrollbar-thumb,
  .ds-prose > .ds-code__pre::-webkit-scrollbar-thumb,
  .ds-prose > section > .ds-code__pre::-webkit-scrollbar-thumb {
    background: var(--c-line-strong);
    background-clip: padding-box;          /* видимий повзунок = 12 − 2×4 = 4 px */
    border: var(--s-1) solid transparent;
    border-radius: var(--r-pill);
  }

  /* Кут між горизонтальною й вертикальною смугою — лише в .ds-tbl__wrap--tall
     (дві таблиці в claude-code-ref-settings.html). Без цього рядка Chrome малює
     там світлий системний квадрат. */
  .ds-tbl__wrap::-webkit-scrollbar-corner { background: transparent; }
}

/* Firefox ::-webkit-* не знає; там смуга робиться стандартними властивостями.
   Гілки взаємовиключні, тож у Chrome цей блок не застосовується й конфлікту з
   scrollbar-color: auto вище немає. */
@supports not selector(::-webkit-scrollbar) {
  .ds-tbl__wrap,
  .ds-diag > pre.mermaid,
  .term > .term__body,
  .ds-code > .ds-code__pre,
  .ds-prose > .ds-code__pre,
  .ds-prose > section > .ds-code__pre {
    scrollbar-width: thin;
    scrollbar-color: var(--c-line-strong) transparent;
  }
}
```

**Токени, які використані, і чому саме вони** (нових токенів не заводимо):

| Токен | Значення | Роль тут |
| ----- | -------- | -------- |
| `--s-3` | 12 px | товщина смуги = площа наведення |
| `--s-1` | 4 px | прозоре поле навколо повзунка → видимі 4 px |
| `--c-line-strong` | `#746C62` | повзунок; роль «межа, що ідентифікує контрол», 3,34–3,78 |
| `--r-pill` | 999 px | повзунок-пігулка, як решта заокруглень системи |

**Чого робити НЕ треба в межах цієї задачі:** `js/ui.js`, HTML, `css/tokens.css`,
`css/claude-code.css`, `css/roadmap.css`, `.assetsignore`, `wrangler.toml`, версії в
конфігах (версії підіймає коренева сесія при релізі).

**`prefers-reduced-motion`:** смуга статична, анімацій не додає — робити нічого не треба
й не можна (жодних `transition` на повзунку: наведення миші не має ворушити 4 px риску).

**Порядок робіт:** робота одноосібна, бекенду тут немає, чекати нема на кого.

### Критерії приймання (для QA, усе перевіряється в браузері на dev-превʼю)

Полігон: `https://dev-ai-academy.andriy-puhalsky.workers.dev`. Кеш вимикати завжди
(пастка №1 стенда). Цільовий браузер — Chrome.

1. **Смуга є там, де є скрол.** На `/claude-code-ref-hooks` при 1280 під кожною з
   прокручуваних таблиць видно тонку світлу риску; на нерухомих блоках риски немає.
   Числом, у консолі:
   ```js
   [...document.querySelectorAll('.ds-tbl__wrap, .ds-diag > pre.mermaid, .term > .term__body, .ds-code > .ds-code__pre, .ds-prose > .ds-code__pre, .ds-prose > section > .ds-code__pre')]
     .map(e => { const cs = getComputedStyle(e);
       return { скрол: e.scrollWidth - e.clientWidth > 1,
                смуга: e.offsetHeight - (parseFloat(cs.borderTopWidth)||0) - (parseFloat(cs.borderBottomWidth)||0) - e.clientHeight }; })
   ```
   Очікувано: `смуга: 12` рівно там, де `скрол: true`, і `0` там, де `false`. Інших
   значень бути не може.
2. **Смуга видима у спокої.** Завантажити `/modules/claude-code-10` при 390, нічого не
   торкатись 5 секунд, зробити знімок: під терміналом риска на місці. (До правки вона
   зʼявлялась лише на 1–2 с після прокрутки — це і був дефект.)
3. **Позиція повзунка відповідає прокрутці.** Прогорнути будь-який широкий блок до кінця:
   повзунок доїжджає до правого краю; на початку — притиснутий до лівого.
4. **Гасіння краю не зламалось.** `data-scroll-fade` на тих самих блоках приймає
   `right → both → left` при прокрутці; текст у краю так само гасне (порівняти з
   `stand/shots/t8-*`).
5. **Маска не зʼїдає повзунок.** На прокрученому до середини блоці повзунок однаково
   світлий по всій довжині — без затемнення біля країв.
6. **Вертикальна смуга.** `/claude-code-ref-settings` при 1280: у двох таблицях
   `.ds-tbl__wrap--tall` вертикальна смуга теж 12 px, кут між смугами прозорий (світлого
   системного квадратика немає), липка шапка таблиці працює як раніше.
7. **CLS не погіршився.** `claude-code.html` і `index.html` на 390 і 1280, `module-05` на
   390: CLS ≤ значень зі звіту (`stand/t9.out.json`, ≤ 0,009 на лендінгу). Мірити з
   вимкненим кешем; на уроках памʼятати про шлагбаум `#aiaGate` (гість → нульові ширини).
8. **Телефон 390.** `/modules/claude-code-10` і `/modules/module-05`: горизонтальний скрол
   сторінки не зʼявився (`document.documentElement.scrollWidth === innerWidth`), блоки не
   налазять один на одного, риска не зливається з рамкою блока.
9. **Три платформи.** По одному уроку кожного курсу (`module-05`, `architect-08`,
   `claude-code-10`) плюс три лендінги: вигляд риски однаковий, акцент курсу на неї не
   впливає (вона на нейтральному токені, не на акцентному).
10. **Клавіатура.** `Tab` до обгортки таблиці (`role="region"`) — видиме кільце фокуса
    ціле, не обрізане маскою; стрілки ← → прокручують блок; повзунок їде разом із вмістом.
11. **Контраст.** Піпеткою: повзунок `#746C62` на фоні таблиці `#161311`, термінала
    `#0E0C0A`, картки діаграми `#1E1A17` — ≥ 3:1 у всіх трьох (очікувано 3,58 / 3,78 / 3,34).
12. **Консоль чиста** на всіх перевірених сторінках; жодного нового попередження про
    невідому властивість.
13. **Зона правок.** `git diff --stat` показує рівно один файл — `css/components.css`.

**Що найімовірніше зламається** (звідси починати ламати): забутий `scrollbar-color: auto`
→ критерій 1 дасть суцільні нулі, і це виглядатиме як «CSS не доїхав» · зайвий
`scrollbar-width` на шести селекторах → те саме · `::-webkit-scrollbar` без `width` →
у `.ds-tbl__wrap--tall` вертикальна смуга лишиться системною 15 px і поруч із 12-піксельною
горизонтальною це видно · `background-clip: padding-box` без `background` у тому ж правилі
→ повзунок стане прозорим.

## Що НЕ робити

1. **Не чіпати `html { scrollbar-width … scrollbar-color … }` у §38.8.** Це смуга самої
   сторінки, відновлена в 010 за поведінкою проду; на Windows вона видима. Наше правило
   переозначує колір **тільки** на шести скролерах.
2. **Не вішати смугу на `[data-scroll-fade]`.** Атрибут ставить JS уже після
   `DOMContentLoaded` (а на уроках — після завантаження `mermaid.min.js` з CDN, тобто
   +1,2–1,5 с), тож перемикання на ненакладну смугу в цей момент дало б стрибок 12 px на
   кожному блоці — новий CLS рівно там, де 011 його щойно прибрала. Правило має бути чисто
   CSS-ним і діяти з першої розкладки.
3. **Не ставити `scrollbar-width` на ці шість селекторів** (ні `thin`, ні `auto`) поза
   гілкою Firefox: будь-яке значення знову вимкне `::-webkit-*` у Chrome.
4. **Не збільшувати `--fade-w`.** Заміряно: 40 → 96 px купує 2,8 п.п. і робить край
   помітно розмитим.
5. **Не міняти `overflow-x: auto` на `scroll`.** На macOS це нічого не дає (перевірено:
   0 px), а на Windows намалювало б порожню смугу під блоками, які не прокручуються.
6. **Не додавати анімацій, `transition`, підсвітки при наведенні.** Постійний елемент, що
   ворушиться під кожним широким блоком, — саме той шум, якого система 009 уникає.
7. **Не братися заразом за високі блоки** (рядок 1a). Це окрема робота з макетом; змішати
   її сюди означає вивести задачу з-під правила «без макета», яке власник дав саме для
   рядка 1.
8. **Не переносити правило в `css/tokens.css`.** Токени — значення, компоненти — поведінка;
   §41 і §41.1 мають лишитись поруч, бо читаються разом.
