  проді 2026-10-01 — `GET /verify.html?code=TEST` віддає **307** на `/verify?code=TEST`,
  а `/verify?code=TEST` → **200**. Параметр той самий (`js/verify.js:281` читає `?code`),
  тож це той самий формат, просто без зайвого переходу. Якщо власник хоче буквально як у
  PDF — це один рядок (`verifyUrl`);
- `escapeHtml` на імені, назві курсу й посиланні; `disable_web_page_preview` у `sendMessage`
  уже стоїть, тож прев'ю сторінки верифікації не роздуває повідомлення;
- заднім числом нічого не розсилається: тригер тільки на `INSERT`.

## Вибір механізмів (і чому саме так)

### Дані для CSV — сервісний ключ напряму, без нової RPC

Звірив гранти наживо: `service_role` має `SELECT` на `profiles`, `courses`, `modules`,
`progress`, `certificates` і має `rolbypassrls = true`. Тобто кнопка працює **без жодної
міграції** — рівно як наявна «✉️ Повідомлення» читає `contact_messages`.

Нова `SECURITY DEFINER` RPC була б гіршою за двома причинами:

1. Postgres дає `EXECUTE` новій функції **ролі PUBLIC за замовчуванням**, тобто з'явився б
   новий публічний ендпоінт, який віддає імена й email усіх учнів. Його довелось би окремо
   закривати — саме це колись зробили для `admin_user_report` (звірив ACL: там лишились
   тільки `postgres` і `service_role`, тобто дірки немає, але це довелось робити руками).
2. Менше міграцій у прод-базу без staging — менше ризику. Безпеку це не погіршує: сервісний
   ключ живе лише в env Edge Function, у клієнт не потрапляє.

### Сповіщення — тригер + pg_net, не Database Webhook із Dashboard

| Варіант | За | Проти |
| ------- | -- | ----- |
| **тригер + `net.http_post`** (обрано) | так уже працює сповіщення про реєстрацію (`trg_notify_new_profile`); `pg_net` 0.20.3 встановлений; усе в одному файлі міграції, видно в git | потрібен один ручний крок із секретом |
| Database Webhook у Dashboard | міграції не треба зовсім | схеми `supabase_functions` у проєкті **немає зовсім** → вебхуки Dashboard тут ніколи не вмикались, це нова інфраструктура; значення заголовка однаково осідає в тілі створеного тригера, тобто виграшу в безпеці нуль; форма на 6 полів для людини, яка не розробник; механізм розходиться з перевіреним шляхом реєстрацій |

### Секрет — Supabase Vault, у репозиторій не потрапляє

`supabase_vault` 0.3.1 встановлений, `vault.decrypted_secrets` існує, `SELECT` на нього має
`postgres` — тобто `SECURITY DEFINER`-функція, створена власником у SQL Editor (вона буде
власності `postgres`, як і решта функцій проєкту), прочитає секрет, а `anon`/`authenticated` — ні.

Порівняння варіантів:

| Варіант | Оцінка |
| ------- | ------ |
| **Vault** (обрано) | значення зашифроване, у міграції лише ім'я `telegram_webhook_secret`; читає тільки `postgres`/`service_role`; ціна — один ручний крок |
| літерал у міграції | ⛔ неможливо: репозиторій публічний, а історія git не забуває |
| Database Webhook із Dashboard | значення в базі так само відкритим текстом (у визначенні тригера), плюс нова інфраструктура |
| GUC (`alter database … set app.secret = …`) | простіше, але значення лежить відкритим текстом у системному каталозі й застосовується лише до **нових** сесій — тобто «працює не одразу», що виглядає як баг |

**Важливо:** якщо секрету у Vault немає, міграція однаково застосується, тригер спрацює, а в
логах Postgres буде `WARNING 013: секрет telegram_webhook_secret не знайдено у Vault`.
Сповіщення не піде, **видача сертифіката не зламається**. Це свідомий порядок пріоритетів:
сертифікат важливіший за сповіщення.

### Чому тригер не може зламати видачу сертифіката

`certificates` наповнює `maybe_issue_certificate()`, яку викликає `submit_quiz()` при здачі
останнього іспиту (звірив обидва тіла наживо). Якби тригер кинув виняток, транзакція
відкотилась би й **учень не зміг би завершити курс**. Тому:

- усе тіло функції — в `begin … exception when others then raise warning …; end;`;
- `EXECUTE` на функцію **свідомо не відкликається**. Тіло повертає `trigger`, тож прямий
  виклик (у т.ч. через PostgREST) одразу падає на «can only be called as a trigger» —
  експозиції немає. А от відкликання `EXECUTE` — це ненульовий ризик для вставки, і платити
  ним за нульовий виграш не варто;
- `net.http_post` асинхронний: запит лягає в чергу `pg_net`, яку воркер читає **після
  коміту**. При відкаті транзакції сповіщення не піде — і це правильно.

### Крок 1 — поклади секрет у Vault (перший і найважливіший)

Потрібне те саме значення, що лежить у секреті **WEBHOOK_SECRET** (Edge Functions → Secrets).
Відкрий Dashboard → **SQL Editor** → New query, встав рядок, замінивши `<СЕКРЕТ>` на це
значення, і натисни **Run**:

```sql
select vault.create_secret('<СЕКРЕТ>', 'telegram_webhook_secret',
       'Секрет Database Webhook -> Edge Function telegram (013)');
```

Перевірка (значення не показує — лише «не порожній»):

```sql
select name, length(decrypted_secret) > 0 as not_empty
  from vault.decrypted_secrets where name = 'telegram_webhook_secret';
```

Очікувано: один рядок, `not_empty = true`.

> ⚠ Цей рядок із підставленим значенням **нікуди не копіюй і не коміть**. Запустив — закрив

## Що передати тестувальнику

Де найімовірніше зламається:

1. **Назва курсу в CSV і в сповіщенні.** Якщо з'явиться п'ятий курс, у шапці буде
   `courses.title` — для «Jira з нуля» це б дало правильно, а для першого курсу дало б
   «AI Essentials». Новий курс = один рядок у `COURSE_NAMES`.
2. **Порожня перша колонка.** Якщо в учня немає ні імені, ні email — буде `—`. Відтворити:
   профіль із `full_name = null`.
3. **Дата на межі доби.** Сертифікат, виданий між 21:00 і 24:00 UTC, у CSV має показувати
   **наступний** день (Київ = UTC+3). Відтворити: порівняти `issued_at` у базі з клітинкою.
4. **`Max rows`.** Коли `progress` перевалить за 1000 рядків, перевірити, що сума
   `пройдено` в CSV збігається з `select count(*) from progress where status='completed'`.
   Якщо раптом не збіглась — пагінація зламана, і це видно тільки таким порівнянням.
5. **Сповіщення має прийти рівно один раз.** `maybe_issue_certificate` вставляє з
   `on conflict (user_id, course_id) do nothing`, тож повторна здача іспиту сповіщення не
   дублює. Відтворити: пройти останній модуль двічі (`uncomplete_module` → знову).
6. **Кнопка в чужих руках.** Будь-який інший chat_id має отримати «🔒 Лише для адміна» і
   жодного файла.

## Знайдене поза обсягом

1. **`anon` і `authenticated` мають `INSERT/UPDATE/DELETE/TRUNCATE` на `certificates`,
   `progress`, `courses`, `modules` і `DELETE/TRUNCATE` на `profiles`** (звірив
   `role_table_grants` наживо). Зараз це не експлуатується, бо політик на запис не існує
   взагалі — RLS мовчки забороняє. Але це рівно та сама конструкція, на якій згоріла задача
   002: **одна необережно додана дозвільна політика відкриє запис**, бо гранти вже є. Варто
   окремою задачею прибрати зайві гранти (лишити `SELECT` там, де він потрібен).
   Я свідомо не чіпав: це зміна прав у проді поза обсягом 013.
2. **`net.http_post` виконуваний роллю PUBLIC, а на схему `net` є `USAGE` у `anon` і
   `authenticated`** (дефолт Supabase). Через Data API це не дістати — `net` не в списку
   виставлених схем, PostgREST таких функцій не бачить. Але як «оборона в глибину» варто
   колись відкликати: це SSRF-поверхня з самої бази.
3. **`notify_new_profile()` досі тримає секрет літералом у тілі.** Після 013 у проєкті
   з'явиться Vault, і цю функцію можна перевести на нього тим самим способом — одна
   маленька задача. Я не чіпав робочий шлях реєстрацій і тіло не знімав.
4. **`admin_user_report()` рахує «усього модулів» як `count(*)` по ВСІХ курсах** (звірив
   тіло). Тобто в наявному «⬇️ Експорт» колонка «усього» зараз 80 для кожного — число
   без сенсу, відколи курсів стало чотири. Нова кнопка цю проблему не має (рахує по курсу),
   але стара колонка так і бреше. Окрема дрібна задача.
5. **Ім'я задеплоєного файла функції — `%25252520telegram_index.ts`** (тобто « telegram_index.ts»
   з пробілом, кілька разів URL-закодований). Косметика, слід завантаження через Dashboard;
   при наступному деплої варто назвати файл `index.ts`.
