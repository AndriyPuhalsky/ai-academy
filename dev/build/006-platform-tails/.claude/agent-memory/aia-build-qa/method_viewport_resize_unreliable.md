**Після кожного `resize_window` читати `{innerWidth, innerHeight}` і звіряти із запитаним.
Не збіглось — переходити на `<iframe>` того самого origin.**

**Why:** інструмент повертає «Successfully resized… to 390x844» навіть тоді, коли нічого не
змінив. 2026-09-05 (005) він працював (768 → 768, 1024 → 1024). 2026-09-06 (006, коло 2) у
тому ж проєкті **не працював**: перший виклик дав `innerWidth` 1440, а всі наступні —
1440×709 незалежно від запиту (просив 600, 900, 390×844 — щоразу 709). Тобто це властивість
конкретного вікна/сесії, а не стала. Приймати на віру той чи інший бік — значить писати
звіт про ширини, яких не було.

**How to apply:**

- Дешева перевірка: `resize_window(1440, 653)` → `JSON.stringify({iw:innerWidth, ih:innerHeight})`.
  Якщо `ih` не рухається між двома різними запитами — інструмент мертвий, далі iframe.
- Iframe-пробник тримати універсальним і мірити ним усе (653, 820, 900, 1024, 1200, 768, 390):
  медіа-запити всередині справжні, `max-height` теж. Обовʼязково `appendChild` до `src`,
  інакше `onload` не спрацює.
- Iframe більший за вʼюпорт (напр. 1440×900 у вікні 709) — нормально для замірів: геометрія
  чесна, просто скріншот обрізаний знизу. Смуга шапки лишається видимою, тож для дефектів
  накладання цього достатньо.
- Скріншот сходиться з CSS-координатами з коефіцієнтом: кадр 1568 px на вʼюпорт 1440 → ×1,089.
  Координати для `computer.left_click` рахувати саме так; промах у 30 px виглядає як «клік не
  спрацював».
