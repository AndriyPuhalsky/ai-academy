## Як саме звірено (і що я НЕ перевіряв)

Робочих інструментів Supabase MCP у моєму тулсеті не виявилось — тільки
`authenticate` / `complete_authentication`. Тулсет підагента фіксується в момент запуску,
тож автентифікація власника мене не дістала (те саме було в попереднього агента).
Читав двома іншими шляхами:

**Прочитано МНОЮ з живої бази сьогодні (2026-09-03):**

| Що | Як | Результат |
| -- | -- | --------- |
| `courses` — усі колонки | PostgREST, anon-ключ (`courses_read` = `using (true)`) | 2 рядки, `sort_order` = 1 і 2 → новому даю **3** |
| `modules` — коди, номери, `passing_score`, `sort_order` | те саме | 34 рядки · **усі** `passing_score` = 70 · **усі** `sort_order` = 0 · коди `m01…m12`, `a01…a22` — глобально унікальні |
| Сигнатури всіх 9 функцій | Dashboard → Database → Functions | збігаються з аудитом до символу |
| Тіло `maybe_issue_certificate` (рядки 1–22) | Dashboard → Edit function | збігається з аудитом **дослівно**, включно з `coalesce(full_name, email, 'Студент')` |
| Мова й початок тіла `admin_user_report` | те саме | **`language sql`** (не plpgsql), `with ess as (… slug = 'ai-essentials' …)` |
| Security Advisor | Dashboard → Advisors | 17 warnings: 8 «Public Can Execute SECURITY DEFINER» + 8 «Signed-In Users Can Execute» + 1 «Leaked Password Protection». **`admin_user_report` у цих списках НЕМАЄ** → EXECUTE у `anon`/`authenticated` для неї відкликаний |

**НЕ перевірено, і це впливає на міграцію:**

- **Точне значення `search_path` на функціях.** SQL Editor мені заборонений, а панель
  Dashboard не докручується до Advanced settings (спробував три способи, включно зі
  збільшенням вікна). **Непрямий висновок:** серед 17 попереджень Advisor **немає жодного
  `Function Search Path Mutable`** — отже `search_path` на функціях **стоїть**, просто я не
  бачу яким. Як я це закрив — див. «Ризик, який лишається».
- **`count(*)` по `profiles` / `enrollments`** — закриті RLS для `anon`. Беру числа з аудиту
  002 (3 профілі, 6 зарахувань = 3 × 2 курси). Для міграції не критично: backfill написаний
  як `select … from public.profiles`, тож накриє скільки б їх не було.
- **Рядки 23–27 тіла `maybe_issue_certificate`** (сам `insert … on conflict`) — редактор
  Dashboard далі не прокрутився. Видно початок рядка 23, збігається з аудитом.

**У базі нічого не змінював.** Жодного `apply_migration` / `execute_sql`, «Run» у SQL Editor
не тиснув. Дві панелі `Edit function` відкривав **для читання** й закривав через **Cancel** —

## Що зроблено

Один файл: **`db/005-1-course-ai-terminal.sql`** (577 рядків, п'ять частин + перевірки + відкат).
Коду сайту не торкався — у цій задачі продукт це SQL і звіт.

### Частина 1 — курс

`slug = 'claude-code'`, `title = 'AI Термінал'`, **`is_paid = false`**, `price_uah = null`,
`sort_order = 3`, змістовний `description`. Ідемпотентно через `on conflict (slug) do nothing`.

`is_paid = false` — не косметика: `handle_new_user` зараховує новачків запитом
`where c.is_paid = false`. З `true` не зарахувався б **ніхто**, а `module_unlocked` першою ж
перевіркою вимагає активного зарахування — курс виглядав би зламаним при 23 цілих модулях.

### Частина 2 — 23 модулі

`c01`…`c23`, `number` **суцільно 1…23**, слаги `modules/claude-code-01.html`…`-23.html`,
назви **дослівно з `program.md`** (перевірено скриптом: 23/23 збігів, 0 розбіжностей).
Ідемпотентно через `on conflict (course_id, code) do nothing`.

**Обране й обґрунтоване:**

- **`passing_score` іспиту `c23` = 85** (решта 70, як у всіх 34 наявних). Чому саме 85, а не
  «90 бо солідно»: клієнт надсилає **відсоток** `Math.round(correct / total * 100)`
  (`js/quiz.js:162`), тож при запланованих ~25 питаннях досяжні значення кратні 4.
  85 означає: 21/25 = 84 % — **не** проходить, 22/25 = 88 % — проходить. Тобто «щонайбільше
  3 помилки з 25». 90 дало б 23/25 (2 помилки) — надто жорстко для безкоштовного курсу;
  80 збіглося б із 20/25 і майже не відрізнялось би від 70.
- **`sort_order` модулів = 0**, як у всіх 34 наявних. Колонка мертва: жодна функція її не
  читає, порядок тримається на `number`. Свідомо **не** нумерував 1…23 — тоді в одній
  колонці співіснували б дві угоди, і `order by sort_order` виглядав би осмисленим,
  лишаючись випадковим (34 нулі + 23 впорядковані). Краще однорідно мертве поле, ніж
  наполовину живе.
- **`sort_order` курсу = 3** — там значення явно осмислені (1 і 2), продовжую ряд.

**Додав запобіжник, якого не було в завданні:** `DO`-блок після вставки перевіряє
`count = 23`, `min = 1`, `max = 23`, `count(distinct number) = 23` і **кидає exception**,
якщо ні. Причина: дірка в нумерації робить усе після неї недосяжним **назавжди** і **мовчки**
— сайт виглядає справним, а учень упирається в «Модуль ще заблоковано» без причини.
Помилка відкочує всю транзакцію: краще не застосувати нічого, ніж застосувати курс із пасткою.

### Частина 3 — backfill зарахувань

```sql
insert into public.enrollments (user_id, course_id)
select p.id, c.id from public.profiles p cross join public.courses c
 where c.slug = 'claude-code'
on conflict (user_id, course_id) do nothing;
```

Дзеркалить `handle_new_user`: вставляються **тільки** `(user_id, course_id)`, а `status`
(`'active'`) і `granted_at` беруться з default — свого варіанта тут немає навмисно.

**Скільки рядків додасться: рівно по одному на кожен наявний профіль.** За останньою
звіркою (2026-08-23) профілів було **3** → очікується **3 рядки**. Точне число власник
побачить перевіркою №4 — вона ж покаже `not_enrolled = 0`.

### Частина 4 — сертифікат більше не друкує email

`coalesce(full_name, email, 'Студент')` → `coalesce(nullif(btrim(full_name, E' \t\r\n'), ''), 'Студент')`.

Закриває **три** дефекти, а не один:

1. `NULL` → друкувався **email**, і `verify_certificate` (публічна, для `anon`) віддавала
   його кожному, хто знає код сертифіката;
2. **порожній рядок** `''` — не NULL, тож старий `coalesce` його пропускав → сертифікат із
   порожнім іменем;
3. **самі пробіли/таби** — те саме, плюс зсунутий текст у PDF.

Побічно: у `certificates.full_name` тепер лягає вже підчищене значення.

Решта тіла збережена дослівно, функція переписана цілком через `create or replace`.

### Частина 5 — `admin_user_report` без захардкодженого курсу

Прибрано `with ess as (… slug = 'ai-essentials' …)`. Показники рахуються по **всіх** курсах,
тож четвертий курс підхопиться сам.

**Форму довелося зберегти точно, і це не стилістика.** `tg/telegram_index.ts` жорстко
зав'язаний на контракт:

- `toCsv` (`tg/telegram_index.ts:100`) хардкодить рівно сім колонок **за іменами**
  `email, full_name, role, registered, completed, total, certificate` — нова колонка
  (напр. `course`) у CSV просто зникла б;
- `/stats` рахує `Користувачів: rows.length` (`:132`) — при «рядку на курс» троє
  користувачів стали б «Користувачів: 9».

Тому: **сім тих самих колонок, один рядок = один користувач**. Це виключило варіант
«рядок на курс», який інакше був би природнішим.

### Ризик, який лишається (і як я його прикрив)

`create or replace function` замінює визначення **цілком, включно з конфігурацією функції** —
якщо не написати `set search_path`, наявне значення буде **втрачено мовчки**. Значення я
прочитати не зміг (див. вище). Що зроблено:

- у файлі `search_path` заданий **явно**: `public, pg_temp` (`pg_temp` останнім — так
  рекомендує документація Postgres для `SECURITY DEFINER`, щоб тимчасова схема нічого не
  перекрила);
- це безпечно за **будь-якого** поточного значення, бо в обох тілах **усі** об'єкти
  схемо-кваліфіковані (`public.modules`, `public.progress`, `public.profiles`,
  `public.certificates`, `public.courses`), а `gen_random_uuid()` на Postgres 13+ живе в
  `pg_catalog`, який шукається завжди;
- крок 0 дає власнику побачити старе значення, і у файлі написано: якщо воно інше —
  підставити його і в міграцію, і у відкат;
- перевірка №7 після застосування показує `proconfig` обох функцій.

`GRANT`-и `create or replace` не чіпає — вужчі права `admin_user_report` (EXECUTE
відкликаний у `anon`/`authenticated`) збережуться. Це правильний стан, ламати його не треба.

## Що перевірив і як

Прод-базу цим файлом **не чіпав** — перевіряв статично, але не «на око»:

1. **Синтаксис — справжнім парсером PostgreSQL 17**, не читанням. Поставив `pglast` 8.4
   (обгортка libpg_query) у `/tmp` і розібрав файл цілком:
   `PARSE OK — statements: 17` (`begin`, 3 × `InsertStmt`, `DoStmt`, 2 × `CreateFunctionStmt`,
   `commit`, 9 перевірочних `SelectStmt`).
   У корінь проєкту нічого не ставив — правило «жодного npm/залежностей у корені» не порушено.
2. **Тіла plpgsql — окремим plpgsql-парсером** (`parse_plpgsql`), бо зовнішній розбір бачить
   їх лише як рядок: `DO`-блок — OK, `maybe_issue_certificate` — OK.
3. **Тіло `admin_user_report`** розібрано як SQL окремо (1 statement) + перевірено, що
   рядка `ai-essentials` в ньому більше **немає**.
4. **23 рядки модулів — скриптом, а не очима:** коди суцільні `c01…c23` ✓, номери 1…23 ✓,
   слаги за шаблоном ✓, **усі слаги в нижньому регістрі** ✓ (та сама пастка, що вже раз
   ламала прод), `passing_score` = 70 × 22 і 85 × 1 ✓, перетину з живими `m01…m12` /
   `a01…a22` немає ✓.
5. **Назви модулів звірені з `program.md` програмно** — 23/23, нуль розбіжностей
   (включно з апострофом у `CLAUDE.md і пам'ять`, який у SQL екранований як `''`).
6. **Контракт із ботом** перевірений читанням `tg/telegram_index.ts:99-110, 124-146` — саме
   звідти вимога «сім колонок, рядок на користувача».

**Чого НЕ перевіряв (чесно):**

- **Міграцію не запускав ніде** — окремої dev-бази в проєкті немає, а прод чіпати
  заборонено. Парсер підтверджує синтаксис, але **не** підтверджує, що `on conflict
  (course_id, code)` збігається з реальним іменем обмеження, що enum `enrollment_status`
  має default `'active'`, і що `create or replace` не впаде на розбіжності сигнатури.
  Усе це взято зі схеми в `audit-gate.md`.
- **Локальний сайт не піднімав** — коду сайту не торкався, перевіряти нічого.
- **Реальний `/stats` після зміни** — побачити можна лише після застосування.

  **відсоток** `Math.round(correct/total*100)`, як зараз у `js/quiz.js`. При 25 питаннях
  прохідний бал — 22 правильні.
- **Три довідники (`claude-code-ref-*.html`) рядків у `modules` НЕ мають** і мати не повинні:
  без квізу, без прогресу, поза сертифікатом. Не додавати їх у `modules` «щоб було» — це
  зіпсувало б `maybe_issue_certificate` (він рахує `count(*) from modules where course_id = …`,
  і сертифікат перестав би видаватись, бо довідники ніколи не стануть `completed`).
- **Нових ключів конфігу від мене не потрібно.** RPC ті самі (`submit_quiz`,
  `uncomplete_module`), формат помилок не змінився («Не авторизовано», «Модуль не знайдено»,
  «Модуль ще заблоковано»).
- Курс стає публічно читабельним автоматично: `courses_read` / `modules_read` = `using (true)`.
  Нових політик RLS і грантів для 005 **не потрібно** — і я їх не додавав.

## Що передати тестувальнику

**Де найімовірніше зламається:**

1. **Найгостріше: перший модуль «заблоковано» у наявного акаунта.** Ознака, що backfill
   (частина 3) не відпрацював або міграцію застосували частково. Відтворення: зайти
   акаунтом, створеним **до** застосування міграції, і натиснути завершення `c01`.
   Очікувано — проходить. Помилка «Модуль ще заблоковано» = немає рядка в `enrollments`.
   **Новий акаунт цю помилку не покаже** (його накриє `handle_new_user`), тож тестувати
   треба саме старим.
2. **Порядок модулів.** `c05` не має відкриватись, доки не завершено `c04`. Це серверна
   перевірка (`submit_quiz` → `module_unlocked`), клієнтське блокування — лише UX. Обходити
   клієнт безглуздо: сервер відмовить.
3. **Сертифікат.** Видається автоматично після **23-го** завершеного модуля (не 22!) —
   `maybe_issue_certificate` кличеться після кожного успішного модуля й спрацює на останньому.
   **Тест із порожнім `full_name` — головний у цій задачі:** сертифікат мусить показати
   «Студент», а **не email**. Перевірити і в PDF, і на публічній `/verify` за кодом.
4. **Чужі курси не зачеплені.** Регресійна перевірка: AI Академія (`m01…m12`) і AI Architect
   (`a01…a22`) розблоковуються як раніше. Якби коди перетнулись, `buildModuleMap` мовчки
   затер би чужий модуль — саме тут це вилізло б.
5. **Бот.** `/stats` має показувати `усього` = 57, а не 12. `/export` — CSV із сімома
   колонками й без дублів email.

**Обмеження, яке треба пам'ятати:** dev-превʼю працює з **продовою** базою. Проходження
модулів створює справжні `progress` / `quiz_attempts`, а завершення курсу — **справжній
сертифікат із публічним кодом**, який неможливо перевидати (`on conflict do nothing`).
Повне проходження курсу до кінця — тільки з дозволу власника й призначеним тестовим акаунтом.

## Знайдене поза обсягом (не чіпав)

1. **`js/auth.js:172-183` — `buildModuleMap` читає модулі БЕЗ фільтра за курсом**
   (`select("id, code")` → `map[m.code] = m.id`). У базі стоїть лише `UNIQUE(course_id, code)`,
   тобто СУБД **дозволить** двом курсам мати однаковий `code`, а клієнт тоді мовчки затре
   один модуль іншим — і живий курс почав би відповідати «Модуль ще заблоковано».
   **Правило на майбутнє: будь-який новий курс мусить мати глобально унікальні `code`.**
   Префікс — не стильова угода, а несуча конструкція. `buildModuleMap` **не чіпав** свідомо:
   це зачепило б два живі курси заради проблеми, якої зараз немає. Те саме стосується
   `hydrateProgress` і `js/certificate.js` — обидва теж читають глобально.
2. **`ai-architect`: `is_paid = false` при `price_uah = 499900`** і описі «Платний курс».
   Зараз працює як безкоштовний (і всі в нього зараховуються автоматично). Це або
   свідоме «поки безкоштовно», або забутий хвіст — але дані самі собі суперечать.
   Рішення за власником, не чіпав.
3. **`maybe_issue_certificate(p_user, …)` і `module_unlocked(p_user, …)` беруть користувача
   параметром і не звіряють його з `auth.uid()`**, EXECUTE відкритий для `anon` (підтверджено
   сьогодні Security Advisor: 8 функцій у списках «Public/Signed-In Users Can Execute»).
   Підробити сертифікат не дає, але шаблон поганий. Стан не змінився з findings 002.
4. **Leaked password protection досі вимкнено** — єдине попередження Advisor, не пов'язане
   з функціями. Вмикається в Dashboard → Authentication → Passwords, коду не потребує.
5. **`modules.slug` без унікального обмеження** — два модулі можуть мати однаковий slug,
   а `js/module.js` шукає модуль за slug. Для 005 закрито дисципліною (перевірив скриптом),
   але обмеження в базі не існує.
